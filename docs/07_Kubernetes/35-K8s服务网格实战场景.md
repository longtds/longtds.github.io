# Kubernetes 服务网格实战场景（Istio 为主）

> 服务网格不是"装完就完事了"，真正的价值在场景里。本文不讲原理堆概念，直接聚焦服务网格在生产里**真能用得上**的 8 大场景：灰度发布、流量镜像、金丝雀、零信任 mTLS、故障注入、熔断限流、可观测性、多集群，每个场景都给 YAML、命令、预期结果和踩坑清单。

---

## 一、服务网格解决什么问题？选型总览

### 1.1 从 SDK 到 Sidecar

```text
微服务网络能力演进:

  阶段 1: 业务代码里写死 (硬编码重试/超时/鉴权)
    每个团队自己实现一套, 语言不通就各写各的, 10 个服务 10 个版本

  阶段 2: 公共 SDK (Spring Cloud / Dubbo / Sentinel)
    统一封装成库, 业务引入依赖就能用
    问题: 多语言难搞、升级要业务改代码、异构系统接不上

  阶段 3: 服务网格 (Sidecar 代理)
    ┌───────────────────────────────────────────┐
    │  Pod                                     │
    │  ┌──────────┐         ┌──────────────┐  │
    │  │ 业务容器  │ ◄────► │  Sidecar 代理 │  │
    │  │ (业务代码)│ 本地回环 │ (envoy/linkerd)│  │
    │  └──────────┘         └──────┬───────┘  │
    └──────────────────────────────┼──────────┘
                                   │
                                   ▼
                          控制面 ( istiod / 控制面 )
                        下发路由 / 安全 / 遥测配置

    业务零侵入: 不用改代码, 不用引 SDK, 多语言统一
    网络能力下沉到基础设施层
```

**服务网格能做（且值得做）的事**：

| 能力 | 不用网格怎么做 | 用了网格怎么做 |
|:---|:---|:---|
| 灰度发布 | 改 Deployment 副本数 / 自己写脚本 | VirtualService + DestinationRule 一条 YAML |
| 流量镜像 | 自己写流量复制工具 / 靠日志回放 | 一条镜像规则，线上流量复制到影子集群 |
| mTLS | 每个服务自己管证书、自己建 TLS | 自动签发自动轮换，业务零感知 |
| 熔断限流 | SDK 做 (Sentinel/Hystrix)，多语言各一套 | DestinationRule 统一配 |
| 故障注入 | 自己改代码模拟 / 人工拔网线 | HTTP 延迟/中止/错误码，按比例注入 |
| 可观测性 | 每个服务埋点，格式不统一 | 自动出 metrics/tracing/accesslog |
| 零信任安全 | 网络层 ACL + 应用层 Token | 认证 (mTLS) + 授权 (RBAC) + 审计 |
| 多集群服务发现 | 各集群独立 + 外部 LB | 东西向全局服务发现 + 流量调度 |

### 1.2 主流服务网格对比

| 维度 | Istio | Linkerd | Kuma | Cilium Service Mesh |
|:---|:---|:---|:---|:---|
| 数据面 | Envoy | Linkerd2-proxy (Rust) | Envoy | eBPF + (可选) Envoy |
| 控制面 | istiod | control-plane | kuma-cp | Cilium agent |
| 成熟度 | 最高 (最广泛生产) | 高 (Buoyant 商业化) | 中 (Kong 开源) | 快速上升 (eBPF 路线) |
| 资源开销 | 中高 (每个 sidecar ~100MB 内存) | 低 (~10-20MB) | 中 | 最低 (eBPF 无 sidecar) |
| 功能丰富度 | 最丰富 | 够用 (80% 场景) | 中 (多集群强) | 基础功能 + eBPF 特性 |
| 学习曲线 | 陡 (CRD 多、概念多) | 平缓 | 中 | 中 |
| 多集群支持 | 强 (多模式) | 中 | 强 | 中 |
| 适用场景 | 大型企业、复杂需求 | 中小团队、追求轻量 | 多集群/多租户 | 追求性能、不想加 sidecar |

**选型一句话**：
- 大厂 / 复杂需求 / 生态要全 → **Istio**
- 小团队 / 资源紧 / 只想要核心功能 → **Linkerd**
- eBPF 路线 / 不想装 sidecar / 性能极致 → **Cilium Service Mesh**
- 多集群多租户混合云 → 都能做，Istio 和 Kuma 更成熟

> ⚠️ 服务网格不是银弹。它本身也是一套分布式系统，装上就多了一套要运维的东西。**只有 30+ 微服务、多语言、对流量治理有强需求**的时候，收益才大于成本。

## 二、环境准备：Istio 快速安装

### 2.1 安装 Istio

```bash
# 下载 istioctl
curl -L https://istio.io/downloadIstio | sh -
cd istio-*
export PATH=$PWD/bin:$PATH

# 安装 (demo 配置文件适合测试, 生产用 default 或 ambient)
istioctl install --set profile=demo -y
# 常用 profile:
#   - demo: 全开, 适合测试 (不要生产用)
#   - default: 生产推荐
#   - minimal: 只装控制面
#   - ambient: Ambient Mesh (无 sidecar)

# 验证
kubectl get pods -n istio-system
# NAME                                    READY   STATUS
# istio-egressgateway-...                 1/1     Running
# istio-ingressgateway-...                1/1     Running
# istiod-...                              1/1     Running
```

### 2.2 注入 Sidecar

```bash
# 方式一: 命名空间自动注入 (推荐)
kubectl label namespace default istio-injection=enabled

# 方式二: 手动注入单个 Deployment
istioctl kube-inject -f deployment.yaml | kubectl apply -f -

# 验证注入
kubectl get pod -n default
# NAME                      READY   STATUS    RESTARTS
# reviews-v1-...            2/2     Running   0       ← 2 个容器 = 业务 + sidecar

# 看 sidecar 是否就绪
istioctl proxy-status
```

### 2.3 示例应用：Bookinfo

Istio 官方的 Bookinfo 示例（4 个微服务），本文所有场景都基于它：

```bash
# 部署 bookinfo
kubectl apply -f samples/bookinfo/platform/kube/bookinfo.yaml
kubectl apply -f samples/bookinfo/networking/bookinfo-gateway.yaml

# 验证
kubectl get services
kubectl get pods

# 获取入口地址
export INGRESS_HOST=$(kubectl -n istio-system get service istio-ingressgateway -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
export INGRESS_PORT=$(kubectl -n istio-system get service istio-ingressgateway -o jsonpath='{.spec.ports[?(@.name=="http2")].port}')
echo "http://$INGRESS_HOST:$INGRESS_PORT/productpage"

# 访问一下
curl -s "http://$INGRESS_HOST:$INGRESS_PORT/productpage" | grep -o "<title>.*</title>"
```

**Bookinfo 服务拓扑**：

```text
                ┌──────────────┐
                │ productpage  │ ← 入口 (Python)
                └──────┬───────┘
                       │
         ┌─────────────┼─────────────┐
         ▼             ▼             ▼
    ┌─────────┐  ┌──────────┐  ┌──────────┐
    │ details │  │ reviews  │  │ ratings  │
    │  (Ruby) │  │  (Java)  │  │  (Node)  │
    └─────────┘  └────┬─────┘  └────┬─────┘
                      │             │
                      └─────────────┘
                         reviews 调用 ratings

  reviews 有三个版本:
    v1: 不调用 ratings (没星星)
    v2: 调用 ratings, 黑星
    v3: 调用 ratings, 红星
```

整个文章的所有场景都围绕这个应用展开。

## 三、场景一：金丝雀发布（Canary）

### 3.1 场景说明

**需求**：新版本 v2 先放 10% 流量，观察没异常再逐步涨到 50%、100%，出问题秒回滚。

```text
金丝雀流量分配:

  用户流量
     │
     ▼
  ┌──────────────┐
  │ productpage  │
  └──────┬───────┘
         │ 100%
         ▼
  ┌───────────────────── reviews ─────────────────────┐
  │                                                     │
  │   90% ────► reviews-v1 (旧版本, 稳定)              │
  │   10% ────► reviews-v2 (新版本, 验证)              │
  │                                                     │
  └─────────────────────────────────────────────────────┘
```

### 3.2 配置步骤

```yaml
# DestinationRule: 定义 subsets (版本子集)
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: reviews
spec:
  host: reviews
  subsets:
    - name: v1
      labels:
        version: v1
    - name: v2
      labels:
        version: v2
    - name: v3
      labels:
        version: v3
---
# VirtualService: 定义流量分配规则
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts:
    - reviews
  http:
    - route:
        - destination:
            host: reviews
            subset: v1
          weight: 90          # 90% 流量走 v1
        - destination:
            host: reviews
            subset: v2
          weight: 10          # 10% 流量走 v2
```

```bash
# 应用配置
kubectl apply -f reviews-dr.yaml
kubectl apply -f reviews-vs-canary.yaml

# 验证: 发 100 次请求, 统计 v1/v2 比例
for i in $(seq 1 100); do
  curl -s "http://$INGRESS_HOST:$INGRESS_PORT/productpage" | \
    grep -oE 'color="black"|color="red"|no rating' | \
    head -1
done | sort | uniq -c

# 预期:
#   ~90 个 no rating (v1)
#   ~10 个 color="black" (v2)
```

### 3.3 逐步放量与回滚

```bash
# 逐步放量: 改 weight (50/50)
kubectl patch vs reviews --type=json -p='[
  {"op":"replace","path":"/spec/http/0/route/0/weight","value":50},
  {"op":"replace","path":"/spec/http/0/route/1/weight","value":50}
]'

# 全量: 100% 切到 v2
kubectl patch vs reviews --type=json -p='[
  {"op":"replace","path":"/spec/http/0/route/0/weight","value":0},
  {"op":"replace","path":"/spec/http/0/route/1/weight","value":100}
]'

# 回滚: 出问题立刻切回 v1
kubectl patch vs reviews --type=json -p='[
  {"op":"replace","path":"/spec/http/0/route/0/weight","value":100},
  {"op":"replace","path":"/spec/http/0/route/1/weight","value":0}
]'

# 更简单的回滚: 直接删 VirtualService (恢复 K8s 默认轮询)
kubectl delete vs reviews
```

### 3.4 基于指标的自动金丝雀（Flagger）

手动放量太慢且靠人盯着不可靠。生产上推荐用 **Flagger** 做自动金丝雀：自动放量、自动分析指标（成功率/延迟/错误率）、不达指标自动回滚。

```bash
# 安装 Flagger
helm repo add flagger https://flagger.app
helm upgrade -i flagger flagger/flagger \
  --namespace istio-system \
  --set meshProvider=istio \
  --set metricsServer=http://prometheus.istio-system:9090
```

```yaml
# Flagger Canary 资源
apiVersion: flagger.app/v1beta1
kind: Canary
metadata:
  name: reviews
  namespace: default
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: reviews-v2
  progressDeadlineSeconds: 60
  autoscalerRef:
    apiVersion: autoscaling/v2
    kind: HorizontalPodAutoscaler
    name: reviews
  service:
    port: 9080
    targetPort: 9080
  analysis:
    interval: 1m          # 每 1 分钟分析一次
    threshold: 10         # 最多 10 次失败就回滚
    maxWeight: 50         # 最大放 50%
    stepWeight: 10        # 每次加 10%
    metrics:
      - name: request-success-rate
        thresholdRange:
          min: 99         # 成功率 < 99% 就回滚
      - name: request-duration
        thresholdRange:
          max: 500        # P95 延迟 > 500ms 就回滚
```

> Flagger 是生产级金丝雀的标配。自己写脚本放量 + 人工看指标 = 迟早翻车。

### 3.5 踩坑清单

| 坑 | 现象 | 解决 |
|:---|:---|:---|
| weight 加起来不等于 100 | Istio 直接拒绝配置 | weight 之和必须 = 100 |
| subsets 不存在 | VirtualService 配了但 503 | 先确认 DestinationRule 的 subset label 对不对 |
| 流量比例和预期偏差大 | 90/10 实际跑出来 70/30 | 流量小的时候概率偏差正常, 样本量够了就收敛 |
| 灰度期间 Pod 重启了 | 灰度比例被重置 | 用 Flagger 管理, 不要手动改 |
| 数据库不兼容新旧版本 | 新版本跑一半报错 | 金丝雀只管流量, 不管数据; 数据库要做向后兼容 |

## 四、场景二：基于用户特征的灰度（Header / Cookie）

### 4.1 场景说明

**需求**：让内部员工 / 特定用户 / 某个地区的用户走新版本，其他用户走旧版本。比按比例金丝雀更可控。

```text
按 Header 灰度:

  用户请求 (带 Header: x-user=internal)
            │
            ├─ 内部用户 → reviews-v2 (新版本)
            │
            └─ 普通用户 → reviews-v1 (旧版本)
```

### 4.2 配置步骤

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts:
    - reviews
  http:
    # 规则 1: 带特定 header 的走 v2
    - match:
        - headers:
            x-user-group:
              exact: beta          # header 值精确匹配 beta
      route:
        - destination:
            host: reviews
            subset: v2

    # 规则 2: 特定 cookie 的走 v3
    - match:
        - headers:
            cookie:
              regex: "^(.*?;)?(user=vip)(;.*)?$"    # cookie 里有 user=vip
      route:
        - destination:
            host: reviews
            subset: v3

    # 默认: 其余走 v1
    - route:
        - destination:
            host: reviews
            subset: v1
```

**支持的匹配方式**：

| 匹配类型 | 关键字 | 示例 |
|:---|:---|:---|
| 精确匹配 | `exact` | `exact: "beta"` |
| 前缀匹配 | `prefix` | `prefix: "/api/v2"` |
| 正则匹配 | `regex` | `regex: "^/api/v[23]"` |
| 包含 | 不用关键字, 直接写 | 用正则 `.*keyword.*` |

```bash
# 测试: 普通用户
curl -s "http://$INGRESS_HOST:$INGRESS_PORT/productpage" | grep -c "no rating"
# → 全是 v1

# 测试: beta 用户 (带 header)
curl -s -H "x-user-group: beta" \
  "http://$INGRESS_HOST:$INGRESS_PORT/productpage" | grep -c 'color="black"'
# → 全是 v2

# 测试: vip 用户 (带 cookie)
curl -s -H "Cookie: user=vip" \
  "http://$INGRESS_HOST:$INGRESS_PORT/productpage" | grep -c 'color="red"'
# → 全是 v3
```

### 4.3 生产常用变体

**按租户灰度**：`x-tenant-id` header 匹配特定租户 → 先走新版本。

**按地域灰度**：Ingress 层把用户地域塞到 header 里 → 服务网格按 header 路由。

**按百分比灰度 + 按用户灰度组合**：先给 10% 的 beta 用户放新版本，这批人没问题再放 10% 全量。

### 4.4 踩坑清单

| 坑 | 现象 | 解决 |
|:---|:---|:---|
| match 顺序问题 | 下面的规则永远不命中 | VirtualService 的 http 规则是**按顺序匹配**，第一个命中就返回 |
| header 大小写敏感 | X-User-Group 和 x-user-group 不匹配 | Istio/Envoy 是 case-insensitive，没问题；但自己写正则要注意 |
| cookie 正则写错 | 匹配不到 | 用 `regex` 测试好，cookie 格式多变 |
| 前端没带 header | 灰度流量一直是 0 | 让前端/网关在入口处注入 header |

## 五、场景三：流量镜像（Traffic Mirroring）

### 5.1 场景说明

**需求**：把线上真实流量**复制一份**发给新版本（影子服务），新版本怎么崩都不影响用户。用真实流量验证新版本的正确性和性能，比压测靠谱 10 倍。

```text
流量镜像:

  真实用户流量 ──► reviews-v1 (生产, 返回响应)
                   │
                   └──► 复制一份 → reviews-v2 (影子, 响应丢弃)
                                   │
                                   ▼
                             日志 / 指标对比
                             (验证 v2 有没有报错)
```

### 5.2 配置步骤

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts:
    - reviews
  http:
    - route:
        - destination:
            host: reviews
            subset: v1
          weight: 100
      # 镜像: 复制流量到 v2
      mirror:
        host: reviews
        subset: v2
      # 镜像流量占比 (默认 100%)
      mirrorPercentage:
        value: 100.0
```

```bash
# 部署
kubectl apply -f reviews-vs-mirror.yaml

# 发 10 次请求
for i in $(seq 1 10); do
  curl -s "http://$INGRESS_HOST:$INGRESS_PORT/productpage" > /dev/null
done

# 观察 v2 的访问日志 (影子服务有没有收到流量)
kubectl logs -l app=reviews,version=v2 -c reviews | tail -20
# 应该能看到 10 条请求日志
# 但用户侧收到的都是 v1 的响应 (v2 的响应被丢弃了)
```

### 5.3 生产里怎么用

```text
典型流量镜像工作流:

  1. 上线新版本 v2, 但不给流量
  2. 配置镜像规则, 把 v1 流量复制给 v2
  3. 跑 24 小时, 收集 v2 的:
     - 错误率 (和 v1 比)
     - 延迟分布 (P50 / P95 / P99)
     - 异常日志数
  4. 指标达标 → 切 1% 金丝雀
  5. 逐步放量 → 全量
  6. 不达标 → 修 v2, 重新跑镜像
```

**指标对比方法**：
- Prometheus 里对 v1/v2 的 `istio_requests_total` / `istio_request_duration_milliseconds` 做对比查询
- 用脚本比对 v1/v2 的响应体（接口维度的功能正确性）
- 日志平台里 v2 报错数 / v1 报错数

### 5.4 踩坑清单

| 坑 | 现象 | 解决 |
|:---|:---|:---|
| 写操作被执行了两次 | 镜像流量也写了数据库 | 影子服务要接**影子数据库** / 只镜像 GET 请求 / 应用层识别镜像请求丢弃写操作 |
| 下游压力翻倍 | 镜像也调用下游，下游扛不住 | 控制 `mirrorPercentage` 比例，从 1% 开始 |
| 延迟没增加但资源用得更多 | CPU/内存翻倍是正常的 | 准备好资源，或者降镜像比例 |
| 幂等问题 | 非幂等接口镜像后数据乱了 | 只镜像读请求，或确保写接口幂等 |
| 追踪乱了 | 同一个请求出现在两个服务里，trace 乱 | 镜像请求的 header 里有 `x-envoy-shadowed: true`，可识别 |

## 六、场景四：mTLS 零信任安全

### 6.1 场景说明

**需求**：服务之间通信全部加密，并且要认证对方身份（"你是谁"），再加上授权（"你能不能访问我"）。零信任网络的核心。

```text
mTLS 工作方式:

  service-a (sidecar) ──── mTLS 握手 ────► service-b (sidecar)
       │                                        │
       ├─ 出示证书 (spiffe://cluster.local/ns/default/sa/a)
       └─ 验证对方证书 (spiffe://cluster.local/ns/default/sa/b)

  身份 = SPIFFE ID = 服务账户 (ServiceAccount)
  证书自动签发 / 自动轮换 (istiod 是 CA)
  业务零感知: 代码不用改, 侧车自动处理
```

### 6.2 配置 mTLS

**全局 mTLS（STRICT 模式）**：

```yaml
# 网格级: 所有服务强制 mTLS
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: istio-system    # 必须在 istio-system 才是全局
spec:
  mtls:
    mode: STRICT   # STRICT=必须 mTLS, PERMISSIVE=可选(兼容没sidecar的), DISABLE=关闭
```

**命名空间级 mTLS**：

```yaml
# 只对 prod 命名空间强制 mTLS
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: prod
spec:
  mtls:
    mode: STRICT
```

**单服务级 mTLS**（针对特定服务关闭）：

```yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: legacy-app
  namespace: prod
spec:
  selector:
    matchLabels:
      app: legacy-app      # 老应用没 sidecar, 单独关 mTLS
  mtls:
    mode: DISABLE
```

```bash
# 验证 mTLS 生效

istioctl proxy-config listener <pod-name> --port 9080 -o json | grep -i tls

# 方法 2: 用一个没 sidecar 的 Pod 去访问 (应该不通)
kubectl run --rm -it test --image=curlimages/curl -- \

# 方法 3: 直接看认证策略
```

### 6.3 授权策略（AuthorizationPolicy）

光有认证（"你是谁"）不够，还要授权（"你能不能访问我"）。

```yaml
# 默认拒绝: 先把所有流量都拒了 (每个命名空间放一条)
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: deny-all
  namespace: prod
spec:
  {}    # 空规则 = 匹配所有 + 拒绝所有

---
# 放行: productpage 可以访问 reviews
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: reviews-allow
  namespace: prod
spec:
  selector:
    matchLabels:
      app: reviews
  action: ALLOW
  rules:
    - from:
        - source:
            principals: ["cluster.local/ns/prod/sa/productpage"]
      to:
        - operation:
            methods: ["GET"]
            paths: ["/reviews/*"]
```

**授权策略语法要点**：

| 字段 | 作用 | 示例 |
|:---|:---|:---|
| `selector` | 作用在哪些 Pod 上 | `matchLabels: {app: reviews}` |
| `action` | ALLOW / DENY / AUDIT | 默认 ALLOW |
| `rules.from` | 来源 (谁) | `principals` (mTLS 身份) / `namespaces` / `ipBlocks` |
| `rules.to` | 目标 (访问什么) | `methods` / `paths` / `ports` |
| `rules.when` | 条件 (header 等) | `key: request.headers[x-token], values: [admin]` |

```bash
# 验证: productpage 服务账户访问 → 通, 其他服务账户 → 403
kubectl exec -it <productpage-pod> -c istio-proxy -- \
  curl -s http://reviews:9080/reviews/1 -o /dev/null -w "%{http_code}\n"
# → 200

kubectl exec -it <其他服务pod> -c istio-proxy -- \
  curl -s http://reviews:9080/reviews/1 -o /dev/null -w "%{http_code}\n"
# → 403
```

### 6.4 踩坑清单

| 坑 | 现象 | 解决 |
|:---|:---|:---|
| 一刀切 STRICT | 没 sidecar 的服务全挂了 | 先用 PERMISSIVE 模式跑几天，确认所有服务都有 sidecar 再切 STRICT |
| 证书过期 | 大面积 TLS 握手失败 | Istio 自动轮换，正常不会；但控制面挂了就续不了，注意 istiod 高可用 |
| AuthorizationPolicy 写错 | 全拒了 / 全放了 | 先 AUDIT 模式观察几天再切 ALLOW/DENY |
| 跨命名空间授权忘了 ns | 策略不生效 | principals 里要写完整 SPIFFE ID（含 ns） |
| 健康检查被挡 | kubelet 探活走明文被 mTLS 挡 | Istio 有 `PILOT_USE_ENDPOINT_TRANSLATION` 自动处理，或用 `ExcludePorts` 排除探活端口 |

## 七、场景五：故障注入与混沌工程

### 5.1 场景说明

**需求**：主动注入故障（延迟、错误、中断），验证系统在依赖出问题时的表现——也就是服务层面的混沌工程。不用改代码，一条 YAML 搞定。

```text
故障注入类型:

  用户 → productpage → reviews → ratings
                     │
                     ├─ 注入延迟: 模拟下游慢
                     ├─ 注入中止: 模拟下游挂了
                     └─ 注入错误码: 模拟下游报错

  看 productpage 有没有超时 / 降级 / 重试, 验证容错能力
```

### 7.2 延迟注入

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: ratings
spec:
  hosts:
    - ratings
  http:
    - fault:
        delay:
          percentage:
            value: 50       # 50% 的请求注入延迟
          fixedDelay: 5s    # 延迟 5 秒
      route:
        - destination:
            host: ratings
            subset: v1
```

```bash
# 部署
kubectl apply -f ratings-delay.yaml

# 测试
time curl -s "http://$INGRESS_HOST:$INGRESS_PORT/productpage" > /dev/null
# 预期: 50% 的请求 ~5s 才返回, 其余正常快
```

### 7.3 错误注入

```yaml
apiVersion: networking.istio.io/v1alpha3

  name: ratings
spec:
  hosts:
    - ratings
  http:

          percentage:
```

```bash
done | sort | uniq -c

```

### 7.4 生产里怎么用

```text
故障注入使用流程 (生产环境):

  1. 先在测试环境跑过, 验证不会真把系统打爆
  2. 选低峰期 (凌晨 / 周末)
  3. 从小比例开始: 先 1% 延迟 500ms 跑 5 分钟
  4. 观察: 业务指标掉没掉, 告警触发了吗, 降级生效了吗
  5. 逐步加大比例 / 加大故障强度
  6. 出问题立刻停止: kubectl delete vs ratings
  7. 复盘: 哪些薄弱点暴露出来了, 下次改
```

**常见验证目标**：

| 注入什么故障 | 验证什么 |
|:---|:---|
| 下游 500ms 延迟 | 上游超时设置是否合理，重试会不会风暴 |
| 下游 5s 延迟 | 熔断有没有触发，降级逻辑有没有生效 |
| 下游 50% 503 | 重试策略会不会放大故障，有没有幂等保护 |
| 下游 100% 中断 | 快速失败还是雪崩，SLO 还保得住吗 |

### 7.5 踩坑清单

| 坑 | 现象 | 解决 |
|:---|:---|:---|
| 注入比例设大了 | 生产大面积报错 | 从小比例 (1%) 开始，随时准备回滚 |
| 忘记删故障规则 | 故障一直"存在"，业务真挂了 | 用完立刻删；最好在 CI 里加校验不允许长留 |
| 和真实故障混了 | 不知道是注入的还是真的 | 注入前标记清楚（时间 + 规则名），结束后核对 |
| delay 和 abort 同时配 | 行为和预期不一样 | 两个可以叠加：先延迟再中止；按需求分开配 |
| 影响了无关服务 | 注入在公共服务上全链路受影响 | 只对特定服务/路径注入，用 match 限制范围 |

## 八、场景六：熔断与限流

### 8.1 场景说明

**需求**：下游扛不住的时候，上游不能把请求一直往里塞，要及时熔断（直接失败），保护下游不被打死。同时限制单位时间的请求量，防止突发流量冲垮服务。

### 8.2 熔断（Circuit Breaker）

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: reviews
spec:
  host: reviews
  subsets:
    - name: v1
      labels:
        version: v1
      trafficPolicy:
        connectionPool:
          tcp:
            maxConnections: 100          # 最大连接数
          http:
            http1MaxPendingRequests: 50  # 等待队列
            maxRequestsPerConnection: 10 # 每个连接最大并发请求
            idleTimeout: 30m             # 空闲连接超时
        outlierDetection:                # 异常检测 (熔断核心)
          consecutive5xxErrors: 5        # 连续 5 个 5xx
          interval: 30s                  # 统计区间 30 秒
          baseEjectionTime: 30s          # 踢出至少 30 秒
          maxEjectionPercent: 50         # 最多踢掉 50% 的实例
          minHealthPercent: 20           # 至少保留 20% 健康实例 (防止全踢了)
```

**关键参数解释**：

| 参数 | 作用 | 默认值 |
|:---|:---|:---|
| `consecutive5xxErrors` | 连续多少个 5xx 就把这个实例踢掉 | 5 |
| `interval` | 异常检测的统计窗口 | 10s |
| `baseEjectionTime` | 最短踢出时间，之后尝试恢复（半开） | 30s |
| `maxEjectionPercent` | 最多踢掉百分之多少的实例 | 10% |
| `minHealthPercent` | 健康实例低于这个比例就不踢了（保命） | 0% |

```bash
# 部署
kubectl apply -f reviews-dr-circuit.yaml

# 用 Fortio 压测 (官方压测工具)
kubectl run -it --rm fortio --image=fortio/fortio -- \
  load -c 50 -n 500 http://reviews:9080/reviews/1
# -c 并发数 -n 总请求数

# 结果里看:
#   - 200 / 503 比例
#   - 延迟分布
# 熔断生效时, 503 会增多 (快速失败), 但不会拖垮下游
```

### 8.3 限流（Rate Limiting）

Istio 的限流有两种做法：**本地限流**（每个 sidecar 各自限流）和**全局限流**（通过 Redis 统一计数）。

**本地限流（Envoy local rate limit）**：

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: reviews-local-ratelimit
  namespace: default
spec:
  workloadSelector:
    labels:
      app: reviews
  configPatches:
    - applyTo: HTTP_FILTER
      match:
        context: SIDECAR_INBOUND
        listener:
          filterChain:
            filter:
              name: envoy.filters.network.http_connection_manager
              subFilter:
                name: envoy.filters.http.router
      patch:
        operation: INSERT_BEFORE
        value:
          name: envoy.filters.http.local_ratelimit
          typed_config:
            "@type": type.googleapis.com/envoy.extensions.filters.http.local_ratelimit.v3.LocalRateLimit
            stat_prefix: http_local_rate_limiter
            token_bucket:
              max_tokens: 100        # 桶里 100 个 token
              tokens_per_fill: 100   # 每秒补 100 个
              fill_interval: 1s
            filter_enabled:
              default_value:
                numerator: 100
                denominator: HUNDRED
            filter_enforced:
              default_value:
                numerator: 100
                denominator: HUNDRED
            response_headers_to_add:
              - append: false
                header:
                  key: x-envoy-ratelimited
                  value: "true"
```

```bash
# 压测验证: 超过 100/s 的部分返回 429
fortio load -c 10 -qps 200 -n 1000 http://reviews:9080/reviews/1
# 看结果里应该有 429 出现
```

> **本地限流 vs 全局限流**：本地限流简单但不精确（每个实例各自计，实例数多了总限流量 = 单实例限流量 × 实例数）。全局限流需要额外部署 Redis + rate limit service，更精准但更重。

### 8.4 重试与超时

和熔断配套的，还有重试和超时配置（VirtualService 里配）：

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts:
    - reviews
  http:
    - route:
        - destination:
            host: reviews
            subset: v1
      timeout: 3s                   # 总超时 3 秒
      retries:
        attempts: 2                 # 最多重试 2 次
        perTryTimeout: 1s           # 每次尝试超时 1 秒
        retryOn: connect-failure,refused-stream,503   # 什么情况重试
```

**重试配置的红线**：

| 注意事项 | 为什么 |
|:---|:---|
| 重试次数不要太多 (2-3 次最多) | 多了会放大故障 (重试风暴) |
| 只对幂等接口重试 | POST 重试可能导致重复下单 |
| perTryTimeout < timeout | 否则重试还没走完总超时就到了 |
| 配合熔断用 | 不然重试 + 慢下游 = 雪上加霜 |

### 8.5 踩坑清单

| 坑 | 现象 | 解决 |
|:---|:---|:---|
| `minHealthPercent` 没设 | 实例少的时候全踢了，服务完全不可用 | 设 20-50%，至少保留部分容量 |
| 熔断阈值太敏感 | 抖一下就熔断，误报多 | 调大 `consecutive5xxErrors` 或 `interval` |
| 本地限流不准 | 期望限流 1000 实际限了 5000 | 实例数 × 单实例限流 = 总流量，全局限流才准 |
| 重试风暴 | 下游一挂，上游疯狂重试，更挂 | 重试次数保守，加熔断 + 退避策略 |

## 十、场景八：多集群服务网格

### 10.1 场景说明

**需求**：多个 K8s 集群的服务能互相发现、互相调用，跨集群流量能调度。配合多集群管理（Karmada/Clusternet），构成「资源层 + 服务层」双层多集群。

```text
Istio 多集群两种模式:

  模式 1: Multi-Primary (多主, 每个集群都有控制面)
  ┌──────── 集群 A ────────┐   ┌──────── 集群 B ────────┐
  │  istiod (控制面)        │   │  istiod (控制面)        │
```

### 10.3 跨集群流量调度

同一个服务在两个集群都有部署，怎么控制跨集群调用？

```yaml
# 场景: 优先调本地集群, 本地挂了再调远端集群 (Locality Load Balancing)
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: httpbin
spec:
  host: httpbin.sample.svc.cluster.local
  trafficPolicy:
    outlierDetection:
      consecutive5xxErrors: 3
      interval: 30s
      baseEjectionTime: 1m
    connectionPool:
      http:
        h2UpgradePolicy: DEFAULT
  #  locality 权重: 本地集群 100, 远端 0
  #  本地挂了自动切到远端 (基于 outlierDetection)
```

### 10.4 踩坑清单

| 坑 | 现象 | 解决 |
|:---|:---|:---|
| 跨集群调用超时 | east-west 网关不通 | 检查防火墙 / LB / 安全组，放通 15443 端口 |
| mTLS 握手失败 | 两个集群根证书不一样 | 共享根证书（同一 CA 签发中间证书） |
| 服务发现不到 | 远端服务不可见 | ServiceEntry 同步了吗 / endpointslice 同步了吗 |
| 跨集群延迟高 | 调用链长 | locality 优先本地调用，跨集群只做灾备 |
| 控制面挂了全瘫痪 | Primary-Remote 模式控制面是单点 | 生产用 Multi-Primary |

## 十一、选型与落地建议

### 11.1 什么情况该上服务网格

| 你的情况 | 上不上 | 理由 |
|:---|:---|:---|
| 1-2 个服务 | ❌ 不要 | 杀鸡用牛刀，复杂度收益不成正比 |
| 10 个以内微服务 | ⚠️ 不一定 | 如果多语言 / 强治理需求可以上，否则 SDK 够了 |
| 30+ 微服务，多语言 | ✅ 上 | 统一治理的收益开始大于复杂度成本 |
| 有零信任 / 合规要求 | ✅ 上 | mTLS + 授权策略，网格是最省力的方案 |
| 对发布质量要求高（金融/电商） | ✅ 上 | 金丝雀 + 流量镜像 + 故障注入，发布质量直接提升 |
| 边缘 / 资源非常紧张 | ❌ 慎上 | sidecar 占资源，考虑 eBPF 网格或 Linkerd |

### 11.2 落地步骤建议

```text
服务网格落地 6 步法:

  第 1 步: 选技术栈
    先评估 Istio vs Linkerd vs Cilium, 选一个

  第 2 步: 测试环境试跑
    装网格 → 注入 1-2 个服务 → 跑通基本场景
    目标: 团队熟悉概念和工具链

  第 3 步: 可观测性先上 (低风险高收益)
    先不开流量治理, 只拿 metrics/tracing/accesslog
    目标: 让团队看到价值, 建立信任

  第 4 步: 灰度 + mTLS 试点
    找一个非核心业务, 用灰度发布 + PERMISSIVE mTLS
    目标: 验证核心能力, 踩坑积累经验

  第 5 步: 逐步推广
    一个命名空间一个命名空间地推, 每推完一个观察一周
    目标: 全量 80% 服务接入

  第 6 步: 高级能力
    STRICT mTLS / 授权策略 / 故障注入 / 多集群
    目标: 深度治理
```

### 11.3 资源开销参考

| 指标 | Istio (Envoy) | Linkerd2 | Cilium (eBPF) |
|:---|:---|:---|:---|
| 每个 sidecar 内存 | ~80-150MB | ~10-20MB | 0 (无 sidecar) |
| 每个 sidecar CPU | ~0.1-0.3 核 | ~0.05 核 | 极少 (eBPF 程序) |
| 延迟增加 | ~2-5ms | ~1-2ms | ~0.1-0.5ms |
| 控制面资源 | 1-2 核 / 2-4GB | 0.5 核 / 512MB | 已在 Cilium agent 里 |
| 集群 100 个 Pod 额外占用 | 约 10-15GB 内存 | 约 1-2GB 内存 | 几乎不增加 |

> 资源开销是服务网格最被诟病的点。1000 个 Pod 的集群，Istio 光 sidecar 就吃掉 ~100GB 内存，是真实存在的成本。要么接受，要么选更轻的方案（Linkerd / eBPF）。

## 十二、速查表

### 12.1 核心 CRD 速查

| CRD | 作用 | 常用场景 |
|:---|:---|:---|
| `VirtualService` | 路由规则 (怎么转) | 灰度/镜像/重写/故障注入 |
| `DestinationRule` | 目标规则 (怎么连) | 版本子集/熔断/负载均衡/mTLS |
| `Gateway` | 入口网关 | 对外暴露服务 / TLS 终止 |
| `PeerAuthentication` | 服务间认证 | mTLS 配置 |
| `AuthorizationPolicy` | 服务间授权 | 谁能访问谁 |
| `RequestAuthentication` | 请求认证 (JWT) | 校验用户 Token |
| `ServiceEntry` | 外部服务注册 | 网格内访问外部服务 |
| `Sidecar` | sidecar 配置 | 限制 sidecar 资源 / 减少配置下发 |
| `EnvoyFilter` | 自定义 Envoy 配置 | 扩展 Istio 不支持的功能 |

### 12.3 配置模板速查

```yaml
# 金丝雀 (90/10)
http:
  - route:
      - destination: {host: svc, subset: v1}
        weight: 90
      - destination: {host: svc, subset: v2}
        weight: 10

# 流量镜像
http:
  - route:
      - destination: {host: svc, subset: v1}
    mirror: {host: svc, subset: v2}
    mirrorPercentage: {value: 100.0}

# 延迟故障注入
http:
  - fault:
      delay: {percentage: {value: 10}, fixedDelay: 5s}
    route:
      - destination: {host: svc, subset: v1}

# 熔断 (DestinationRule)
trafficPolicy:
  outlierDetection:
    consecutive5xxErrors: 5
    interval: 30s
    baseEjectionTime: 30s
    maxEjectionPercent: 50

# 全局 mTLS STRICT
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata: {name: default, namespace: istio-system}
spec: {mtls: {mode: STRICT}}

# 授权策略 (allow)
spec:
  selector: {matchLabels: {app: svc}}
  action: ALLOW
  rules:
    - from: [{source: {principals: ["cluster.local/ns/x/sa/y"]}}]
      to: [{operation: {methods: ["GET"], paths: ["/api/*"]}}]
```

### 12.4 问题排查速查

| 现象 | 先查什么 | 再查什么 |
|:---|:---|:---|
| 503 Service Unavailable | Endpoints 对吗 | DestinationRule subset 对吗 |
| 路由不生效 | VirtualService 匹配顺序 | match 条件 / host 名 |
| mTLS 握手失败 | PeerAuthentication 模式 | 证书是不是同一 CA |
| 授权策略不生效 | selector 选中了吗 | principals / namespaces 写对了吗 |
| sidecar 资源太高 | Sidecar CRD 限制一下 | 减少不必要的配置下发 |
| 延迟明显增加 | 是 sidecar 本身慢 | 业务慢还是网络慢 |
| 配置不生效 | istiod 同步了吗 (proxy-status) | 看 envoy 配置 (proxy-config) |
