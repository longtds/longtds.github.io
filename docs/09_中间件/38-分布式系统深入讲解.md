# 分布式系统深入讲解

> 为什么分布式系统这么难？因为你以为只是把程序跑在多台机器上，实际上你面对的是一整套全新的物理定律：网络不可靠、时钟不同步、故障是常态。本文从基础理论到工程实践，覆盖一致性、共识算法、CAP、分布式事务、数据复制、故障模型、可观测性，一站讲透分布式系统的底层逻辑。

---

## 一、为什么分布式系统这么难？基础认知

### 1.1 分布式系统的本质

```text
什么是分布式系统？

  经典定义 (Leslie Lamport):
  "A distributed system is one in which the failure of a computer
   you didn't even know existed can render your own computer unusable."

  人话版:
  一堆通过网络连接的独立计算机，对外表现为一个整体。
  好处: 扩容 / 高可用 / 地理分布
  代价: 复杂性爆炸
```

**为什么需要分布式？**

| 动机 | 说明 |
|:---|:---|
| 性能/容量 | 单机 CPU/内存/磁盘顶不住了 |
| 高可用 | 单机会挂，多机可以冗余 |
| 地域分布 | 用户在世界各地，就近接入 |
| 自治 | 不同团队/组织独立系统需要协作 |
| 异构 | 不同技术栈/平台的系统要集成 |

### 1.2 分布式的八大谬误 (Fallacies)

Peter Deutsch 总结的分布式计算八大谬误——新手最容易想当然的 8 件事：

| # | 谬误 | 真相 |
|:---|:---|:---|
| 1 | 网络是可靠的 | 包会丢、连接会断、交换机故障、光纤被挖断 |
| 2 | 延迟为零 | 同城机房来回 ~0.5ms，跨地域几十到几百 ms |
| 3 | 带宽是无限的 | 带宽有上限，跨机房更贵 |
| 4 | 网络是安全的 | 内网也可能被入侵，中间人攻击真实存在 |
| 5 | 拓扑不会变 | 节点增删、网络变化是常态 |
| 6 | 只有一个管理员 | 分布式 = 多方协作，没有上帝视角 |
| 7 | 传输成本为零 | 序列化/反序列化有成本，跨机房流量要花钱 |
| 8 | 网络是同构的 | 不同链路质量、不同设备、不同协议 |

> 这 8 条每条都是血的教训。设计分布式系统时，每条都当反例来检验你的设计。

### 1.3 故障是常态，不是例外

```text
单机时代的假设:
  机器要么活着要么死了 → 二态

分布式时代的现实:
  ┌─ 活着但慢 (网络抖动/GC/磁盘满)
  ├─ 部分活着 (某些接口能用, 某些不行)
  ├─ 脑裂 (以为对方死了, 其实只是网络不通)
  ├─ 活着但说谎 (拜占庭故障)
  ├─ 死了 (进程挂了 / 机器宕机)
  └─ 复活 (以为死了又活过来了)

这就是为什么分布式算法这么难 —— 要处理的"故障模式"太多了。
```

**故障类型分类**：

| 故障模型 | 说明 | 难度 | 真实场景 |
|:---|:---|:---|:---|
| 崩溃故障 (Crash) | 节点直接挂了，不再响应 | ★ | 进程崩溃、机器断电 |
| 遗漏故障 (Omission) | 丢消息、不响应请求 | ★★ | 网络丢包、队列满了 |
| 计时故障 (Timing) | 响应超时、时钟漂移 | ★★★ | 网络延迟、NTP 漂移 |
| 拜占庭故障 (Byzantine) | 节点故意发假消息、撒谎 | ★★★★★ | 被入侵的节点、区块链 |

> 99% 的企业场景只需要处理崩溃故障 + 遗漏故障。拜占庭故障只在金融/区块链/安全敏感场景需要考虑。

### 1.4 时间与时钟

分布式系统里**没有全局一致的时间**，这是最反直觉但最核心的一个事实。

```text
单机: 只有一个时钟, 事件先后一目了然
分布式: 每台机器一个时钟, 各走各的
        你以为的同时发生, 其实不一定同时

  机器 A 的时钟: 12:00:00.000  事件 X 发生
  机器 B 的时钟: 12:00:00.001  事件 Y 发生
  问题: X 和 Y 谁先发生?
  答案: 不知道! 因为两个时钟不一样, 可能 A 的钟快了 10ms
```

**时钟类型**：

| 时钟类型 | 原理 | 用途 | 局限 |
|:---|:---|:---|:---|
| 物理时钟 (Time-of-Day Clock) | 系统时间，NTP 同步 | 人类可读的时间 | 不准（毫秒到秒级漂移），可回拨 |
| 单调时钟 (Monotonic Clock) | 开机后一直递增 | 测量时间间隔 | 只增不减，但各节点起点不同 |
| 逻辑时钟 (Logical Clock) | Lamport 算法，基于事件计数 | 确定事件先后顺序 | 只有偏序，不是真实时间 |
| 向量时钟 (Vector Clock) | 每个节点一个计数器的数组 | 检测并发和因果关系 | 空间随节点数增长 |

**Lamport 逻辑时钟**：

```text
规则:
  1. 每个事件发生时, 本地时钟 +1
  2. 收到消息时, 本地时钟 = max(本地时钟, 消息里的时钟) + 1

性质:
  如果 A 因果先于 B (A → B), 那么 clock(A) < clock(B)
  反过来不成立: clock(A) < clock(B) 不能推出 A 因果先于 B
  (可能只是巧合数字小)
```

**向量时钟**：

```text
每个节点维护一个向量 [C1, C2, ..., Cn]
  Ci = 自己看到的节点 i 的时钟

规则:
  1. 本地事件: 自己的位置 +1
  2. 发消息: 自己位置 +1, 把整个向量发出去
  3. 收消息: 每个位置取 max, 自己位置再 +1

性质:
  VC(A) < VC(B) 当且仅当 A 因果先于 B
  都不小且有大有小 → 并发事件

用处: 检测冲突 (DynamoDB / Riak 的向量时钟版本)
```

> **工程实践**：99% 的场景你不需要向量时钟，甚至不需要逻辑时钟。记住一句话——**不要相信物理时钟，用递增 ID / 版本号 / 全局序号来定序**。

## 二、CAP 定理与一致性模型

### 2.1 CAP 定理

```text
CAP 定理 (Eric Brewer, 2000):

  分布式系统不可能同时满足以下三个属性, 最多同时满足两个:

  ┌── C: Consistency (一致性)
  │     所有节点同时看到相同的数据
  │
  ├── A: Availability (可用性)
  │     每个请求都能收到响应 (不一定是最新数据)
  │
  └── P: Partition Tolerance (分区容忍性)
        网络分区 (节点间不通) 时系统仍能工作
```

**CAP 的三个组合**：

| 组合 | 放弃 | 特点 | 代表 |
|:---|:---|:---|:---|
| **CP** | A (可用性) | 强一致，分区时部分节点不可用 | ZooKeeper / etcd / HBase |
| **AP** | C (一致性) | 高可用，分区时各自服务，数据可能不一致 | Cassandra / DynamoDB / Riak |
| CA | P (分区容忍) | 没有网络分区时既一致又可用 | 单机数据库 / 传统分布式事务 |

> **注意**：P（网络分区）不是选不选的问题——**网络分区一定会发生**，你只能在 C 和 A 之间做取舍。CA 系统只存在于"网络永远可靠"的理想世界。

### 2.2 CAP 的常见误解

| 误解 | 正解 |
|:---|:---|
| "三选二，选两个就行" | P 是必选项，只能在 C 和 A 之间选 |
| "系统要么 CP 要么 AP" | 可以配置、可以调整、可以动态切换（比如正常情况 CA，分区时选 AP 或 CP） |
| "CAP 是 0 和 1 的关系" | 其实是连续的：一致性可以有不同级别，可用性也可以有百分比 |
| "CAP 覆盖了所有设计维度" | CAP 只讲了一致性、可用性、分区。延迟、吞吐量、持久性都不在 CAP 里 |

### 2.3 PACELC 定理

CAP 的扩展版本——正常情况下怎么选，分区时怎么选。

```text
PACELC:
  如果发生 Partition (P) → 在 Availability (A) 和 Consistency (C) 之间选
  Else (E) → 在 Latency (L) 和 Consistency (C) 之间选

  系统类型     P 时选   正常时选   代表
  PA/EL       A        L         Cassandra / DynamoDB (高可用 + 低延迟)
  PC/EC       C        C         ZooKeeper / 强一致数据库
  PA/EC       A        C         有些数据库正常强一致, 分区时降级
```

### 2.4 一致性模型一览

一致性不是"有或没有"，而是一个光谱：

```text
强一致 (Strong Consistency)
  │
  ├─ 线性一致性 (Linearizability)
  │     一旦写成功, 所有后续读都读到新值 (就像单机一样)
  │
  ├─ 顺序一致性 (Sequential Consistency)
  │     所有进程看到的操作顺序一致, 但不一定和真实时间一致
  │
  ├─ 因果一致性 (Causal Consistency)
  │     有因果关系的操作顺序一致, 并发操作可以各看各的
  │
  ├─ 读己之写 (Read-your-writes)
  │     自己写的自己总能读到, 别人不一定
  │
  ├─ 会话一致性 (Session Consistency)
  │     同一个会话内读己之写, 会话间不保证
  │
  ├─ 单调读 (Monotonic Reads)
  │     读过新值后不会再读到旧值
  │
  └─ 最终一致性 (Eventual Consistency)
        只要没有新写入, 最终所有副本都会一致
        但不知道要多久 (秒/分钟/小时)
```

| 一致性模型 | 性能 | 易用性 | 典型应用 |
|:---|:---|:---|:---|
| 线性一致性 | 慢 | 最容易写代码 | 分布式锁 / 配置 / 元数据 |
| 因果一致性 | 中 | 中等 | 社交动态 / 评论 |
| 最终一致性 | 快 | 需要处理冲突 | DNS / 缓存 / 计数 |

> **工程经验**：能用最终一致的就别用强一致。强一致的代价是性能、可用性、延迟，每项都很贵。先想清楚业务是不是真的需要强一致——大部分场景其实不需要。

### 2.5 BASE 理论

BASE 是对 CAP 中 AP 系统的总结，和 ACID 对应。

| | ACID (关系数据库) | BASE (分布式系统) |
|:---|:---|:---|
| A | Atomicity 原子性 | **Basically Available** 基本可用 |
| C | Consistency 一致性 | **Soft State** 软状态 |
| I | Isolation 隔离性 | **Eventually Consistent** 最终一致 |
| D | Durability 持久性 | |

BASE 的核心思想：接受数据在中间状态（软状态），接受短暂的不一致，换取高可用和高性能。

## 三、数据复制

### 3.1 为什么要复制

```text
复制 (Replication) = 同一份数据存多个副本

目的:
  1. 高可用: 一个副本挂了还有别的
  2. 低延迟: 就近访问 (用户离哪个近读哪个)
  3. 读扩展: 读请求分摊到多个副本

代价:
  1. 多副本之间怎么同步? → 一致性问题
  2. 写冲突怎么办? → 冲突解决
  3. 副本越多, 越难管理
```

### 3.2 主从复制 (Primary-Replica / Master-Slave)

```text
写请求 → 主节点 (Leader / Primary)
            │
            ├───── 同步复制 ─────► 副本 1 (写成功等所有副本确认)
            ├───── 异步复制 ─────► 副本 2 (写成功不等副本)
            └───── 半同步 ───────► 副本 3 (等至少 N 个副本确认)

读请求: 可以从主节点读, 也可以从副本读
```

| 复制方式 | 一致性 | 性能 | 可用性 | 适用场景 |
|:---|:---|:---|:---|:---|
| 同步复制 | 强一致 | 慢（等所有副本） | 低（一个副本挂了写就停） | 金融/核心数据 |
| 异步复制 | 最终一致 | 快（写主就返回） | 高 | 大多数场景 |
| 半同步 | 介于两者之间 | 中 | 中 | MySQL 半同步 / 云数据库 |

**主从复制的问题**：

| 问题 | 说明 |
|:---|:---|
| 主节点单点故障 | 主挂了整个写挂了，需要选主 |
| 主从延迟 | 异步复制时，读副本可能读到旧数据 |
| 写瓶颈 | 所有写都走主节点，主节点是单点瓶颈 |
| 脑裂 | 主没死但副本以为主死了，选了新主，两个都接写 |

### 3.3 多主复制 (Multi-Master / Multi-Leader)

```text
每个节点都能接受写请求，节点之间异步同步。

  数据中心 A (主) ──── 双向同步 ──── 数据中心 B (主)
       │                              │
       ▼                              ▼
     写请求                        写请求
```

**优点**：
- 每个数据中心本地写，延迟低
- 任何一个数据中心挂了，其他的还能写

**最大的问题：写冲突**

```text
用户 1 改了数据中心 A 的记录 (用户信息: 地址 = 北京)
用户 2 改了数据中心 B 的同一条记录 (用户信息: 地址 = 上海)

过了一会儿, 两边同步...
  冲突了! 以谁为准?

冲突解决策略:
  1. Last Write Wins (LWW): 时间戳大的赢  (最简单, 但可能丢数据)
  2. 版本号 / 向量时钟: 检测冲突, 让应用自己解决
  3. 合并: 比如购物车, 两边的商品合并
  4.  CRDT: 数据结构本身支持合并, 不会冲突
```

### 3.4 无主复制 (Leaderless / Dynamo-style)

```text
没有主节点, 任何节点都能接受写。
读和写都需要至少 W 个节点确认写 / R 个节点响应读。

  客户端
    │
    ├─► 节点 A (写成功)
    ├─► 节点 B (写成功)
    ├─► 节点 C (写成功)
    └─► 节点 D (慢/挂了, 后面会补)

W + R > N  → 可以保证读到最新值 (Quorum)
  N = 副本数 (通常 3)
  W = 写确认数 (W=2)
  R = 读响应数 (R=2)
  2 + 2 > 3 → 有交集, 一定有一个节点是新数据
```

**可调一致性**：
- W + R > N：强一致（可以读到最新值）
- W + R ≤ N：最终一致（可能读到旧值，但读更快）

**常用配置**：

| 配置 | W | R | 特点 |
|:---|:---|:---|:---|
| 高可用读 | 1 | N | 写快，读慢，读一致性高 |
| 高可用写 | N | 1 | 读快，写慢，写可靠性高 |
| 均衡 | 2 | 2 | N=3 时读写都要 2 个节点确认 |

**数据修复 (Repair)**：

```text
读到旧数据了怎么办?

  1. Read Repair (读修复):
     读的时候发现某个节点数据旧了, 顺手帮它更新

  2. Anti-Entropy (反熵):
     后台定期对比各节点数据, 把旧的更新成新的
     (Merkle Tree 可以高效比较大量数据)
```

### 3.5 一致性哈希

分布式存储里怎么决定数据存在哪个节点？

```text
普通哈希: hash(key) % N
  问题: 加/减节点时, 几乎所有数据都要重新分配 (N 变了)

一致性哈希 (Consistent Hashing):
  把节点和 key 都映射到一个 0~2^32-1 的哈希环上
  key 顺时针找第一个节点, 就是它的归属节点

    节点 A ────── 节点 B
      ╲              ╱
       ╲            ╱
        哈希环 (0~2^32)
       ╱            ╲
      ╱              ╲
    节点 D ────── 节点 C

加一个节点: 只影响它顺时针相邻的那个节点的数据 (1/N 的数据)
减一个节点: 它的数据全部给顺时针下一个节点

虚拟节点:
  每个物理节点对应 N 个虚拟节点 (vnode), 均匀分布在环上
  好处: 负载更均匀, 节点数量少时也不会倾斜
```

## 四、共识算法

### 4.1 什么是共识

```text
共识 (Consensus) = 多个节点就一个值达成一致

核心挑战:
  - 节点可能挂掉 (崩溃故障)
  - 消息可能丢失 / 延迟 / 乱序
  - 没有全局时钟

FLP 不可能定理 (Fischer-Lynch-Paterson):
  在异步网络模型 + 一个节点可能崩溃的情况下,
  不存在能保证在有限时间内达成共识的算法。

  人话: 纯异步下, 你永远不知道一个节点是死了还是慢。
  但实际系统中, 我们可以用超时来做同步假设, 绕开这个定理。
```

### 4.2 Paxos

Leslie Lamport 1990 年提出，最强一致性共识算法，也是最难懂的。

```text
Paxos 角色:
  Proposer (提议者): 提出一个值
  Acceptor (接受者): 投票决定接受哪个值
  Learner (学习者): 学习最终达成一致的值

两阶段提交 (不是 2PC, 是 Paxos 的两阶段):

  阶段 1: Prepare (准备)
    Proposer  发起 Prepare(n) → 多数 Acceptor
                            ← Promise(接受 n, 不接受 <n 的提议)

  阶段 2: Accept (接受)
    Proposer  发起 Accept(n, value) → 多数 Acceptor
                              ← Accepted
    多数 Acceptor 接受 → value 被选定 (Chosen)

关键性质:
  1. 安全性: 只有一个值能被选定
  2. 活性: 只要多数节点活着, 最终一定能选定一个值
  3. 多数派: 任何两个多数派集合必有交集 (保证一致性)
```

**Paxos 太复杂了**——原始论文难懂，工程实现更难。所以有了更工程化的 Raft。

### 4.3 Raft

Raft (2013) = Paxos 的易理解版本。通过**分离问题**让算法更容易懂。

```text
Raft 把共识拆成三个子问题:
  1. Leader 选举 (Leader Election)
  2. 日志复制 (Log Replication)
  3. 安全性 (Safety)

节点角色:
  Leader (领导者): 处理所有客户端请求, 管理复制
  Follower (跟随者): 被动接收日志, 不主动发起
  Candidate (候选人): 选举时的中间状态
```

**Raft 任期 (Term)**：

```text
每个 Leader 有一个任期号 (term), 单调递增。
  term 0 → term 1 → term 2 → term 3 → ...
  每个 term 最多一个 Leader (也可能选不出来)

  时间 →
  ── term 1 ──┼── term 2 ──┼── term 3 ──┼── ...
    Leader A    Leader B    Leader C
```

**Leader 选举**：

```text
选举触发条件:
  Follower 在 election timeout 内没收到 Leader 的心跳
  → 自己变成 Candidate, term + 1, 发起选举

选举过程:
  1. Candidate 给自己投一票
  2. 给其他节点发 RequestVote RPC
  3. 收到多数票 → 变成 Leader
  4. 没收到多数票 → 等下一轮 (随机超时后重新选)

选举的随机化:
  每个节点的 election timeout 是随机的 (比如 150~300ms)
  → 通常只有一个节点先超时 → 顺利当选
  → 避免多 Candidate 同时抢票导致谁都选不上
```

**日志复制**：

```text
写请求流程:
  客户端 → Leader → Leader 写本地日志 → 复制给 Follower
                                           ↓
                                  多数 Follower 写入日志
                                           ↓
                                  Leader 提交 (commit)
                                           ↓
                                  通知 Follower 提交
                                           ↓
                                  返回客户端成功

  日志是有序的 (Log Index), 每条日志带 term 号
  一致性保证: 相同 index + 相同 term → 相同的命令 → 前面的日志也都相同
```

**安全性**：

Raft 如何保证不会选一个日志不全的节点当 Leader？

```text
选举时:
  Candidate 要把自己最后一条日志的 index 和 term 发给 Follower
  Follower 发现 Candidate 的日志没自己新 → 不投它
  → 只有日志最全的节点才可能当选 (得到多数票)

这样就保证: 新 Leader 的日志一定是最新的, 不会丢已提交的数据。
```

**Raft 工程实现**：

| 实现 | 语言 | 用户 |
|:---|:---|:---|
| etcd | Go | K8s 标配 |
| Consul | Go | 服务发现 |
| TiKV | Rust | 分布式 KV |
| LogCabin | C++ | Raft 参考实现 |

> **Paxos vs Raft**：理论上等价，安全性和活性都一样。Raft 的优点是工程实现更容易、可读性更强。**新项目一律用 Raft 实现的系统，别自己写 Paxos**。

### 4.4 Gossip 协议

另一种思路：**没有 Leader，节点之间互相八卦**。

```text
Gossip (Epidemic) 协议:
  每个节点定期随机选几个邻居, 把自己知道的信息告诉对方
  像病毒传播一样, 信息最终会扩散到全网

  节点 A ── 知道 {X:v1}
    │ 随机告诉 B
    ▼
  节点 B ── 学到 {X:v1}
    │ 随机告诉 C 和 D
    ▼
  节点 C, D ── 学到 {X:v1}
    ...  一传十, 十传百

特点:
  - 去中心化, 无单点
  - 最终一致 (不是立刻全知道)
  - 容错性极强 (挂几个节点完全不影响)
  - 网络带宽有冗余 (重复传播)
  - 收敛速度快 (指数级传播)
```

**典型应用**：
- Cassandra / DynamoDB 的成员管理和状态同步
- Consul 的 Serf (基于 Gossip 的成员管理)
- 集群成员发现、故障检测

### 4.5 共识算法选型

| 算法 | 一致性 | 性能 | 复杂度 | 适用场景 |
|:---|:---|:---|:---|:---|
| **Raft** | 强一致 | 中 | 低 | 大多数场景 (etcd/Consul) |
| Paxos | 强一致 | 中 | 高 | 历史遗留 (Google Chubby) |
| **Gossip** | 最终一致 | 高 | 低 | 成员发现、状态同步 |
| 向量时钟 | 因果一致 | 高 | 中 | 冲突检测 |
| CRDT | 强最终一致 | 高 | 中 | 协作编辑、计数器 |

## 五、分布式事务

### 5.1 为什么难

```text
本地事务: ACID 一套搞定
分布式事务: 多个节点、多个数据库 → 没有全局时钟、没有全局锁、网络可能断

  节点 A (扣钱)      节点 B (加钱)
    BEGIN             BEGIN
    UPDATE 余额-100   UPDATE 余额+100
    COMMIT?           COMMIT?
    两边要么都成功, 要么都失败
  问题: A 成功了 B 挂了怎么办? 怎么回滚 A?
```

### 5.2 2PC (两阶段提交)

```text
2PC (Two-Phase Commit):
  协调者 (Coordinator) 管着所有参与者 (Participants)

  阶段 1: Prepare (准备)
    协调者 → 所有参与者: 准备好提交吗?
    参与者 → 协调者: Yes / No
    (Yes = 我已经把事务日志写盘了, 随时可以提交)

  阶段 2: Commit / Rollback
    所有都答 Yes → 协调者发 Commit, 所有参与者提交
    任何一个答 No  → 协调者发 Rollback, 所有参与者回滚
```

**问题**：

| 问题 | 说明 |
|:---|:---|
| 同步阻塞 | 参与者在 Prepare 之后要锁资源，等协调者决定 |
| 单点故障 | 协调者挂了 → 所有人都卡死（不知道该提交还是回滚） |
| 数据不一致 | Commit 阶段协调者发了一部分挂了 → 部分提交部分没提交 |
| 性能差 | 两次网络往返，所有节点都要等最慢的那个 |

> 2PC 是强一致的，但可用性差。**实际生产中用得不多**（XA 事务就是 2PC 的实现），更多用在数据库内部的分布式事务里。

### 5.3 3PC (三阶段提交)

2PC 的改进版，加了一个 PreCommit 阶段，试图解决协调者挂了的阻塞问题。

```text
三阶段:
  CanCommit → PreCommit → DoCommit

  CanCommit: 问参与者"你能提交吗?" (不锁资源)
  PreCommit: 都 Yes 就进入准备阶段 (写日志, 锁资源)
  DoCommit: 正式提交

改进:
  - 参与者有超时机制, 协调者挂了不会无限等
  - 减少阻塞时间

问题:
  - 网络分区时还是可能不一致
  - 更复杂了, 多了一轮 RPC
  - 实际用得更少
```

### 5.4 TCC

TCC = Try-Confirm-Cancel，业务层面的两阶段提交。

```text
每个服务提供三个接口:

  Try:    资源预留 / 冻结 (不真正扣, 只是占住)
  Confirm: 确认提交 (把预留的真正扣掉)
  Cancel:  取消 (把预留的释放掉)

流程:
  1. 协调者调用所有服务的 Try
  2. 都成功 → 调用所有 Confirm
     任何失败 → 调用所有 Cancel
```

| 优点 | 缺点 |
|:---|:---|
| 性能比 2PC 好（锁粒度更细） | 每个服务要写三个接口，侵入性强 |
| 业务可控，可以做业务级幂等 | 开发成本高 |
| 适用性广（跨数据库、跨服务） | 要处理空回滚、悬挂等异常 |

**TCC 的三大坑**：

| 坑 | 说明 | 解法 |
|:---|:---|:---|
| 空回滚 | Try 没收到，先收到 Cancel | Cancel 先查有没有 Try 记录，没有直接返回成功 |
| 幂等 | 网络重试导致重复调用 Confirm/Cancel | 每个操作有唯一 ID，去重 |
| 悬挂 | Cancel 先到，Try 后到 (网络乱序) | Try 执行前检查是否已 Cancel，已 Cancel 就不再 Try |

### 5.5 Saga

长事务的解决方案，把一个大事务拆成多个本地事务，失败了反向补偿。

```text
正常流程 (正向):
  服务 A: 创建订单 → 服务 B: 扣库存 → 服务 C: 扣余额 → 服务 D: 发通知

补偿流程 (反向):
  任何一步失败 → 从失败点往回走, 每一步调用补偿操作
  服务 C 失败 → B: 加库存 → A: 取消订单
```

两种实现方式：

| 方式 | 原理 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **编排式 (Choreography)** | 每个服务监听事件，自己决定下一步 | 简单，松耦合 | 流程散落在各服务，难追踪 |
| **协同式 (Orchestration)** | 有一个协调者统一指挥 | 流程清晰，好监控 | 协调者单点 |

**Saga 的本质是"补偿"不是"回滚"**——数据已经提交了，补偿是用另一个操作把它改回来。所以 Saga 只能保证最终一致性，不是强一致。

### 5.6 本地消息表 + 最终一致

最常用、最可靠、实现最简单的方案。

```text
原理: 业务操作 + 消息写在同一个本地事务里 → 保证要么都成要么都败

  1. 开始本地事务
  2. 执行业务 SQL (比如扣库存)
  3. 往 outbox 消息表插一条待发送消息
  4. 提交事务

  5. 后台任务轮询 outbox 表, 把消息发到 MQ
  6. 发送成功标记已发送
  7. 消费方消费消息, 执行业务 (保证幂等)

关键点:
  - 消息一定能发出去 (本地事务保证)
  - 消费方必须幂等 (消息至少投递一次, 可能重复)
  - 一致性: 最终一致 (不是立刻, 但最终会一致)
```

### 5.7 选型决策

```text
分布式事务选型:

  一致性要求有多高?
  │
  ├─ 必须强一致 (钱/库存)
  │   └─ 服务数 ≤ 3 且性能要求不高 → 2PC / XA
  │   └─ 性能要求高 / 服务多 → TCC
  │
  ├─ 最终一致就行
  │   ├─ 流程长步骤多 → Saga
  │   └─ 简单的服务间通知 → 本地消息表 + MQ
  │
  └─ 可以丢 (日志/埋点)
      └─ 直接发 MQ, 失败就丢
```

> **真心话**：90% 的业务场景用"本地消息表 + 幂等消费 + 定时对账"就能搞定。不要上来就 TCC/Saga 全家桶，复杂和成本是线性增长的。

## 六、分布式锁

### 6.1 为什么需要分布式锁

单机时代：线程锁（synchronized / Lock）就够了
分布式时代：多进程多机器，需要跨机器的锁

```text
场景:
  10 台机器上的服务同时处理一个订单
  只能有一个机器成功处理 → 需要分布式锁保证互斥
```

### 6.2 基于 Redis 的分布式锁

最常见的实现方式。

**基本版本**：

```bash
# 加锁: SET key value NX EX timeout
SET lock:order:123 "client-A" NX EX 30
# NX = Not Exists (不存在才设置成功, 就是加锁)
# EX = 过期时间 (防止死锁)

# 释放锁: 不能直接 DEL (可能释放了别人的锁)
# 必须用 Lua 脚本保证"判断是自己的锁 + 删除"原子
EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 lock:order:123 "client-A"
```

**三个关键要素**：

| 要素 | 为什么重要 | 实现 |
|:---|:---|:---|
| 互斥性 | 同时只有一个持有者 | `SET NX` |
| 超时释放 | 持有者挂了也不会死锁 | `EX 30` |
| 只能释放自己的锁 | 不能释放别人的锁 | value 存唯一 ID + Lua 脚本释放 |

**Redlock (Redis 集群锁)**：

```text
单 Redis 节点的问题:
  Redis 主节点挂了, 从节点升主, 但锁数据还没同步过去 → 两个人都拿到锁

Redlock (红锁) 算法:
  有 N 个独立的 Redis 节点 (N 通常是 5)
  加锁: 依次向 N 个节点请求加锁
    - 超过半数 (N/2+1) 成功, 且总耗时 < 锁超时 → 加锁成功
    - 失败 → 释放所有已加的锁, 重试
  释放锁: 向所有节点发删除

争议: Redlock 的安全性有争议 (Martin Kleppmann vs antirez)
     时钟漂移、GC 停顿都可能导致问题
```

### 6.3 基于 etcd / ZooKeeper 的锁

利用临时节点（ephemeral node）+ watch 机制。

```text
ZooKeeper 锁原理:
  1. 加锁: 在 /locks/mylock 下创建临时顺序节点
  2. 判断自己是不是序号最小的节点
     - 是 → 拿到锁
     - 不是 → watch 前一个节点, 等它删了再抢
  3. 释放锁: 删自己的节点 (会话断开自动删)

优点:
  - 不会有死锁 (临时节点, 会话断了自动删)
  - 公平锁 (先来先得, 按顺序)
  - 强一致 (ZooKeeper 是 CP 的)

缺点:
  - 性能不如 Redis
  - 羊群效应 (一个节点删了唤醒所有等待者)
    → 顺序节点 + watch 前一个可以解决
```

### 6.4 分布式锁的坑

| 坑 | 说明 | 解法 |
|:---|:---|:---|
| 锁超时了任务还没做完 | GC 停顿 / 网络慢导致超过超时时间 | 续期（看门狗 / watchdog） |
| 释放了别人的锁 | 自己的锁过期了，以为还在自己手里 | 每个锁有唯一 value，删的时候校验 |
| 重入问题 | 同一个线程再获取同一把锁会卡死 | 加计数，可重入 |
| 羊群效应 | 一把锁几百个竞争者，释放时全唤醒 | 顺序节点，只 watch 前一个 |
| 时钟漂移 | 机器时钟不准导致锁过期判断错 | 不用依赖绝对时间的方案（ZK 临时节点） |

### 6.5 选型

| 方案 | 性能 | 一致性 | 复杂度 | 推荐场景 |
|:---|:---|:---|:---|:---|
| Redis 锁 | 高 | 最终一致 | 低 | 大多数场景、性能要求高 |
| etcd/ZK 锁 | 中 | 强一致 | 中 | 对可靠性要求极高 |
| 数据库锁 | 低 | 强一致 | 最低 | 并发不高、已有数据库 |
| Redlock | 高 | 理论上强一致 | 高 | 有争议，谨慎使用 |

> **经验法则**：能用"乐观锁 + 版本号"就别用分布式锁。分布式锁成本高、坑多，能不用就不用。

## 七、限流与削峰

### 7.1 为什么要限流

```text
分布式系统的容量是有限的。
  流量来了 → 超过系统承载能力 → 排队 → 超时 → 雪崩

限流就是: 在入口处拦住超出容量的请求, 保护系统不被冲垮。
          (牺牲一部分请求, 保住整体可用)
```

### 7.2 常见限流算法

| 算法 | 原理 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **计数器** | 固定窗口内计数，超了就拒 | 最简单 | 窗口边界 2 倍流量突刺 |
| **滑动窗口** | 时间片滑动，平滑计数 | 准确、无边界突刺 | 稍复杂 |
| **令牌桶** | 桶里有令牌，请求拿令牌，没令牌就等/拒 | 允许突发流量 | 实现稍复杂 |
| **漏桶** | 请求进桶，匀速漏出 | 输出绝对平滑 | 应对突发能力差 |

**令牌桶图示**：

```text
  令牌以固定速率生成 → 放进桶里 (桶有最大容量)

         令牌令牌令牌
        ┌───────────┐
        │ ● ● ● ● ●  │ ← 令牌桶 (容量 N)
        └────┬──────┘
             │
             ▼  请求来 → 拿一个令牌 → 有就通过, 没有就拒绝
          请求请求请求
```

### 7.3 分布式限流

单机限流简单，分布式限流难——要知道全局的 QPS。

**方案一：集中式计数器（Redis + Lua）**

```text
所有请求都去 Redis 查/增计数器。
  KEY[1] = 限流 key (比如 "rate:order-service")
  ARGV[1] = 限流阈值 (1000)
  ARGV[2] = 窗口大小 (秒)

Lua 脚本保证原子性:
  - 计数器 +1
  - 如果是窗口第一次, 设置过期时间
  - 超过阈值返回 0 (限流), 否则返回 1 (通过)
```

**方案二：令牌桶（Redis + Lua）**

```text
Redis 存:
  - 当前令牌数
  - 上次补充令牌的时间

每次请求:
  1. 根据时间差计算应该补充多少令牌
  2. 更新令牌数 (不超过桶容量)
  3. 有令牌就扣一个, 通过
  4. 没令牌就拒绝
```

**方案三：网关层限流 + 本地限流结合**

```text
最佳实践: 两层限流
  - 网关层 (Nginx/APISIX): 全局限流, 总 QPS 不超
  - 服务层 (本地令牌桶): 每个实例限流, 保护自己

这样即使网关挂了, 每个服务自己也有一层保护。
```

### 7.4 服务雪崩与保护机制

```text
雪崩效应:
  服务 A 调用 B, B 调用 C
  C 挂了 → B 所有请求都超时 → B 的线程池被占满 → B 也挂了
  → A 调 B 也全超时 → A 也挂了
  从底往上逐层崩溃 → 整个系统雪崩

三道防线:
  1. 限流: 不让太多请求进来 (入口防护)
  2. 熔断: 下游挂了就不调了 (中间防护)
  3. 降级: 非核心功能关掉 (业务防护)
```

**熔断（Circuit Breaker）状态机**：

```text
    失败率超阈值
  ┌───────────────────┐
  │                   ▼
┌─────┐  半开探测成功 ┌──────┐  探测失败 ┌──────┐
│Closed│ ──────────▶ │HalfOpen│ ─────────▶ │ Open │
└─────┘              └──────┘            └──────┘
  ▲                   │
  └───────────────────┘
      熔断时间过后

Closed  (闭合): 正常调用, 统计失败率
HalfOpen (半开): 放少量请求试试, 成功了就恢复, 失败了继续熔断
Open    (打开): 所有请求直接失败, 不调用下游
```

## 八、故障检测与容错

### 8.1 心跳检测

怎么知道一个节点挂了？

```text
最常用: 心跳 (Heartbeat)
  节点定期 (比如 1s) 发心跳给中心 / 所有节点
  一定时间没收到心跳 → 认为节点挂了

  节点 A ──心跳──▶ 节点 B
  节点 A ──心跳──▶ 节点 C
  ...

问题:
  - 网络分区: 不是节点挂了, 是网络断了
  - 误判率和及时性的权衡:
      心跳间隔短 + 超时短 → 检测快, 但误判多
      心跳间隔长 + 超时长 → 误判少, 但发现慢
```

**Gossip 式故障检测（SWIM）**：

```text
Scalable Weakly-consistent Infection-style Process Group Membership
  1. 每个节点随机选几个节点 ping
  2. 没回应 → 再让其他几个节点帮忙 ping
  3. 还没回应 → 标记为可疑
  4. 再等一段时间确认 → 标记为死亡
  5. 通过 gossip 扩散这个消息

好处:
  - 可扩展 (节点越多不越慢)
  - 误判率低 (多次确认)
  - 去中心化
```

### 8.2 脑裂 (Split-Brain)

分布式最棘手的问题之一。

```text
什么是脑裂?
  网络分区 → 一个集群变成两个独立的子集群
  两边都认为对方挂了, 两边都当主
  → 两边都接受写请求 → 数据冲突 / 数据丢失

  ┌─────── 数据中心 A ───────┐    ┌─────── 数据中心 B ───────┐
  │  我是主! 我来处理写请求  │    │  我是主! 我来处理写请求  │
  └─────────────────────────┘    └─────────────────────────┘
             \                              /
              \———— 网络分区 ————————————/
```

**怎么防止脑裂？**

| 方法 | 原理 | 例子 |
|:---|:---|:---|
| 多数派 (Quorum) | 必须得到超过半数节点的同意才能当主 | Raft / Paxos |
| 隔离机制 (Fencing) | 旧主被隔离后, 即使活过来也不能写 | ZooKeeper 临时节点 / Redis Redlock |
| 租约 (Lease) | 主节点有一个租约期，过期了就下台 | GFS Chubby |

> **核心思想**：用"数量"而不是"我觉得对方挂了"来决定谁是主。多数派的存在保证了不可能有两个主（两个多数派交集非空，不可能同时存在）。

### 8.3 重试与退避

调用失败了怎么办？重试。但重试也有讲究。

**重试的正确姿势**：

```text
❌ 错误做法:
  失败立刻重试 → 下游本来就慢, 再加上重复请求 → 更挂了 (重试风暴)

✅ 正确做法:
  1. 指数退避 (Exponential Backoff):
     第 1 次失败 → 等 100ms → 重试
     第 2 次失败 → 等 200ms → 重试
     第 3 次失败 → 等 400ms → 重试
     时间越等越长, 给下游恢复的时间

  2. 加抖动 (Jitter):
     不要所有客户端都在同一时刻重试 (惊群效应)
     退避时间上加个随机值: delay = base * 2^n + random()

  3. 最大重试次数:
     不能无限重试, 最多 2-3 次够了

  4. 只重试幂等操作:
     GET / DELETE / PUT 可以重试
     POST 不能随便重试 (可能重复下单)
```

### 8.4 容错模式总结

| 模式 | 作用 | 适用场景 |
|:---|:---|:---|
| 超时 | 别让请求无限等 | 所有跨服务调用 |
| 重试 | 临时故障自动恢复 | 幂等操作 + 偶发故障 |
| 熔断 | 下游挂了就别再调了 | 强依赖的下游服务 |
| 限流 | 入口处拦流量 | 高并发场景 |
| 降级 | 保核心舍边缘 | 大促 / 故障期间 |
| 舱壁隔离 | 不同资源池互不影响 | 多下游调用 |
| 故障转移 | 主挂了切备 | 数据库 / 消息队列 |
| 回滚 / 灰度 | 发布出问题立刻回 | 发布系统 |

## 九、可观测性

### 9.1 分布式系统的可观测性挑战

```text
单机: 看日志就能定位问题
分布式: 一个请求串了 8 个服务, 不知道在哪慢的/挂的
        日志散在各个机器上, 怎么串起来?
```

**三大支柱**：

| 支柱 | 回答什么问题 | 数据形式 | 代表工具 |
|:---|:---|:---|:---|
| Metrics (指标) | "系统好不好" | 数字 / 时间序列 | Prometheus |
| Logging (日志) | "发生了什么" | 文本 / 结构化 | ELK / Loki |
| Tracing (链路) | "请求去了哪" | 调用链 / Span | Jaeger / SkyWalking |

### 9.2 OpenTelemetry 标准

```text
OpenTelemetry (OTel) = 统一的可观测性标准
  一套 API + SDK + 规范, 所有语言都一样
  自动埋点 (很多框架自带)
  数据格式统一, 后端随便换 (Jaeger/Tempo/Zipkin...)

概念:
  Trace: 一次完整请求的全链路
  Span:  链路上一个节点 (一次调用)
  Context: 传递的上下文 (trace_id, span_id, baggage)
```

### 9.3 分布式追踪的采样

```text
全量采样成本太高 (每条 trace 都存, 存储爆炸)

采样策略:
  1. 概率采样 (Probabilistic): 每条请求 N% 概率采样
     生产常用 1%~10%
  2. 错误全采: 错误的请求 100% 采样
  3. 尾部采样 (Tail-based): 整条链路走完再决定采不采
     慢的 / 错的 / 有价值的才采
     (但需要先缓存整条链, 成本高)
  4. 按业务采样: 重要业务 100%, 非核心 1%
```

### 9.4 告警设计

```text
告警的目标: 让人在正确的时间关注正确的问题。

错误的告警:
  - 太多, 看不过来 → 狼来了效应
  - 太频繁, 半夜响 → 大家都关了
  - 没 actionable, 收到不知道干啥

正确的告警:
  - 每条告警都能行动
  - 分级 (P0/P1/P2/P3)
  - 同类聚合
  - 定期复盘, 清理无效告警
```

## 十、经典系统设计参考

### 10.1 设计短链接系统

```text
需求: 长 URL → 短 URL, 点击短 URL 跳转

方案:
  1. 发号器生成自增 ID → 转 62 进制 → 短码
  2. 存映射关系 (Redis 缓存 + DB 持久化)
  3. 访问短码 → 查缓存 → 302 跳转
  4. 数据分片: 按短码哈希分片到不同 DB

挑战:
  - 发号器: 用号段模式 (一次拿 1000 个号, 用完再取)
  - 热点: 热门短码缓存 + CDN
  - 统计: 异步写 ClickHouse
```

### 10.2 设计秒杀系统

```text
需求: 瞬间几万 QPS 抢限量商品

方案 (从外到内层层限流):
  1. 前端: 按钮置灰 + 验证码 (防刷)
  2. CDN/网关: 限流 + 缓存静态页面
  3. 入口层: 令牌桶限流 (只有商品数 ×10 的请求能进)
  4. 服务层:
     - 库存预热 (Redis 预扣库存)
     - 请求进 MQ 削峰
     - 消费端慢慢落库
  5. DB: 乐观锁更新库存

核心理念: 把流量一层一层拦住, 落到 DB 的已经很少了。
```

### 10.3 设计消息队列

```text
Kafka 类设计要点:
  - 分区 (Partition): 水平扩展的单位
  - 副本 (Replica): 高可用, ISR 同步
  - 顺序保证: 同一分区有序
  - 零拷贝: 消费直接从磁盘发, 不经过用户态
  - 存储: 分段文件 + 索引, 顺序写
  - 消费位点 (offset): 消费者自己维护
```

### 11.3 设计检查清单

```text
设计一个分布式系统之前, 先过一遍:

  数据层:
    □ 一致性要求是什么? (强一致 / 最终一致 / 因果)
    □ 数据量和 QPS 预估? (量级决定方案)
    □ 怎么分片? (按什么 key 分, 怎么扩容)
    □ 副本数? 复制方式? (主从 / 多主 / 无主)
    □ 故障怎么恢复? (RPO/RTO 目标)

  服务层:
    □ 有单点故障吗? (每个服务至少 2 副本)
    □ 上下游超时配置了吗? (不能无限等)
    □ 熔断/限流/降级做了吗? (保护自己和下游)
    □ 幂等性考虑了吗? (重试/重复消息/重复提交)
    □ 分布式事务用什么方案? (2PC / TCC / Saga / 消息表)

  运维层:
    □ 日志/指标/链路 三件套齐了吗?
    □ 告警能行动吗? (不是一堆没用的告警)
    □ 发布策略? (灰度 / 蓝绿 / 滚动)
    □ 回滚方案? (出问题多久能回滚)
    □ 容量规划? (峰值多少, 留多少余量)
    □ 故障演练过吗? (定期 chaos engineering)
```
