# 微服务架构最佳实践

> 微服务不是银弹，但如果要做，就得做对。本文不讲康威定律和领域驱动设计的概念，直接聚焦落地：服务拆分、API 设计、数据一致性、服务治理、观测、部署、安全、组织协同八个维度的实战经验、踩坑与推荐方案。适用于 20-200 个微服务规模的团队参考。

---

## 一、什么时候该用微服务？演进路径

### 1.1 先问自己三个问题

```text
要不要拆微服务？先过这三关：

  第 1 关: 团队规模
    3 个人 2 个服务 → 没必要, 部署成本都赚不回来
    10 个人 5 个服务 → 可以考虑, 但别拆太细
    50+ 人 20+ 业务域 → 微服务收益明显

  第 2 关: 业务复杂度
    简单 CRUD + 几个接口 → 单体就够
    多个业务域 + 不同变更节奏 → 拆了合理
    异构技术栈需求 + 独立扩缩容 → 必须拆

  第 3 关: 工程能力
    CI/CD 没有 → 别拆 (部署累死)
    监控日志没有 → 别拆 (出问题找不到)
    团队不会写分布式系统 → 别拆 (分布式坑太多)

三关都过了 → 可以开始微服务化。
不过任何一关没过 → 先补工程能力, 再谈架构。
```

### 1.2 常见的反模式

| 反模式 | 表现 | 后果 |
|:---|:---|:---|
| **纳米服务** | 一个 CRUD 拆成 3 个服务 | 调用链巨长，延迟爆炸，排障地狱 |
| **分布式单体** | 改个功能要改 5 个服务，一起发布 | 比单体还难搞，耦合比单体还紧 |
| **共享数据库** | 多个服务连同一个库，直接互相查表 | 数据耦合，改个字段全链路震 |
| **过度同步调用** | 一个请求串行调 8 个服务 | 一个慢全链慢，雪崩容易发生 |
| **没有基础设施** | 没有监控/日志/链路追踪/CI/CD | 出问题全靠猜，发布全靠手 |
| **按技术层拆** | UI/Service/DAO 各成一个服务 | 改一个功能要改三个服务，毫无独立部署价值 |

### 1.3 演进路径（推荐模式）

```text
微服务演进路线图 (6 阶段):

  阶段 1: 模块化单体
  ┌─────────────────────────────────────┐
  │  一个部署单元, 但代码按业务域分模块    │
  │  模块间通过接口调用, 不直接跨层访问   │
  │  数据库按域分 schema, 但一个实例      │
  └─────────────────────────────────────┘
           ↓  组织扩张 / 业务复杂度上升
  阶段 2: 核心域先拆
  ┌─────────────────────────────────────┐
  │  把最独立 / 变更最频繁的域先拆出来     │
  │  比如: 支付 / 用户 / 订单 先独立       │
  │  其他还在单体里, 逐步向外迁移          │
  └─────────────────────────────────────┘
           ↓  服务数量到 5-10 个
  阶段 3: 基础设施补齐
  ┌─────────────────────────────────────┐
  │  API Gateway / 注册中心 / 配置中心    │
  │  统一日志 / 监控 / 链路追踪           │
  │  CI/CD 流水线 / 容器化                │
  └─────────────────────────────────────┘
           ↓  基础设施成熟
  阶段 4: 全面微服务化
  ┌─────────────────────────────────────┐
  │  各业务域陆续独立, 服务数 20+         │
  │  引入服务网格 / 事件驱动 / 熔断降级   │
  │  建立 SRE / 平台团队                  │
  └─────────────────────────────────────┘
           ↓  服务数 50+
  阶段 5: 平台化治理
  ┌─────────────────────────────────────┐
  │  服务网格 / 多集群 / 混沌工程         │
  │  服务目录 / 契约测试 / API 生命周期   │
  │  自助发布平台 / 成本治理              │
  └─────────────────────────────────────┘
           ↓  服务数 100+
  阶段 6: 领域自治
  ┌─────────────────────────────────────┐
  │  按领域划分团队 (团队拓扑)            │
  │  每个领域端到端负责                  │
  │  内部平台支撑, 业务团队自助           │
  └─────────────────────────────────────┘
```

> **关键心法**：先保证"拆得开"，再追求"拆得好"。很多团队第一步就踩坑——还没模块化，直接上微服务，结果就是分布式屎山。

## 二、服务拆分原则

### 2.1 拆分的 5 个维度

```text
拆分服务不是拍脑袋定，按这 5 个维度评估：

  1. 业务域边界
     └─ 按 DDD 的限界上下文 (Bounded Context) 拆
        一个限界上下文 = 一个服务的候选

  2. 变更频率
     └─ 经常改的和几乎不改的分开
        比如: 商品基础信息很少变, 价格库存天天变 → 拆开

  3. 团队归属
     └─ 一个服务一个团队负责
        康威定律: 系统架构 = 沟通结构的镜像

  4. 性能要求
     └─ 高 QPS 和低 QPS 分开
        高 QPS 的服务单独扩容, 不拖累别人

  5. 数据一致性要求
     └─ 强一致性需求的放在一个服务里
        跨服务 = 最终一致性, 不能接受就别拆
```

### 2.2 拆分的粒度把握

**一个服务多大合适？** 没有标准答案，但有几个体感指标：

| 指标 | 过小 | 合适 | 过大 |
|:---|:---|:---|:---|
| 代码行数 | < 1000 行 | 5000-50000 行 | > 10 万行 |
| 数据表数量 | 1-2 张 | 3-10 张 | > 20 张 |
| 团队人数 | < 1 人 | 2-6 人 (2 Pizza Team) | > 10 人 |
| 接口数 | < 5 个 | 10-30 个 | > 50 个 |
| 发布频率 | 每天多次 | 每周 1-3 次 | 每月都难发一次 |

> **2 Pizza Team 原则**：一个团队两个披萨能吃饱，就是合适的规模（6-8 人）。对应到服务，也就是一个小团队端到端负责 1-3 个服务。

### 2.3 拆分实操步骤

```text
从单体拆微服务的 7 步法:

  1. 画现状图
     把单体里的模块、依赖、数据流全部画出来
     工具: 依赖分析工具 / 代码调用链 / 数据库 ER 图

  2. 找最松的耦合点
     找一个依赖最少、最独立的模块先拆
     通常是: 用户中心 / 通知服务 / 文件服务

  3. 定义接口契约
     先定 API 接口 (REST/RPC + 数据结构)
     用 API 优先设计 (API-First)

  4. 数据分离
     先拆代码，再拆库
     数据库可以先同实例不同 schema，逐步迁移
     数据迁移用双写 + 校验 + 切换，不搞大爆炸

  5. 引入防腐层 (Anti-Corruption Layer)
     老代码和新服务之间加一层适配
     老系统不用改太多，新服务可以独立演进

  6. 灰度切流
     新服务上线后，先切 1% 流量
     观察指标，逐步放大到 100%
     留好回滚开关

  7. 清理旧代码
     稳定运行 2-4 周后，删掉单体里的旧代码
     合并请求不要留尾巴 (否则永远删不干净)
```

### 2.4 拆分决策表

| 场景 | 拆不拆 | 原因 |
|:---|:---|:---|
| 两个模块经常一起改 | ❌ 别拆 | 高内聚，拆开就是分布式单体 |
| 数据强一致要求 | ❌ 慎拆 | 跨服务很难做强一致 |
| 一个接口都没有 | ⚠️ 等等 | 边界还不清楚，先模块化 |
| 不同团队维护 | ✅ 拆 | 团队独立比什么都重要 |
| 性能要求差很多 | ✅ 拆 | 各自扩缩容，成本优化 |
| 第三方系统对接层 | ✅ 拆 | 防腐隔离，外部变化不影响内部 |
| 通用工具/基础设施 | ✅ 拆 | 复用价值高 |

## 三、API 设计最佳实践

### 3.1 API 风格选型

| 风格 | 适用场景 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **RESTful + JSON** | 对外 API / 前端对接 | 简单、通用、调试方便 | 性能一般、类型弱 |
| **gRPC** | 服务间内部调用 | 高性能、强类型、流式 | 调试难、浏览器不直连 |
| **GraphQL** | BFF 层 / 前端灵活查询 | 前端按需取数据，减少请求 | N+1 问题、缓存难、复杂度高 |
| **异步消息** | 解耦 / 事件驱动 | 削峰填谷、松耦合 | 一致性复杂、排障难 |

**推荐组合**：

```text
    客户端
       │
       ▼  REST/GraphQL
  ┌──────────┐
  │  BFF/网关 │
  └────┬─────┘
       │
       ▼  gRPC (内部服务间)
  ┌──────────┐
  │ 微服务集群│
  └────┬─────┘
       │
       ▼  异步消息 (事件通知)
  ┌──────────┐
  │ 消息队列  │
  └──────────┘
```

### 3.2 REST API 设计规范

**URL 命名**：

| 原则 | 正确 | 错误 |
|:---|:---|:---|
| 名词复数 | `/users`, `/orders` | `/getUser`, `/user_list` |
| 层级嵌套不超过 3 层 | `/users/123/orders` | `/company/1/dept/2/team/3/user/4` |
| 不用动词 | `GET /users/123` | `GET /getUser?id=123` |
| 用中划线不用下划线 | `/user-profiles` | `/user_profiles` |
| 全小写 | `/orders/123/order-items` | `/Orders/123/OrderItems` |

**HTTP 方法**：

| 方法 | 用途 | 幂等 | 副作用 |
|:---|:---|:---|:---|
| GET | 查询 | ✅ | 无 |
| POST | 创建 | ❌ | 有 |
| PUT | 全量更新 | ✅ | 有 |
| PATCH | 部分更新 | ❌ | 有 |
| DELETE | 删除 | ✅ | 有 |
| HEAD | 取 header | ✅ | 无 |
| OPTIONS | 支持的方法 | ✅ | 无 |

**状态码使用**：

| 范围 | 用途 | 典型场景 |
|:---|:---|:---|
| 2xx | 成功 | 200 OK / 201 Created / 204 No Content |
| 3xx | 重定向 | 301 永久 / 302 临时 / 304 Not Modified |
| 4xx | 客户端错 | 400 参数错 / 401 未认证 / 403 无权限 / 404 不存在 / 409 冲突 / 429 限流 |
| 5xx | 服务端错 | 500 内部错误 / 502 网关错 / 503 不可用 / 504 超时 |

> **红线**：不要所有接口都返 200 然后 body 里放 code。HTTP 状态码就是协议的一部分，别浪费。

**统一响应格式**：

```json
// 成功 (200)
{
  "code": 0,
  "message": "ok",
  "data": {
    "id": 123,
    "name": "foo"
  },
  "requestId": "req-abc123"
}

// 列表 (200)
{
  "code": 0,
  "data": {
    "items": [],
    "total": 100,
    "page": 1,
    "pageSize": 20
  }
}

// 错误 (400)
{
  "code": 40001,
  "message": "参数校验失败",
  "details": [
    {"field": "email", "message": "邮箱格式不正确"}
  ],
  "requestId": "req-abc123"
}
```

### 3.3 gRPC 设计要点

```protobuf
// proto 文件命名: <服务名>.proto
// 包名: <公司>.<产品>.<版本>
syntax = "proto3";

package example.user.v1;

option go_package = "example.com/api/user/v1";
option java_multiple_files = true;
option java_package = "com.example.user.v1";

// 服务定义: 一个服务一组相关操作
service UserService {
  rpc GetUser(GetUserRequest) returns (GetUserResponse);
  rpc ListUsers(ListUsersRequest) returns (ListUsersResponse);
  rpc CreateUser(CreateUserRequest) returns (CreateUserResponse);
  rpc UpdateUser(UpdateUserRequest) returns (UpdateUserResponse);
  rpc DeleteUser(DeleteUserRequest) returns (DeleteUserResponse);

  // 流式: 大文件 / 实时推送
  rpc SubscribeUserEvents(SubscribeUserEventsRequest)
    returns (stream UserEvent);
}

// 消息命名: <操作名>Request / <操作名>Response
message GetUserRequest {
  int64 user_id = 1;  // 字段编号一旦分配就不能改
}

message GetUserResponse {
  User user = 1;
}

// 实体用单独的 message, 复用
message User {
  int64 id = 1;
  string username = 2;
  string email = 3;
  UserStatus status = 4;  // 枚举
  int64 created_at = 5;   // 时间用 int64 (秒/毫秒时间戳)
}

enum UserStatus {
  USER_STATUS_UNSPECIFIED = 0;  // 零值不使用, 前向兼容
  USER_STATUS_ACTIVE = 1;
  USER_STATUS_DISABLED = 2;
}
```

**gRPC 设计红线**：
1. **字段号一旦分配永不修改**，废弃字段用 `reserved` 保留
2. **枚举零值是 UNSPECIFIED**，防止忘记赋值时的静默错误
3. **不用 string 传时间/数字**，用 int64 时间戳或 `google.protobuf.Timestamp`
4. **字段按使用频率排序**，1-15 号字段编码更省空间
5. **接口版本号在包名里**（v1 / v2），升级不破坏老客户端

### 3.4 API 版本化

| 方式 | 示例 | 优点 | 缺点 |
|:---|:---|:---|:---|
| URL 路径版本 | `/v1/users`, `/v2/users` | 直观，路由简单 | URL 会变，客户端要改 |
| Header 版本 | `Accept: application/vnd.xxx.v2+json` | URL 不变 | 调试麻烦，缓存难 |
| Query 参数 | `/users?version=2` | 简单灵活 | 不优雅，容易乱 |
| 向下兼容扩展 | 加字段不改结构 | 成本最低 | 限制多，大改不行 |

**推荐**：对外 API 用 URL 路径版本（`/v1/` `/v2/`），内部 gRPC 用包名版本（`v1` / `v2`）。小改（加字段、加接口）保持兼容，不用升版本。

### 3.5 API 生命周期治理

```text
API 生命周期 5 阶段:

  设计 → 发布 → 维护 →  deprecate → 退役
   │       │       │          │         │
   ▼       ▼       ▼          ▼         ▼
  OpenAPI  文档    兼容保证    通知用户   下线确认
  契约测试  SDK     监控使用    时间线    使用率统计
  评审     版本    Bug 修复     迁移指引   最后下线
```

**废弃 API 的正确姿势**：
1. 先在文档和响应 header 里加 `Deprecation` 标记
2. 保留至少 6 个月的过渡期
3. 监控调用量，通知还在调用的业务方
4. 降到 0 了再下线（或者先返回 410 Gone 几天再删）

## 四、数据一致性与事务

### 4.1 微服务下的数据困境

```text
单体时代: 一个数据库 + 本地事务 → 强一致性 + ACID
微服务时代: 多个数据库 + 跨服务调用 → 只能最终一致

  ┌── 订单服务 ──┐     ┌── 库存服务 ──┐     ┌── 支付服务 ──┐
  │  order_db   │────▶│  stock_db   │────▶│ payment_db   │
  └─────────────┘     └─────────────┘     └─────────────┘
        一个事务？        另一个事务        又一个事务

问题: 中间任何一步失败, 前面的怎么回滚?
答案: 没有免费的午餐, 只能最终一致。
```

### 4.2 常见一致性方案对比

| 方案 | 原理 | 一致性 | 性能 | 复杂度 | 适用场景 |
|:---|:---|:---|:---|:---|:---|
| **2PC (两阶段提交)** | 协调者 + 参与者，先预提交再提交 | 强一致 | 差（锁资源） | 中 | 传统分布式事务，互联网少用 |
| **TCC (Try-Confirm-Cancel)** | 每个服务提供 Try/Confirm/Cancel 三个接口 | 最终一致 | 中 | 高 | 资金类、对一致性要求高的 |
| **本地消息表** | 业务数据和消息存在同一个本地事务 | 最终一致 | 好 | 低 | 通用，最推荐 |
| **事件驱动 + Outbox** | 业务 + 事件表同一事务，异步发布事件 | 最终一致 | 好 | 中 | DDD / Event Sourcing |
| **Saga (编排式)** | 一个协调者按步骤调用，失败反向补偿 | 最终一致 | 好 | 中高 | 长流程、多步骤 |
| **Saga (协同式)** | 各服务监听事件，自己决定下一步 | 最终一致 | 好 | 高 | 事件驱动架构 |

### 4.3 方案一：本地消息表（最推荐）

**原理**：业务操作和发消息在**同一个本地事务**里写入数据库，然后有个后台任务轮询消息表发送，发成功了标记已发送。

```text
本地消息表流程:

  1. 开启本地事务
  2. 执行业务 SQL (比如: 扣库存)
  3. 往 message 表插一条待发送消息
  4. 提交事务 (业务 + 消息要么都成要么都败)

  5. 后台任务 (或定时任务) 扫描 message 表 status=PENDING 的
  6. 发送到 MQ
  7. 发送成功 → 标记 SENT
     发送失败 → 重试 (有最大重试次数)
```

**消息表结构**：

```sql
CREATE TABLE `outbox_message` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `topic` varchar(128) NOT NULL COMMENT '消息主题',
  `biz_key` varchar(128) DEFAULT NULL COMMENT '业务唯一键, 去重用',
  `payload` json NOT NULL COMMENT '消息内容',
  `status` tinyint NOT NULL DEFAULT 0 COMMENT '0待发送 1已发送 2失败',
  `retry_count` int NOT NULL DEFAULT 0 COMMENT '重试次数',
  `next_retry_at` datetime DEFAULT NULL COMMENT '下次重试时间',
  `created_at` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_status_next` (`status`, `next_retry_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**优点**：
- 可靠性高（业务和消息同事务，不会丢）
- 实现简单（就是多一张表 + 一个定时任务）
- 和业务解耦，业务代码侵入小

**缺点**：
- 每个服务都要建一张消息表
- 有延迟（取决于轮询频率，通常秒级）

### 4.4 方案二：Saga 编排

适合跨多个服务的长流程，比如"下单 → 扣库存 → 扣余额 → 创建订单 → 发通知"。

```text
正常流程 (正向):
  订单服务 ──▶ 库存服务: 扣库存 ──▶ 支付服务: 扣余额 ──▶ 订单服务: 更新状态

失败补偿 (反向):
  订单服务 ◀── 库存服务: 加库存 ◀── 支付服务: 加余额 ◀── 订单服务: 标记失败
```

**Saga 状态机**：

```python
# Saga 状态机 (简化示意)
class OrderSaga:
    steps = [
        {"name": "reserve_stock", "service": "stock", "action": "reserve", "compensate": "release"},
        {"name": "deduct_balance", "service": "payment", "action": "deduct", "compensate": "refund"},
        {"name": "create_order", "service": "order", "action": "confirm", "compensate": "cancel"},
    ]

    def execute(self, params):
        completed = []
        for step in self.steps:
            try:
                call_service(step["service"], step["action"], params)
                completed.append(step)
            except Exception:
                # 失败 → 反向补偿已完成的步骤
                for s in reversed(completed):
                    call_service(s["service"], s["compensate"], params)
                raise
```

**Saga 的关键注意事项**：

| 注意点 | 说明 |
|:---|:---|
| 幂等性 | 补偿操作可能重复调用，必须幂等 |
| 空补偿 | Try 没成功就收到 Cancel → 直接返回成功（不能报错） |
| 悬挂 | Cancel 比 Try 先到 → Cancel 后 Try 再到要拒绝 |
| 持久化 | Saga 状态要落盘，服务重启后能恢复 |
| 监控 | Saga 失败率 / 平均时长 / 各步骤耗时 都要监控 |

### 4.5 幂等性设计

分布式系统里**所有写操作都要考虑幂等**。网络可能超时、消息可能重复投递、重试可能多次触发。

**常用幂等手段**：

| 手段 | 原理 | 适用场景 |
|:---|:---|:---|
| **唯一键 + 数据库唯一索引** | 业务唯一键重复插入报错 | 创建类操作 |
| **Token / 请求 ID** | 先拿 token，执行时校验 token 是否用过 | 前端提交防重复 |
| **状态机** | 状态只能单向流转，重复请求忽略 | 订单状态流转 |
| **乐观锁** | 版本号匹配才更新 | 更新类操作 |
| **去重表** | 专门一张表记录处理过的请求 | 通用方案 |
| **雪花 ID + 幂等表** | 上游生成全局唯一 ID，下游查重 | 消息消费 |

```sql
-- 去重表 (通用方案)
CREATE TABLE idempotent_record (
  id bigint AUTO_INCREMENT PRIMARY KEY,
  biz_type varchar(64) NOT NULL,
  biz_key varchar(128) NOT NULL,
  result json DEFAULT NULL,
  created_at datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_biz_type_key (biz_type, biz_key)
) ENGINE=InnoDB;
```

### 4.6 一致性选型决策树

```text
一致性选型:

  对一致性要求多高?
  │
  ├─ 强一致 (钱/库存等核心)
  │   └─ 服务数 ≤ 3? → TCC
  │   └─ 服务数多? → Saga + 人工对账兜底
  │
  ├─ 最终一致就行 (通知/日志/统计)
  │   └─ 业务简单 → 本地消息表
  │   └─ 领域事件驱动 → Outbox + 事件总线
  │
  └─ 可以丢少量 (日志采集/埋点)
      └─ 直接发 MQ, 失败就丢 (至少一次都不用保证)
```

> **真心话**：90% 的业务场景用"本地消息表 + 最终一致 + 定时对账兜底"就能搞定。不要一上来就 TCC / Saga 全家桶，复杂度收益不成正比。

## 五、服务治理

### 5.1 服务注册与发现

**主流方案对比**：

| 方案 | 一致性协议 | 性能 | 运维复杂度 | 生态 |
|:---|:---|:---|:---|:---|
| Nacos | Raft | 高 | 低 | Java 系首选 |
| Consul | Raft + Gossip | 中 | 中 | 云原生，多数据中心强 |
| Eureka | P2P (AP) | 高 | 低 | Spring Cloud 原生，已停更 |
| etcd | Raft | 高 | 中 | K8s 生态首选 |
| K8s Service + CoreDNS | - | 高 | 低 (K8s 自带) | K8s 环境 |

**K8s 环境推荐**：直接用 K8s 原生 Service + CoreDNS，不用额外的注册中心。简单、稳定、零运维成本。

什么时候才需要独立注册中心？
- 需要服务元数据（权重/版本/灰度标签）
- 需要精细的流量控制
- 跨集群 / 跨 K8s 服务发现
- 非 K8s 环境（物理机/VM）

### 5.2 配置中心

| 方案 | 特点 | 适用 |
|:---|:---|:---|
| Nacos Config | 长连接推送 + 控制台 + 历史版本 | Java 生态 |
| Apollo | 配置管理功能最全，灰度发布、权限 | 大型企业 |
| Spring Cloud Config | Git 存储，简单 | Spring 项目 |
| etcd | K8s 自带，强一致 | Go / 云原生 |
| ConfigMap + Reloader | K8s 原生，零依赖 | 简单场景 |

**配置管理最佳实践**：

```text
配置分三层:

  1. 环境级配置 (环境变量)
     数据库地址、中间件地址、环境标识
     → 通过 K8s ConfigMap / 环境变量注入

  2. 应用级配置
     线程池大小、超时时间、重试次数
     → 通过配置中心, 支持热更新

  3. 业务开关/动态配置
     功能开关、灰度比例、限流阈值
     → 通过配置中心 / 特性开关平台, 运营可改

红线:
  □ 密钥不放配置中心 (用 Secret Manager / Vault)
  □ 大文本不放配置中心 (放对象存储)
  □ 不直接改生产配置 (走审批/发布流程)
  □ 配置变更有审计日志 (谁改的、改了啥、什么时候)
```

### 5.3 熔断、降级、限流

| 概念 | 作用 | 触发条件 | 恢复 |
|:---|:---|:---|:---|
| **熔断** | 下游挂了就不调了，保护下游也保护自己 | 错误率/慢请求率超阈值 | 半开探测，成功了恢复 |
| **降级** | 非核心功能暂时关掉，保核心链路 | 系统负载高 / 依赖故障 | 故障恢复后回退 |
| **限流** | 防止突发流量冲垮服务 | QPS 超过阈值 | 流量降下来自动恢复 |

**熔断状态机**：

```text
  ┌───────┐    失败率超阈值     ┌────────┐
  │ Closed│ ─────────────────▶ │  Open  │  → 所有请求直接失败
  │(闭合)  │ ◀──────────────── │ (打开)  │
  └───────┘   熔断时间过后      └───┬────┘
        ▲                         │
        │                         │ 放一个请求试试
        │                         ▼
        │                    ┌──────────┐
        └─────────────────── │ Half-Open │
            探测成功          │ (半开)    │
                            └──────────┘
```

**降级策略示例**：

| 场景 | 降级方式 |
|:---|:---|
| 商品详情页推荐服务挂了 | 直接不显示推荐区域，返回空数据 |
| 搜索服务响应慢 | 返回热门榜单 / 本地缓存兜底 |
| 评价服务挂了 | 不显示评价，商品正常卖 |
| 消息推送服务挂了 | 攒着，恢复后补发 |
| 非核心链路全挂 | 只保核心交易链路，其他全关 |

**限流算法**：

| 算法 | 原理 | 优点 | 缺点 |
|:---|:---|:---|:---|
| 计数器 | 固定窗口内计数 | 简单 | 临界突发（窗口边界 2 倍流量） |
| **滑动窗口** | 时间片滑动，更平滑 | 准确 | 稍复杂 |
| **令牌桶** | 令牌匀速生成，请求拿令牌 | 允许突发，最常用 | 实现稍复杂 |
| 漏桶 | 匀速处理，多余排队/丢弃 | 输出平滑 | 应对突发能力弱 |

> **生产推荐**：限流用令牌桶（Guava RateLimiter / Sentinel / 网关层限流），熔断用 Resilience4j 或服务网格。

### 5.4 超时与重试

**超时配置原则**：

```text
一个请求的总超时 = 下游 P99 延迟 × 重试次数 + 余量

  ┌──────────────────────────────────┐
  │ 调用方总超时                      │
  │  ┌────────────────────────────┐  │
  │  │  第 1 次 (1s)  失败重试     │  │
  │  │  第 2 次 (1s)  失败重试     │  │
  │  │  第 3 次 (1s)  最终失败     │  │
  │  └────────────────────────────┘  │
  │  总超时 ≤ 3s + 网络开销           │
  └──────────────────────────────────┘
```

| 配置项 | 推荐值 | 说明 |
|:---|:---|:---|
| 连接超时 | 1-3s | 建连超时，和网络质量相关 |
| 读超时 | P99 × 2 | 至少覆盖 99% 的正常请求 |
| 重试次数 | 1-2 次 | 多了反而放大故障 |
| 重试退避 | 指数退避 + 抖动 | 避免大家同一时间重试（惊群） |
| 重试条件 | 只重试幂等的 + 网络错误 | POST 不能随便重试 |

**重试风暴（Retry Storm）**：

```text
下游挂了 → 所有上游都重试 → 本来下游就挂了, 流量还翻 N 倍 → 更挂了

解法:
  1. 熔断: 错误率高了直接停, 不重试
  2. 退避 + 抖动: 不要所有实例同一时刻重试
  3. 总超时严格控制: 重试别没完没了
  4. 限流: 下游有限流保护, 不会被打死
```

### 5.5 API Gateway

**网关职责边界**：

```text
网关做的事:
  ✅ 统一入口 / 路由
  ✅ 认证鉴权 (Token 校验)
  ✅ 限流 / 熔断 / 降级
  ✅ 日志 / 监控 / 审计
  ✅ 协议转换 (HTTP→gRPC / WebSocket)
  ✅ CORS / 缓存 / 压缩
  ✅ 灰度发布 / 流量切分
  ✅ WAF / 防爬 / 黑白名单

网关不做的事:
  ❌ 业务逻辑 (校验参数/组装数据)
  ❌ 数据聚合 (BFF 层做)
  ❌ 跨服务事务编排
  ❌ 复杂的业务鉴权 (应该在服务内做细粒度鉴权)
```

**选型**：

| 网关 | 定位 | 性能 | 生态 |
|:---|:---|:---|:---|
| Nginx + Lua | 老牌，稳 | 极高 | Lua 生态 |
| Kong | Nginx 基础上的 API 网关 | 高 | 插件丰富 |
| APISIX | Nginx + etcd，云原生 | 高 | 国产，插件多 |
| Spring Cloud Gateway | Java 系，Spring 生态 | 中 | Java 全家桶 |
| Envoy + Istio | 服务网格入口 | 高 | 云原生 |
| Traefik | 轻量，K8s 友好 | 高 | 云原生 |

## 六、可观测性

### 6.1 三大支柱

```text
可观测性三件套:

  ┌──────────┐  ┌──────────┐  ┌──────────┐
  │ Metrics  │  │ Logging  │  │ Tracing  │
  │  指标     │  │  日志     │  │  链路     │
  │  (数量)   │  │  (事件)   │  │  (路径)   │
  └────┬─────┘  └────┬─────┘  └────┬─────┘
       │              │              │
       └──────────────┼──────────────┘
                      ▼
                 统一关联 (trace_id)
```

**什么时候用什么**：

| 问题 | 先看什么 | 再看什么 |
|:---|:---|:---|
| 系统挂了吗 | 指标（错误率/成功率） | 日志 / 链路 |
| 为什么慢 | 指标（延迟分布） | 链路（哪个服务慢） |
| 某个请求报错 | 链路（trace_id） | 日志（具体错误） |
| 用户反馈有问题 | 日志（搜用户 ID） | 链路（看整条调用链） |
| 异常增长 | 指标（告警触发） | 日志（看什么错多了） |

### 6.2 日志规范

**日志级别**：

| 级别 | 用途 | 生产是否开启 |
|:---|:---|:---|
| ERROR | 系统级错误，需要人工介入 | ✅ |
| WARN | 异常但不影响主流程，值得关注 | ✅ |
| INFO | 关键业务流程节点，有追踪价值 | ✅ |
| DEBUG | 调试用，详细过程信息 | ❌ (按需开) |
| TRACE | 非常详细的调试信息 | ❌ |

**日志结构（JSON）**：

```json
{
  "timestamp": "2024-08-20T10:30:00.123Z",
  "level": "INFO",
  "traceId": "abc123def456",
  "spanId": "xyz789",
  "service": "order-service",
  "version": "v1.2.3",
  "env": "prod",
  "host": "pod-xxx",
  "userId": "10086",
  "requestId": "req-abc",
  "message": "订单创建成功",
  "biz": {
    "orderId": "O202408200001",
    "amount": 99.9
  },
  "stacktrace": ""     // error 级别才有
}
```

**日志红线**：

```text
❌ 不打敏感信息 (密码、身份证、手机号、银行卡)
❌ 不打整大对象 (一条日志几十 KB, 把 ES 撑爆)
❌ 循环里打 INFO (容易把日志系统打挂)
❌ 用 System.out.println (无级别、无格式)
❌ 只打"进来了" / "出去了" (没有信息量)

✅ 关键路径必须打 (入口、出口、异常、分支)
✅ 日志里带 traceId / userId / orderId 等检索关键字段
✅ 异常日志打完整堆栈
✅ 日志格式统一 (JSON 结构化)
```

### 6.3 链路追踪

**Trace / Span 模型**：

```text
一个 Trace = 一次完整的请求链路
一个 Span  = 链路上的一个节点 (一次服务调用)

  Client Request (Trace: abc123)
        │
        ▼
  ┌─────────────┐
  │ API Gateway │── Span: gateway
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │Order Service│── Span: order-service
  └──┬───────┬──┘
     │       │
     ▼       ▼
  ┌─────┐ ┌──────┐
  │Stock│ │Payment│  Span: stock-service / payment-service
  └─────┘ └──────┘
```

**埋点原则**：

```text
✅ 自动 + 手动结合
   - 框架级自动埋点 (MVC/Feign/RestTemplate/DB/MQ) → 80% 的链路有了
   - 关键业务节点手动加 span (重要方法/外部调用) → 剩下 20%

✅ 每个 span 带上业务标签
   - orderId / userId / productId / tenantId
   - 方便按业务维度查询链路

✅ 采样率合理
   - 全量采样成本太高 (存储 + CPU)
   - 生产建议: 1%-10% 全量采样 + 错误全采 + 关键业务全采

❌ 不要每个方法都打 span
   - 太多反而看不清
   - 只在跨进程 / 跨服务 / 关键业务节点打
```

### 6.4 告警体系

**告警分级**：

| 级别 | 响应时间 | 通知方式 | 示例 |
|:---|:---|:---|:---|
| P0 (紧急) | 5 分钟内 | 电话 + 短信 + 群 @所有人 | 核心服务不可用 / 大面积报错 |
| P1 (严重) | 15 分钟内 | 电话 + 群 | 单服务不可用 / 错误率 > 5% |
| P2 (一般) | 1 小时内 | 群消息 | 错误率上升 / 慢请求增加 / 队列堆积 |
| P3 (提醒) | 工作日处理 | 邮件 / 群消息 | 磁盘 80% / 超时率轻微上升 |

**告警设计原则**：

```text
告警不是越多越好, 而是越少越准越好。

  ✅ 每条告警都能行动 (收到就知道该干什么)
  ✅ 同类告警聚合 (100 个实例同一个错, 发 1 条就够)
  ✅ 分级 (不同级别不同渠道不同响应时间)
  ✅ 有告警就有处理 SOP
  ✅ 定期复盘无效告警，删掉/调阈值

  ❌ 告警风暴 (一次故障发几百条告警)
  ❌ 狼来了 (经常误报, 大家都不看了)
  ❌ 只有告警没有处理流程
  ❌ 只看技术指标, 不看业务指标
```

**关键业务指标（不只是技术指标）**：

```text
技术指标: CPU / 内存 / 错误率 / 延迟 / QPS
业务指标: 下单量 / 支付成功率 / GMV / 注册数 / 活跃用户

告警要以业务指标为主、技术指标为辅。
  例: CPU 90% 但下单量正常 → 不一定是问题
      下单量跌了 50% → 不管 CPU 多少都是大问题
```

## 七、部署与发布

### 7.1 CI/CD 流水线

```text
标准微服务 CI/CD 流水线:

  代码提交
     │
     ▼
  代码检查 (lint + 静态分析 + 安全扫描)
     │
     ▼
  单元测试 + 覆盖率检查
     │
     ▼
  构建镜像 + 扫描漏洞 (Trivy)
     │
     ▼
  推镜像仓库
     │
     ▼
  部署到测试环境
     │
     ▼
  集成测试 + 接口自动化
     │
     ▼
  灰度发布 (1% → 10% → 50% → 100%)
     │
     ▼
  发布完成

每个阶段失败就停，不往下走。
```

### 7.2 发布策略对比

| 策略 | 原理 | 对用户影响 | 资源成本 | 回滚速度 | 适用 |
|:---|:---|:---|:---|:---|:---|
| **滚动发布** | 逐批替换旧版本 | 无感知 | 低 (多几个实例) | 中 (再滚回去) | 大多数场景 |
| **蓝绿发布** | 两套环境，切流量 | 无感知 | 高 (×2 资源) | 极快 (切流量) | 核心业务、资源充足 |
| **金丝雀发布** | 逐步放量，先小比例 | 影响少部分用户 | 低 | 快 (切比例) | 大版本、有风险 |
| **A/B 测试** | 按用户特征分流 | 按策略 | 中 | 中 | 产品验证 |
| **重建发布** | 全删了再建 | 停机 | 低 | 慢 | 测试环境 / 小服务 |

**金丝雀发布流程（推荐）**：

```text
发布前: v1 跑 100% 流量

  步骤 1: 部署 v2 (0% 流量)
    确认 v2 Pod 都 Ready, 健康检查通过

  步骤 2: 1% 流量切到 v2
    观察 5-10 分钟
    看: 错误率 / 延迟 / 业务指标

  步骤 3: 10% → 30% → 50%
    每步观察, 指标异常立刻回滚

  步骤 4: 100%
    v1 留一段时间 (留着以防回滚)
    稳定 24h 后再缩掉 v1

回滚: 任意一步出问题, 立刻把流量切回 v1, v2 缩到 0
```

### 7.3 配置与代码分离

```text
配置的归配置, 代码的归代码。

  ❌ 不要把环境配置写死在代码里
  ❌ 不要把配置存在 Git 里的 properties 文件 (改配置要发版)
  ❌ 不要每个环境一份 jar 包 / 镜像 (同一份镜像, 不同环境用不同配置)

  ✅ 镜像一份, 配置通过环境变量 / ConfigMap / 配置中心注入
  ✅ 配置变更可以热更新, 不需要重发版
  ✅ 敏感配置 (密码/密钥) 走专门的密钥管理 (Vault / K8s Secret)
  ✅ 配置有版本、有审计、可回滚
```

### 7.4 健康检查

**三种探针**：

| 探针 | 作用 | 触发动作 |
|:---|:---|:---|
| `startupProbe` | 应用有没有启动完 | 启动超时就重启 |
| `livenessProbe` | 应用还活着吗 | 挂了就重启 |
| `readinessProbe` | 能接流量了吗 | 没好就从 Service 摘下来 |

**正确写法**：

```yaml
# 示例: Java 应用
startupProbe:
  httpGet:
    path: /actuator/health
    port: 8080
  failureThreshold: 30   # 最多等 30 × 10s = 5 分钟 (Java 启动慢)
  periodSeconds: 10

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 0    # startupProbe 成功后才开始
  periodSeconds: 10
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  periodSeconds: 5
  failureThreshold: 2
```

> **红线**：livenessProbe 不要和业务强依赖（数据库挂了就把应用重启 → 雪崩）。liveness 只探应用本身是不是活的，业务依赖用 readiness。

## 八、安全

### 8.1 认证 & 授权

**微服务安全分层**：

```text
  ┌───────────────────────────────────┐
  │  第 4 层: 数据级权限               │ ← 行级/列级权限, 数据脱敏
  ├───────────────────────────────────┤
  │  第 3 层: 接口级权限               │ ← 谁能调用哪个接口 (RBAC/ABAC)
  ├───────────────────────────────────┤
  │  第 2 层: 服务间认证               │ ← 服务 A 调服务 B 也要认证
  ├───────────────────────────────────┤
  │  第 1 层: 边缘认证 (网关)          ← 用户登录 / Token 校验
  └───────────────────────────────────┘
```

**服务间认证方案**：

| 方案 | 原理 | 安全 | 性能 | 复杂度 |
|:---|:---|:---|:---|:---|
| mTLS | 双向证书认证 | 高 | 中 (加解密开销) | 中 |
| JWT | 网关下发 token，各服务验证 | 中 | 高 | 低 |
| API Key | 每个服务一个 key | 低 | 高 | 低 |
| 服务网格 | sidecar 自动 mTLS | 高 | 中 (sidecar 开销) | 低 (业务零侵入) |

**推荐**：有服务网格就用 mTLS（零侵入），没有就用 JWT（简单够用）。

### 8.2 敏感数据

| 类型 | 处理方式 |
|:---|:---|
| 密码 | 加盐哈希 (bcrypt/Argon2)，不可逆 |
| 身份证/手机号 | 加密存储 (AES)，展示脱敏 |
| Token / API Key | 放 Vault / KMS，不放代码/配置 |
| 日志中的敏感信息 | 统一脱敏中间件，正则替换 |
| 数据库连接密码 | 从 Secret Manager 动态获取，不放配置文件 |

**密码存储红线**：
- ❌ 明文存密码
- ❌ MD5 / SHA1 存密码（太容易撞库）
- ✅ 用 bcrypt / Argon2id / PBKDF2
- ✅ 每个密码独立 salt

### 8.3 常见安全漏洞

| 漏洞 | 说明 | 防护 |
|:---|:---|:---|
| **越权访问** | 改个 userId 就能看别人的数据 | 接口级鉴权 + 数据归属校验 |
| **SQL 注入** | 拼接 SQL 字符串 | ORM / 预编译 / 参数化查询 |
| **XSS** | 用户输入直接渲染到页面 | 输入过滤 + 输出转义 |
| **CSRF** | 跨站请求伪造 | SameSite Cookie + Token |
| **重试风暴** | 下游挂了全往上怼 | 熔断 + 限流 + 退避 |
| **敏感信息泄露** | 错误堆栈 / 日志里有密码 | 统一异常处理 + 日志脱敏 |
| **依赖漏洞** | 第三方库有 CVE | 依赖扫描 + 定期升级 |
| **水平越权** | A 用户能操作 B 用户的数据 | 每个操作校验归属关系 |

## 九、组织与团队

### 9.1 团队拓扑

```text
微服务组织架构 = 系统架构的镜像 (康威定律)

  反模式: 前端组 / 后端组 / DBA 组 (按技术职能分)
    → 改一个功能要跨三个团队, 沟通爆炸

  正模式: 按业务域分团队 (每个团队全栈 + 端到端负责)
    订单团队 → 订单服务 + 订单库 + 订单前端
    支付团队 → 支付服务 + 支付库 + 支付前端
    用户团队 → 用户服务 + 用户库 + 用户前端

  平台团队 → 基础设施 / CI/CD / 监控 / 中间件
    支撑业务团队, 不直接做业务
```

**团队类型（Team Topologies）**：

| 团队类型 | 职责 | 和其他团队的交互 |
|:---|:---|:---|
| 流对齐团队 (Stream-aligned) | 端到端负责一个业务域 | 和其他团队尽量少依赖 |
| 平台团队 (Platform) | 提供内部平台/基础设施 | 为流对齐团队提供服务 |
| 赋能团队 (Enabling) | 帮助其他团队提升能力 | 培训、咨询、引入新技术 |
| 复杂子系统团队 (Complicated-subsystem) | 负责一个技术复杂的模块 | 被其他团队调用 |

### 9.2 服务所有权

```text
每个服务必须有明确的负责人 (Owner)。

  ✅ 一个服务有且只有一个主负责团队
  ✅ 代码仓库 / CI/CD / 线上问题 / 故障处理 都是这个团队负责
  ✅ 服务文档里写清楚: 谁负责、怎么联系、SLA 是什么
  ✅ 团队轮值 on-call, 线上告警直接打到 on-call

  ❌ 一个服务多个团队都改, 出了问题没人管
  ❌ 运维团队负责所有服务的稳定性 (不懂业务, 修不了)
  ❌ 团队只负责开发, 线上问题交给运维 (没有运维思维)
```

### 9.3 API 团队协作

**跨团队改 API 的正确姿势**：

```text
1. 先提 API 变更提案 (接口定义 + 变更原因 + 影响面)
2. 上下游一起评审 (消费者也要参与)
3. 先定契约 (API 文档 / proto 定义)
4. 提供方先做 (兼容新版本)
5. 消费方再对接
6. 旧版本保留一段时间 (过渡期)
7. 确认没人用了再下线
```

**契约测试**：
- 提供方保证 API 符合契约
- 消费方保证按契约调用
- 任何一方改了契约，CI 自动报错
- 工具：Pact / Spring Cloud Contract

## 十、踩坑与反模式 Top 20

| # | 反模式 | 为什么坑 | 正确做法 |
|:---|:---|:---|:---|
| 1 | 上来就全量微服务化 | 基础设施跟不上，一步到位必翻车 | 渐进式，先拆 1-2 个试试水 |
| 2 | 按技术层拆分服务 | DAO/Service/Controller 各一个服务 | 按业务域拆，不按技术层拆 |
| 3 | 共享数据库 | 数据耦合比代码耦合还难搞 | 每个服务独立的库，不准跨库直连 |
| 4 | 过度同步调用 | 一个请求串行调 7-8 个服务 | 能用异步就用异步，能聚合就聚合 |
| 5 | 分布式事务追求强一致 | 性能差 + 实现复杂 + 容易死锁 | 接受最终一致，对账兜底 |
| 6 | 没有幂等设计 | 重试/重复消息导致数据错乱 | 所有写接口必须考虑幂等 |
| 7 | 没有可观测性 | 出问题全靠猜，排查靠经验 | 日志/指标/链路三件套先到位 |
| 8 | 没有 CI/CD | 发版靠手，回滚靠哭 | 全自动流水线，一键发布回滚 |
| 9 | 日志打一堆没用的 | 日志系统撑爆，真问题找不到 | INFO 级别只打关键节点，结构化 |
| 10 | 告警泛滥 | 狼来了，大家都不看了 | 每条告警都能行动，定期清理 |
| 11 | 复制粘贴代码 | 多个服务同一份逻辑，改一个忘一个 | 公共逻辑抽 SDK / 公共服务 |
| 12 | 接口版本管理混乱 | 改个字段消费者全挂 | 向下兼容 + 版本号 + 废弃周期 |
| 13 | 服务粒度太细 | 100 行代码一个服务 | 合并服务，粒度放大 |
| 14 | 网关做业务逻辑 | 网关越来越重，变成大单体 | 网关只做通用能力，业务放服务里 |
| 15 | 所有调用都重试 | 下游挂了重试风暴打得更死 | 只重试幂等接口 + 熔断保护 |
| 16 | 超时配置不合理 | 下游挂了上游跟着耗死 | 总超时 < 上游超时，层层递减 |
| 17 | 没有压测 | 上线就崩 | 核心链路定期压测，知道容量边界 |
| 18 | 团队按技术职能分 | 改个功能跨三个团队 | 按业务域组队，端到端负责 |
| 19 | 没有服务目录 | 不知道有什么服务谁负责 | 服务注册 + 服务目录 + 文档 |
| 20 | 为了微服务而微服务 | 跟风，没有实际收益 | 先想清楚解决什么问题再拆 |

### 11.2 服务规模与阶段对应

| 服务数 | 团队规模 | 阶段 | 需要的基础设施 |
|:---|:---|:---|:---|
| 1-3 | 3-5 人 | 单体 / 微服务初期 | CI/CD + 基础监控 |
| 5-10 | 10-20 人 | 快速扩张 | 注册中心 + 配置中心 + 网关 + 链路追踪 |

### 11.3 检查清单

```text
新建一个微服务之前:
  □ 这个服务的边界清楚吗 (高内聚低耦合)?
  □ 有没有独立的业务价值 (能独立部署独立演进)?
  □ 团队有足够的人力维护吗 (2 Pizza Team)?
  □ 基础设施准备好了吗 (监控/日志/CI/CD)?
  □ 数据拆分方案定了吗 (会不会有分布式事务难题)?
  □ 和其他服务的接口契约评审过了吗?
  □ 有明确的负责人团队吗?
  □ 幂等性 / 容错 / 降级 设计了吗?

上线前:
  □ 单元测试覆盖率 > 70%
  □ 集成测试通过
  □ 核心接口有压测数据
  □ 日志/指标/链路 三件套齐全
  □ 告警规则配置完成
  □ 健康检查 (startup/liveness/readiness) 配好
  □ 资源限制 (request/limit) 配好
  □ 回滚方案验证过
  □ 服务文档写了 (接口文档 + 运维文档)

运营中:
  □ SLA / SLO 有定义且达标
  □ 定期做故障演练
  □ 依赖版本定期升级 (安全补丁)
  □ 定期 review 接口, 清理废弃接口
  □ 成本定期优化 (资源利用率)
```
