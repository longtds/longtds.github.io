# SRE 工程师实战指南（方法论 / SLI-SLO / 错误预算 / 事故管理 / 容量与稳定性）

> SRE（Site Reliability Engineering，站点可靠性工程）是 Google 提出的一套"用软件工程的方法解决运维问题"的实践体系。它的核心不是"上什么监控工具"，而是一组可量化、可决策、可问责的机制：用 **SLI/SLO** 定义"什么叫可靠"，用**错误预算**在"稳定性"和"迭代速度"之间做数据驱动的取舍，用**事故响应与复盘**把故障变成组织资产。本文面向已有运维基础、想体系化落地 SRE 的工程师，讲清方法论、数学公式、落地步骤、工程实践和常见反模式。

---

## 一、SRE 是什么

### 1.1 一句话定位

```text
SRE = 当你让软件工程师去做运维时, 诞生的东西 (Google, 2003, Ben Treynoyes)

本质:
  把"运维"从一项手工、被动、靠经验的工作,
  变成可量化、自动化、工程化、有明确决策边界的软件工程。
```

### 1.2 SRE 的核心信念

| 信念 | 含义 | 反直觉点 |
|:---|:---|:---|
| **可靠性是产品的属性** | 可靠性要像功能一样被定义、度量、排期 | 不是"越可靠越好"，而是"达到目标即可" |
| **100% 是错误的目标** | 用户对 99.999% 和 100% 的感知几乎无差别，但成本天差地别 | 追求 100% 会浪费资源、拖慢迭代 |
| **用错误预算做取舍** | 可靠性目标和上线速度是同一个指标的两面 | SLO 没达标时，**应该**冻结发布——这不是惩罚，是机制 |
| **拥抱风险** | 故障不可避免，关键是控制影响和从故障中学习 | 目标不是"不出事"，是"少出事、快恢复、不重犯" |
| **自动化一切重复劳动** | 人不该做机器能做的事 | SRE 团队的运维工作时间设上限（50%） |
| **事后无责（Blameless）** | 故障根因是系统问题，不是人的道德问题 | "惩罚人"会让人隐瞒，系统反而更不可靠 |

### 1.3 SRE 和传统运维、DevOps 的关系

```text
传统运维 (Ops):
  被动响应、手工操作、靠人盯、变更靠审批、目标是"系统别挂"
  开发和运维是两个部门, 责任互相甩

DevOps:
  一种"打破开发运维壁垒、共同对交付负责"的文化与运动
  强调自动化、CI/CD、协作, 但没有给出具体"怎么做可靠性决策"

SRE:
  DevOps 理念的一种具体实现 (class SRE implements DevOps)
  给出了可落地的机制: SLI/SLO、错误预算、自动化、事故流程、容量规划
```

**SRE vs DevOps 对照**：

| DevOps 关注点 | SRE 的具体实现 |
|:---|:---|
| 减少组织孤岛 | SWE 和 SRE 共享代码库、共同 oncall、错误预算把利益对齐 |
| 在变更中接受失败 | 错误预算量化"能接受多少失败"，预算耗尽自动减速 |
| 渐进式发布 | 灰度、Canary、Progressive Delivery 由错误预算门控 |
| 杠杆与工具化 | SRE 至少 50% 时间做工程/自动化，ops 工作设上限 |
| 度量一切 | SLI/SLO、USM、数据驱动的可靠性决策 |

> 一句话：**DevOps 是"应该做什么"的文化，SRE 是"具体怎么做"的一套带公式和流程的工程实践。**

### 1.4 SRE 团队的职责边界

```text
SRE 对什么负责 (Own):
  ✅ 服务的可靠性 (SLO 达成)
  ✅ 容量规划与性能
  ✅ 监控/告警/可观测性
  ✅ 事故响应与复盘
  ✅ 变更安全 (发布、灰度、回滚机制)
  ✅ 自动化 (消除 toil)

SRE 不对什么负责:
  ❌ 业务功能开发 (那是产品研发团队的事)
  ❌ 替业务团队长期背运维 (SRE 有"退出标准", 不达标可把服务退回)
  ❌ 无限度的"稳定需求" (可靠性目标要和产品一起定)
```

**关键机制——服务接入 SRE 的前提与退出**：

```text
接入前提 (SRE 不是什么服务都接):
  1. 服务有明确的负责人和团队
  2. 已建立基础可观测性 (有 SLI 可采)
  3. 通过 SRE 的就绪评审 (Production Readiness Review)
  4. 团队承诺配合错误预算机制

退出标准 (Service SLA 违约时可退回业务团队):
  服务长期不满足可运维性要求 (没有监控、不写复盘、
  反复犯同类错误、文档缺失), SRE 可将服务退回研发,
  研发自己值班, 直到整改达标。
  ⇒ 这保证 SRE 不会变成"给烂代码无限擦屁股"的团队。
```

## 二、SLI / SLO / SLA：可靠性的度量体系

这是 SRE 的基石。三个词必须分清楚，很多团队混为一谈导致落不了地。

### 2.1 定义与关系

```text
SLI (Service Level Indicator, 服务等级指标)
  → 一个可测量的"服务好不好"的量化指标
  → 例: 成功请求数 / 总请求数、P99 延迟、可用性百分比

SLO (Service Level Objective, 服务等级目标)
  → 针对 SLI 设定的"内部目标值"
  → 例: 99.9% 的请求在 300ms 内成功 (滚动 30 天)

SLA (Service Level Agreement, 服务等级协议)
  → 对客户的"合同承诺", 违约通常有赔偿
  → 例: 月度可用性不低于 99.5%, 否则减免当月费用

关系:
  SLO 是内部目标, SLA 是对外承诺
  SLA 必须比 SLO 宽松 (留缓冲), 否则动不动就违约赔钱
  SLI 是支撑前两者的数据
```

**数值关系示例**：

```text
内部 SLO:  99.9% 可用          ← 工程团队努力的目标
对外 SLA:  99.5% 可用          ← 给客户的承诺, 违约赔偿
                ↑
         中间 0.4% 是"缓冲带": 内部先于客户感知到问题, 有时间止血

绝不能让 SLA == SLO, 更不能 SLA 比 SLO 还高。
```

### 2.2 好 SLI 的特征

一个可落地的 SLI 应该是 **SPORC**（或类似原则）：

| 特征 | 说明 | 反例 |
|:---|:---|:---|
| **S**pecific 具体 | 明确测量什么、在哪测、怎么聚合 | "系统正常"（无法测量） |
| **P**roportion 比例化 | 最好用"好事件/总事件"的比率 | 只看错误数（不反映流量变化） |
| **O**utcome 用户视角 | 从用户体验出发，而非内部组件 | CPU 利用率（用户不关心 CPU） |
| **R**elevant 相关 | 和用户满意度真实相关 | 与体验无关的内部指标 |
| **C**omparable 可比较 | 不同时间、版本间可对比 | 口径经常变的指标 |

**SLI 的标准比率形式**：

```text
SLI = 好事件数 / 有效事件总数 × 100%

常见 SLI:
  可用性 SLI = 成功请求数 / 总请求数
  延迟 SLI   = 延迟 < 阈值的请求数 / 总请求数
  质量 SLI   = 返回正确数据的请求数 / 总请求数
  完整性 SLI = 及时处理的消息数 / 消息总数
```

### 2.3 延迟必须看分位数，不能只看平均值

这是最常见的错误：**用平均延迟衡量服务会掩盖长尾问题**。

```text
反例:
  100 个请求, 99 个用 10ms, 1 个用 5000ms
  平均延迟 = (99×10 + 5000)/100 = 59.9ms  ← 看起来还行?
  但有 1% 的用户等了 5 秒! 这 1% 可能就是支付失败的用户。

正确: 看分位数 (Percentile)
  P50 (中位数): 一半请求快于这个值   → 反映"典型体验"
  P90: 90% 请求快于这个值
  P95/P99: 长尾, 反映"最差的一批用户"
  P999: 极端长尾 (高流量服务要看)
```

**延迟 SLO 的设定方式（按比例而非单一阈值）**：

```text
不好: "平均延迟 < 200ms"
较好:
  90% 的请求 < 100ms   (P90)
  99% 的请求 < 300ms   (P99)
  99.9% 的请求 < 1000ms(P999)
```

### 2.4 选择 SLI 的框架（按请求类型）

| 请求类型 | 关键 SLI |
|:---|:---|
| **在线请求-响应**（API、网页） | 可用性（成功率）、延迟（P95/P99）、吞吐 |
| **批处理/离线任务** | 成功率、处理时长（是否在 deadline 前完成）、处理量/吞吐、数据新鲜度 |
| **流式/队列处理** | 端到端延迟、积压量（lag）、消息丢失率、处理速率 |
| **存储系统** | 读写成功率、延迟、持久性（durability，年数据丢失概率）、数据新鲜度 |

**批处理 SLI 的特殊性**：没有单个请求，重点是"**是否在截止时间前成功完成**"和"**数据多旧了**"。

```text
批处理 SLI 示例:
  成功率  = 成功结束的批任务数 / 总批任务数
  新鲜度  = 数据更新延迟 < 阈值的时间比例
  例: "每天 08:00 前报表数据必须更新完成" → 新鲜度 SLO
```

### 2.5 SLO 的数学：可用性等级与故障时间预算

| 可用性 | 俗称 | 每天允许停机 | 每月(30天) | 每年 |
|:---|:---|:---:|:---:|:---:|
| 90% | "两个九" | 2h 24m | 72h | 36.5 天 |
| 99% | 两个九 | 14m 24s | 7h 12m | 3 天 15.6h |
| 99.5% | | 7m 12s | 3h 36m | 1 天 19.7h |
| 99.9% | 三个九 | 1m 26s | 43m 12s | 8h 45m 36s |
| 99.95% | | 43.2s | 21m 36s | 4h 22m 48s |
| 99.99% | 四个九 | 8.6s | 4m 19s | 52m 33.6s |
| 99.999% | 五个九 | 0.86s | 25.9s | 5m 15.4s |

> 从三个九到四个九，允许停机时间缩到 1/10，但成本可能翻数倍。**多一个九不是线性成本，是指数成本。**

**怎么选目标？看用户和业务**：

```text
内部工具、非关键后台    → 99% ~ 99.5% 足够 (追求更高是浪费)
一般面向用户的 Web/API  → 99.9% (行业常见目标)
支付、交易、核心链路    → 99.95% ~ 99.99%
电信级/生命相关          → 99.999% (需要巨额投入和冗余设计)

决策原则: 用户能容忍什么 + 多花的钱能不能换来对应的业务价值。
```

### 2.6 SLO 落地步骤（从 0 到 1）

```text
第 1 步: 梳理用户旅程和关键动作
  用户用你的服务做什么? (下单、支付、查询、登录……)
  列出"如果这个动作失败, 用户会直接受影响"的关键事务 (Critical User Journeys)

第 2 步: 为每个关键动作定义 SLI
  选能反映用户体验的指标, 而不是机器指标
  例: "下单接口 HTTP 2xx 且在 800ms 内返回" 的比例

第 3 步: 先测, 再定目标 (不要拍脑袋)
  先采集 2~4 周的真实 SLI 数据, 看当前实际水平
  SLO 应该"跳一跳够得着": 比现状略好, 而不是远高于现状

第 4 步: 设定滚动窗口 SLO
  推荐用滚动 28/30 天窗口, 而不是自然月 (自然月月初清零会掩盖问题)

第 5 步: 建 SLO 看板和错误预算燃尽图
  让所有人能实时看到: 当前 SLO 达成率、错误预算还剩多少、预算消耗速率

第 6 步: 定义预算耗尽时的策略 (关键!)
  没有"预算耗尽怎么办"的 SLO 只是数字, 不是机制

第 7 步: 定期复盘和调整
  SLO 不是定一次就完。季度回顾: 目标太低还是太高? SLI 选得对不对?
```

## 三、错误预算（Error Budget）：SRE 的决策引擎

### 3.1 概念与公式

```text
错误预算 = 1 - SLO

例: SLO = 99.9%
  则错误预算 = 0.1%
  滚动 30 天:
    总请求预算 = 30 × 24 × 60 = 43200 分钟
    允许的"不可用分钟" = 43200 × 0.1% = 43.2 分钟

  或按请求:
    30 天预计 1 亿次请求
    允许的失败请求 = 1亿 × 0.1% = 10 万次
```

**核心思想**：

```text
SLO 99.9% 意味着你"被允许"有 0.1% 的失败。
这 0.1% 就是可以用来"冒风险"的预算:
  - 发新版本可能出 bug
  - 做变更可能引入故障
  - 做实验可能失败

只要错误预算没花完, 团队就应该大胆、快速地迭代。
一旦错误预算花完, 就必须停止冒险, 全力修稳定性, 直到预算恢复。
```

### 3.2 错误预算怎么驱动决策

| 预算状态 | 动作 |
|:---|:---|
| 预算充足（剩很多） | 放心发布、做变更、上实验性特性，迭代速度优先 |
| 预算消耗正常 | 正常节奏，保持监控 |
| 预算消耗过快 | 提高警惕，加强灰度和评审，排查预算主要被谁消耗 |
| 预算接近耗尽 | 冻结高风险变更，只允许稳定性修复和安全补丁 |
| 预算已耗尽 | **冻结所有非必要发布**，所有资源转向提升可靠性（补测试、修 bug、加冗余），直到预算恢复 |

**为什么这个机制强大**：

```text
没有错误预算时 (典型争吵):
  开发: "赶紧上线这个功能!"
  运维: "不行, 万一挂了怎么办?"
  → 靠职位高低、嗓门大小、关系好坏决策, 永远扯皮

有错误预算时:
  大家看同一个数字。预算还剩 60%, 开发自己就能决定发;
  预算只剩 2%, 运维说"先别发", 开发也认, 因为数字摆在那。
  → 把"立场之争"变成"数据决策", 开发和运维利益对齐。
```

### 3.3 多窗口多燃尽率告警（Multiwindow, Multi-Burn-Rate Alert）

错误预算消耗速度是核心告警依据。Google SRE 推荐**多窗口 + 多燃尽率**策略，避免"预算还很多但短时故障疯狂告警"或"预算快没了但没人发现"。

**燃尽率（Burn Rate）**：消耗预算的相对速度。

```text
burn rate = 1 → 恰好按预算允许的速度消耗 (30 天恰好花完)
burn rate = 14.4 → 1 小时烧掉 14.4 小时的预算 (快速, 要告警)
burn rate > 14.4 → 极快, 立即呼叫人 (page)
```

**经典告警策略表**（Google SRE 推荐，30 天窗口、预算 0.1% 即 43.2 分钟）：

| 燃尽率 | 长窗口 | 短窗口 | 动作 | 含义 |
|:---:|:---:|:---:|:---|:---|
| 14.4× | 1h | 5m | **Page（呼叫）** | 约 2% 预算/小时，2 天会烧完 |
| 6× | 6h | 30m | **Page** | 约 5% 预算/天，5 天烧完 |
| 3× | 24h | 2h | **工单（ticket）** | 10 天烧完，工作日处理 |
| 1× | 72h | 6h | **工单** | 30 天恰好烧完，趋势预警 |

> 双窗口的意义：长窗口确认"这是持续问题不是抖动"，短窗口确认"问题现在还在发生"，两者同时满足才告警，大幅降低误报和漏报。

### 3.4 错误预算的常见坑

```text
坑 1: 预算耗尽没有任何后果
  → SLO 立刻变成墙上的标语。必须预先约定"耗尽就冻结发布"并真的执行。

坑 2: SLO 定得太高, 预算永远花不完
  → 团队被过度约束, 迭代龟速。说明 SLO 脱离业务需要, 应下调。

坑 3: SLO 定得太低, 预算永远花不完
  → 错误预算失去约束意义, 且用户体验真的差。应上调或拆分。

坑 4: 一个 SLO 套整个系统
  → 核心支付和边缘功能用同一个目标, 要么浪费要么不够。应按关键事务分层。

坑 5: 只看故障, 不把灰度/降级的部分失败计入
  → 预算被低估, 实际体验差但 SLO 显示健康。SLI 必须覆盖真实用户路径。

坑 6: 自然月窗口
  → 月底预算花完, 月初清零, 团队月底摆烂/月初激进。用滚动窗口。
```

## 四、监控与告警工程

> 监控工具的部署见 [12_AIOps](../12_AIOps/index.md) 相关文章，这里讲的是**监控的方法论和告警设计原则**。

### 4.1 监控的四个黄金信号（Four Golden Signals）

Google 提出，每个服务都应该监控这四类信号，覆盖了绝大多数故障形态：

| 信号 | 含义 | 缺了它会怎样 |
|:---|:---|:---|
| **延迟（Latency）** | 请求延迟，**成功和失败请求要分开统计** | 慢故障、长尾问题发现不了 |
| **流量（Traffic）** | 需求量，如 QPS、带宽、并发 | 无法做容量规划、区分"错误率高"是量少还是全挂 |
| **错误（Errors）** | 失败请求率/数，区分显式错误和隐式错误 | 业务失败、数据错误无感知 |
| **饱和度（Saturation）** | 系统离"最满"还有多远（CPU、内存、队列、IO） | 资源耗尽型故障无预警（通常是故障的前兆） |

```text
"失败请求的延迟"要单独统计:
  一个请求 500 错误返回得很快, 延迟很低,
  如果混在一起算平均延迟, 会掩盖大量快速失败。
```

**补充框架——USE 方法（偏资源/主机视角）**：

```text
Utilization   使用率   (资源被用的比例, 如 CPU 80%)
Saturation    饱和度   (排队等待的量, 如 run queue、IO wait)
Errors        错误数   (错误计数)
适合排查单机/网络/磁盘资源瓶颈。
```

**RED 方法（偏请求服务视角）**：

```text
Rate    每秒请求数
Errors  每秒失败请求数
Duration 请求延迟分布
适合微服务/API 的监控, 是黄金信号在请求侧的精简。
```

> 实战组合：**用 RED 监控服务层面，用 USE 监控资源/节点层面，用黄金信号做完整覆盖。**

### 4.2 告警的分层：症状 vs 原因

```text
症状告警 (Symptom-based) — 应该 page 人:
  "用户受影响了" — SLO 燃烧、错误率飙升、延迟超标、核心接口不可用
  → 面向用户可感知的问题, 需要人立即介入
  → 数量少、质量高、可执行

原因告警 (Cause-based) — 通常只建工单:
  "某个内部组件异常, 但用户暂时没感知" — 单盘故障、CPU 高、主从切换
  → 可能自愈或有冗余, 工作时间处理即可
```

**告警设计原则**：

| 原则 | 说明 |
|:---|:---|
| **每条 page 告警都应可操作** | 收到就知道要做什么；"CPU 高"且无人需要操作的，不该 page |
| **优先基于 SLO 燃尽率告警** | 而不是基于每个组件阈值，避免告警风暴 |
| **告警指向症状，仪表盘指向原因** | 告警说"用户下单失败率高"，仪表盘让你去下钻定位是 DB 还是网络 |
| **消除告警噪音** | 没人处理的告警 = 没有告警，还训练了人忽略告警（狼来了） |
| **分级 + 分级响应** | P1 立即 page、P2 工作时间、P3 工单，不要所有告警都 @全员 |
| **避免阈值过敏** | 静态阈值加持续时间/多窗口确认，防止瞬时抖动告警 |

### 4.3 告警分级示例

| 级别 | 定义 | 响应 | 例子 |
|:---|:---|:---:|:---|
| **P1 紧急** | 核心功能大面积不可用 / SLO 快速燃尽 / 数据丢失风险 | 立即（7×24 page，5 分钟响应） | 支付全挂、主库宕机、全站 502 |
| **P2 高** | 部分功能受影响 / 冗余失效 / 错误预算中速燃烧 | 30 分钟~工作时间 | 单 AZ 故障但服务降级、缓存全失效、非核心接口高错误率 |
| **P3 中** | 用户暂无明显影响，需要处理 | 工作日工单 | 磁盘 80%、单副本异常、慢查询增多 |
| **P4 低** | 优化项、趋势性问题 | 排期 | 容量趋势、技术债、偶发抖动 |

### 4.4 一个 SLO 告警的 PromQL 示例

```promql
# 30 天 SLO=99.9% (错误预算 0.1%)
# 短窗口 5 分钟、长窗口 1 小时, burn rate 14.4x → page
# 14.4x burn over 1h 对应错误率 = 14.4 × 0.001 = 1.44%
# 双窗口: 1 小时错误率高 AND 5 分钟错误率仍高

(
  sum(rate(http_requests_total{code=~"5.."}[1h]))
  / sum(rate(http_requests_total[1h]))
  > 14.4 * 0.001
)
and
(
  sum(rate(http_requests_total{code=~"5.."}[5m]))
  / sum(rate(http_requests_total[5m]))
  > 14.4 * 0.001
)
```

> 用 Prometheus 时，更工程化的做法是引入 **Sloth / Pyrrha / OpenSLO** 这类 SLO 工具自动生成多窗口燃尽告警规则，不用手写每一条。

## 五、事故响应管理（Incident Response）

### 5.1 事故生命周期

```text
   发现                响应                 缓解               恢复              复盘
    │                  │                   │                 │                │
 监控告警/    →  值班响应、拉起   →  止血(降级/限流/   →  确认服务恢复   →  无责复盘、
 用户上报       应急指挥、定级       回滚/切流量)         SLO 回升          行动项跟踪
                分配角色
    │                                                                     │
    └──────────── 时间线全程记录 (Timeline) ────────────────────────────────┘
```

### 5.2 事故响应中的角色（不要一堆人乱作一团）

| 角色 | 职责 |
|:---|:---|
| **事故指挥官（IC，Incident Commander）** | 总指挥：定级、决策、协调，**通常不亲自操作**，保证全局可控 |
| **操作/技术负责人（Ops Lead）** | 执行具体止血操作（回滚、切流、扩容），和 IC 明确分工 |
| **通讯/记录负责人（Comms / Scribe）** | 记录时间线、对内对外同步状态，让技术的人不被打断 |
| **相关专家（按需）** | DBA、网络、业务研发等被拉入支援 |

> 小事故可以一人多角，但**一定要有一个人在"指挥位"做全局判断和对外沟通**，避免所有人埋头操作、没人看全局和时间线。

### 5.3 响应的关键原则

```text
① 缓解优先, 根因其次 (Mitigate first)
   目标是尽快让用户恢复, 不是当场定位根因。
   能回滚就回滚, 能切流就切流, 能降级就降级。
   根因可以等服务恢复后慢慢查 (保留现场证据即可)。

② 升级要果断, 不要硬扛
   5~15 分钟没进展就升级拉人。早叫人是负责任, 不是无能。

③ 全程记录时间线
   谁、几点、做了什么、结果如何。这是复盘和改进的依据。

④ 对外沟通要诚实、有节奏
   固定间隔更新状态 (哪怕"还在查, 暂无进展"), 不要让业务和管理层只能靠猜。

⑤ 冻结非必要变更
   重大事故期间, 其他发布一律暂停, 避免叠加变量。
```

### 5.4 无责复盘（Blameless Postmortem）

这是 SRE 文化的灵魂。

**核心假设**：

```text
在一个设计良好的系统里, 假设操作的人都是理性、想做好工作的。
事故发生, 是因为系统(流程、工具、设计、文档)给了人犯错的空间。
问"为什么系统允许这个错误变成事故", 而不是"谁犯了错"。
```

**为什么必须无责**：

```text
如果复盘会追责、惩罚:
  → 下次出事, 第一反应是隐瞒、甩锅、不敢操作
  → 组织失去从故障中学习的机会
  → 同类故障反复发生 (因为真正的系统性问题没被修)

无责文化下:
  → 人愿意主动报告、如实还原、分享教训
  → 每个故障都变成一次系统改进
```

**复盘文档模板**：

```markdown
# 事故复盘: <标题, 用现象而非人名, 如"订单接口 P99 延迟激增">

## 摘要 (一句话说清影响)
- 发生时间: 2026-xx-xx 14:02 ~ 15:18 (CST), 持续 76 分钟
- 影响范围: 约 12% 下单请求超时, 华东区为主
- 严重等级: P1
- 业务影响: 预估损失订单约 xxx 笔

## 时间线 (Timeline, 精确到分钟)
- 14:02  监控告警: 下单接口 P99 > 1s (burn rate 14.4x page)
- 14:05  值班 A 响应, 定位到 DB 主库 CPU 100%
- 14:12  拉起事故指挥, 判定 P1, 拉入 DBA
- 14:25  发现为 xx 批处理任务全表扫描导致
- 14:31  kill 慢查询 + 限流批任务, 延迟开始下降
- 15:18  SLO 恢复, 解除应急

## 根因分析 (用 5 Whys / 鱼骨图, 找系统性原因)
直接原因: 批处理任务缺少查询条件, 触发全表扫描
深层原因:
  - 该任务上线未经过 SQL 评审 (流程缺口)
  - 数据库缺少慢查询自动 kill 保护 (系统缺口)
  - 批任务和在线交易共用主库, 无资源隔离 (架构缺口)

## 做得好的 (What went well)
- 监控在用户大规模感知前 3 分钟告警
- 回滚/限流决策果断

## 做得不好的 / 运气成分 (What went wrong)
- 值班同学一开始试图自己调 SQL, 延迟了升级 10 分钟
- 时间线靠事后回忆, 记录不完整

## 行动项 (Action Items, 必须可跟踪、有负责人、有期限)
| # | 行动项 | 负责人 | 优先级 | 截止 | 状态 |
|---|--------|--------|--------|------|------|
| 1 | 修复该批任务 SQL 并加查询条件 | xxx | P1 | xx | 待办 |
| 2 | 上线慢查询自动 kill (阈值 30s) | xxx | P1 | xx | 待办 |
| 3 | 批任务迁移到只读从库/隔离资源组 | xxx | P2 | xx | 待办 |
| 4 | 完善上线 SQL 评审 checklist | xxx | P2 | xx | 待办 |

## 经验教训 (可复用)
- <提炼成可推广的通用经验>
```

**行动项的铁律**：

```text
① 每个行动项必须有: 明确内容 + 负责人 + 优先级 + 截止日期
② 必须跟踪到关闭, 不能"写完就结束在文档里"
③ 行动项要改系统, 而不是"下次注意" (人不是可靠的防线)
   ❌ "下次操作小心点"
   ✅ "给该操作加二次确认和自动备份"
④ 优先消除"能让同类故障发生"的系统性条件
```

### 5.5 5 Whys 根因分析示例

```text
现象: 用户下单失败率升高
Why 1?  数据库连接池耗尽
Why 2?  慢查询长时间占用连接
Why 3?  新上线的报表功能没有分页, 一次查百万行
Why 4?  该功能上线时没有 DBA 评审和性能测试
Why 5?  上线流程里没有"涉及 DB 变更必须过 DBA"的强制卡点
        ↑ 真正的根因: 流程缺口
行动: 在 CI/CD 中加 DB 变更强制评审卡点 (改系统, 而非怪人)
```

## 六、容量规划（Capacity Planning）

### 6.1 目标

```text
容量规划要回答:
  "为了应对未来的负载(增长、促销、突发), 我需要在什么时候、
   加多少什么资源, 才能既不浪费、又不会被打爆?"

核心矛盾:
  资源加太少 → 高峰期被打爆, SLO 违约
  资源加太多 → 长期闲置, 成本高企 (和 FinOps 直接相关)
```

### 6.2 容量规划的输入

| 输入 | 来源 |
|:---|:---|
| 当前资源使用率与上限 | 监控（USE 指标） |
| 业务增长预测 | 业务方（自然增长率、用户计划） |
| 已知峰值事件 | 大促、活动、新品发布、结算日 |
| 单机/单实例容量基准 | 压测得出的单实例最大安全 QPS |
| 余量目标（Headroom） | 一般保留 20%~40% 余量应对突发和故障切换 |

### 6.3 基本计算方法

```text
步骤 1: 压测得到单实例安全容量
  单实例在满足延迟 SLO (如 P99 < 300ms) 前提下, 最大 QPS = 2000
  (注意: 不是压到崩, 是压到"快违反 SLO"的临界点)

步骤 2: 预测目标峰值
  日常峰值 QPS = 8000
  大促预估 = 日常 × 5 = 40000 QPS

步骤 3: 计算所需实例 (含余量和故障冗余)
  基础需求   = 40000 / 2000 = 20 台
  加 30% 余量 = 20 × 1.3 = 26 台
  N+1/N+2 冗余: 考虑挂掉 1~2 台仍不超载 → 取 28 台

步骤 4: 结合水平扩展边界
  确认数据库、网络、下游依赖也能支撑这个量
  (应用层好扩, 有状态层往往才是真正的容量天花板)
```

### 6.4 容量与自动扩缩容

```text
K8s HPA: 按 CPU/内存/自定义指标(如 QPS、P99)自动伸缩
  优点: 应对可预测的周期性波动、削峰
  坑:   扩容有滞后(分钟级), 扛不住瞬间洪峰;
        冷启动慢的服务要预留基础副本数

关键实践:
  ① 用 SLO 相关指标驱动扩缩容, 而不只是 CPU
  ② 设合理的 minReplicas 兜底, 别缩到 0/1
  ③ 大促前预扩 (pre-provisioning), 不要赌自动扩容能跟上
  ④ 配合限流/熔断, 容量到顶时优雅降级而不是雪崩
```

### 6.5 负载测试的分类

| 类型 | 目的 |
|:---|:---|
| **负载测试（Load）** | 在预期负载下验证性能和 SLO |
| **压力测试（Stress）** | 超出预期负载，找崩溃点和失效模式 |
| **峰值/洪峰测试（Spike）** | 瞬间流量暴涨（秒杀），验证弹性和限流 |
| **浸泡测试（Soak/Endurance）** | 长时间中等负载，发现内存泄漏、连接泄漏 |
| **容量测试（Volume）** | 数据量极大时的性能（如十亿行表） |
| **混沌工程（Chaos）** | 主动注入故障，验证系统韧性（见下章） |

## 七、变更管理与韧性工程

### 7.1 变更：故障的最大来源

```text
行业统计: 约 60%~80% 的生产故障由变更触发 (发布、配置、基础设施变更)。
所以 SRE 的一大块工作是"让变更更安全", 而不是"禁止变更"。
```

**安全变更的机制**：

| 机制 | 作用 |
|:---|:---|
| **渐进式发布（Progressive Delivery）** | 小范围逐步放量，出问题影响面小 |
| **金丝雀发布（Canary）** | 先放 1% 流量到新版本，对比 SLI 后再扩大 |
| **蓝绿部署（Blue-Green）** | 两套环境切换，出问题秒级切回 |
| **功能开关（Feature Flag）** | 发布和"对用户可见"解耦，可秒级关闭新功能（不用回滚代码） |
| **快速回滚（Rollback）** | 每次发布必须有验证过的回滚方案，且回滚要比上线快 |
| **变更窗口/冻结期** | 高危时段（大促、深夜无人）冻结非必要变更 |
| **变更追踪** | 任何变更可追溯，故障时能快速回答"最近改了什么" |

### 7.2 金丝雀分析（Canary Analysis）

```text
把新版本和稳定版本的关键 SLI 自动对比:
  错误率:   canary 5xx% vs baseline 5xx%
  延迟:     canary P99 vs baseline P99
  成功率/业务指标: 支付成功率等

判定:
  canary 指标显著恶化 → 自动暂停/回滚发布
  canary 指标正常     → 自动/手动进入下一阶段放量

工具: Argo Rollouts, Flagger (配合 Istio/NGINX 做流量切分)
关键: 用统计方法判断"显著"差异, 避免小样本下的误判。
```

### 7.3 熔断、限流、降级：韧性三板斧

| 模式 | 解决什么 | 做法 |
|:---|:---|:---|
| **熔断（Circuit Breaker）** | 下游挂了，调用方不要一直傻等把自己拖垮 | 连续失败超阈值就"断开"，直接快速失败，定期探测恢复 |
| **限流（Rate Limiting）** | 流量超过容量时，保护系统不被打挂 | 超过阈值的请求拒绝/排队（令牌桶、漏桶、滑动窗口） |
| **降级（Degradation）** | 资源不足时，保核心、弃边缘 | 关闭推荐、评论等非核心功能，保支付/下单主链路 |

```text
雪崩的形成:
  下游变慢 → 调用方线程全部卡在等待 → 调用方线程池耗尽
  → 调用方也挂 → 调用调用方的上游也跟着挂 → 级联雪崩

熔断的价值:
  下游不健康时快速失败, 不占用调用方线程, 切断级联。
配合超时(timeout)和重试预算(retry budget)效果更好:
  - 每个外部调用必须有超时, 不能无限等
  - 重试要有上限和退避, 避免"重试风暴"放大故障
```

### 7.4 混沌工程（Chaos Engineering）

```text
定义: 主动、有计划地向系统注入故障, 验证系统是否真的如设计般 resilient。

常见实验:
  - 杀实例 / 杀 Pod (验证自动拉起和负载均衡)
  - 模拟 AZ 故障 (验证跨可用区容灾)
  - 网络延迟/丢包/分区 (验证超时和重试)
  - CPU/内存/磁盘打满 (验证资源隔离和限流)
  - 依赖服务不可用 (验证熔断降级)

原则:
  ① 先在测试/预发布环境做, 成熟后再在生产(小范围、有预案)
  ② 定义"稳态假设"(blast radius + 停止条件)
  ③ 从小爆炸半径开始, 随时可一键终止实验
  ④ 工作日、有人值守时做, 绝不在周五下午/大促期做

工具: Chaos Mesh (K8s 原生), Litmus, Gremlin, AWS FIS
```

## 八、Toil：SRE 要消灭的敌人

### 8.1 什么是 Toil

```text
Toil = 那些手工的、重复的、可自动化的、无长期价值的、
       随服务规模线性增长的运维劳动。

特征:
  手工的、重复的、可自动化的、琐碎的、无持久价值的、
  与服务规模成比例增长的。

例子:
  - 每天手工重启某个卡住的服务
  - 手工扩容、手工创建账号、手工导数据
  - 手工检查一堆仪表盘再发日报
  - 反复手工处理同类告警/工单
```

> **不是所有运维工作都是 toil**：应急响应、复杂排障、架构设计、写自动化工具本身——这些有长期价值，不是 toil。

### 8.2 Google 的 50% 上限原则

```text
SRE 团队应保证运维(toil)工作不超过 ~50% 时间,
剩下至少 50% 投入工程: 写自动化、改系统、做平台。

如果 toil 长期超过 50%:
  → 团队沦为"人肉运维", 没有时间改进系统
  → 系统不改进 → toil 更多 → 恶性循环
  → 应该向上反映、增员或用"退回服务"机制倒逼业务团队整改
```

### 8.3 降低 Toil 的路径

```text
① 识别和度量 toil
   让团队记录时间花在哪, 量化 toil 占比

② 自动化高频重复操作
   脚本化 → 平台化 → 自愈(self-healing)

③ 把运维知识沉淀进系统
   常见故障的处理逻辑做成自动处置, 而不是写进 Wiki 等人来看

④ 推动"你 build, 你 run"
   让业务研发对自己服务的运维负责, SRE 提供平台和标准, 而非包办
```

## 九、可观测性与可靠性工程化

### 9.1 监控 ≠ 可观测性

```text
监控 (Monitoring):
  预先知道"会出什么问题", 预先定义好指标和告警, 去"检查已知问题"。

可观测性 (Observability):
  能在"没预想到的问题"发生时, 通过系统的外部输出(指标、日志、链路)
  去探索和理解"到底发生了什么", 而不用改代码重新发版。

三大支柱:
  Metrics 指标  — 聚合数值, 擅长告警和趋势 (Prometheus)
  Logs 日志     — 离散事件详情, 擅长排查具体问题 (ELK/Loki)
  Traces 链路   — 单次请求跨服务路径, 擅长微服务依赖与瓶颈 (Jaeger/Tempo)

现代趋势: 统一标签/关联 ID, 把三者打通。
```

### 9.2 从"监控"到"AIOps"的演进（衔接）

SRE 沉淀的大量 SLI、告警、时间线、复盘数据，正是 AIOps 的数据基础：

```text
SRE 提供:
  - 结构化的指标/日志/链路
  - 标注好的事故时间线和根因(复盘文档)
  - SLO 和错误预算

AIOps 增强:
  - 异常检测: 不依赖静态阈值, 自动识别指标异常
  - 告警收敛/降噪: 把告警风暴聚合成少数根因事件
  - 根因辅助分析: LLM 结合 trace/log/变更记录给出可能根因
  - 自动生成复盘初稿
  - 容量预测: 基于时序预测资源耗尽时间
详见 [12_AIOps](../12_AIOps/index.md) 章节。
```

### 9.3 可靠性工程的平台化

```text
SRE 成熟度提升路径:
  L1 手工运维   → 人盯、手工操作、靠经验
  L2 脚本化     → 常用操作写成脚本
  L3 自动化     → CI/CD、自动扩缩容、自动告警
  L4 平台化     → 自助发布平台、SLO 平台、统一可观测、自助扩容
  L5 智能化/自愈 → 自动止损、AIOps 根因、自动容量调度

SRE 的终极形态: 把可靠性能力做成"平台",
让业务研发自助、安全地发布和运维自己的服务, SRE 退到平台和标准层。
```

## 十、SRE 落地路线图（给中小团队的现实建议）

很多团队读了 Google SRE Book 觉得"我们没那么多人手，学不了"。其实 SRE 可以分阶段、低成本落地。

### 10.1 分阶段落地

```text
阶段 0: 打基础 (1~2 个月)
  ✅ 先有基础监控(四大黄金信号)和日志, 能发现问题
  ✅ 明确核心服务和负责人
  ✅ 建立最简单的 oncall 和告警通道
  不做: 不要一上来就追求完美 SLO 体系

阶段 1: 定义可靠性 (1~2 个月)
  ✅ 梳理 2~3 个最核心的用户旅程
  ✅ 为它们定义 SLI, 先采集真实数据
  ✅ 基于实测数据, 定出第一版务实的 SLO
  ✅ 做一个 SLO/错误预算看板(哪怕很简陋)

阶段 2: 建立事故流程 (2~3 个月)
  ✅ 定义事故分级和响应角色
  ✅ 推行无责复盘模板, 行动项跟踪到关闭
  ✅ 把告警从"阈值轰炸"改成"症状/SLO 驱动 + 分级"

阶段 3: 错误预算机制运转 (持续)
  ✅ 明确预算耗尽的策略并真正执行(冻结高风险发布)
  ✅ 用多窗口燃尽率告警
  ✅ 让开发和运维看同一个数字做决策

阶段 4: 工程化和自动化 (长期)
  ✅ 安全发布: 灰度/金丝雀/回滚/功能开关
  ✅ 韧性: 熔断/限流/降级
  ✅ 自动化消灭 toil, 容量规划常态化
  ✅ 成熟后引入混沌工程和 AIOps
```

### 10.2 小团队的务实取舍

```text
✅ 先做"高性价比"的:
   - 核心链路的 SLI/SLO (3~5 个就够, 别贪多)
   - 错误率/延迟的症状告警 (砍掉 80% 的噪音告警)
   - 一份能用的复盘模板 + 行动项跟踪
   - 快速回滚能力 (这是性价比最高的稳定性投资)

❌ 不要过早做的:
   - 给几十个服务都定精细 SLO
   - 追求五个九 (先搞清用户到底需不需要)
   - 复杂的 SRE 平台 (先脚本, 有规模了再平台化)
   - 形式化的繁琐流程 (SRE 是减负, 不是增加会议和文档)
```

### 10.3 SRE 工程师的能力模型

| 能力域 | 具体要求 |
|:---|:---|
| **系统与工程基础** | Linux、网络、分布式系统原理、数据结构、至少一门系统语言（Go/Python） |
| **云原生技术栈** | K8s、容器、服务网格、CI/CD、IaC（Terraform/Ansible） |
| **可观测性** | Prometheus/指标、日志系统、分布式追踪、SLO 工具链 |
| **可靠性方法论** | SLI/SLO/SLA、错误预算、事故管理、无责复盘、容量规划 |
| **韧性与性能** | 熔断/限流/降级、压测、性能调优、混沌工程 |
| **自动化/平台开发** | 把运维流程做成工具和平台，消除 toil |
| **软技能** | 事故指挥、跨团队沟通、无责文化推动、数据驱动决策、写清晰的复盘 |
| **业务理解** | 理解关键用户旅程和业务影响，能把技术指标翻译成业务价值 |

## 十一、反模式 Top 15

| # | 反模式 | 问题 | 正确做法 |
|:---|:---|:---|:---|
| 1 | 把 SRE 当成"改名的运维"，继续干纯手工运维 | 没有工程化，没有 SLO，只是换了个抬头 | 至少 50% 时间做自动化和系统改进 |
| 2 | 追求 100% 可用 | 成本无限、迭代停滞，用户也无感 | 基于业务定务实 SLO，拥抱错误预算 |
| 3 | 只定 SLO，不定义预算耗尽策略 | SLO 是墙上的数字 | 预算耗尽真的冻结高风险发布 |
| 4 | SLA = SLO，甚至更高 | 动不动违约赔偿，没有缓冲 | SLA 比 SLO 宽松，留缓冲带 |
| 5 | 用平均延迟衡量服务 | 掩盖长尾，部分用户体验极差却无感 | 看 P95/P99/P999 分位数 |
| 6 | 告警阈值风暴，所有告警都 @全员 | 告警疲劳，真正的事故被淹没 | 症状告警 page，原因告警工单；分级 |
| 7 | 复盘追责、处罚当事人 | 人隐瞒问题，同类故障反复 | 无责复盘，改系统而非怪人 |
| 8 | 行动项写成"下次小心" | 没有可执行的系统改进 | 行动项具体、有负责人、有期限、改系统 |
| 9 | 复盘文档写完就归档 | 教训不落地 | 行动项跟踪到关闭，定期回顾 |
| 10 | 事故时一堆人一起上手操作 | 混乱、没人看全局、时间线丢失 | 明确 IC/操作/通讯角色 |
| 11 | 执着于当场找根因，不先止血 | 用户长时间受影响 | 缓解优先（回滚/切流/降级），根因事后查 |
| 12 | 容量靠拍脑袋或"加到满" | 要么打爆要么浪费 | 压测定单容量 + 增长预测 + 余量 + 冗余 |
| 13 | 大促赌 HPA 自动扩容能跟上 | 扩容滞后，洪峰打挂 | 大促预扩容 + 限流降级兜底 |
| 14 | 只监控 CPU/内存等资源指标 | 资源没满但用户已经失败 | 黄金信号/RED，从用户体验出发 |
| 15 | 不做回滚演练，或回滚比上线慢 | 真出事时回滚失败，雪上加霜 | 回滚方案每次验证，回滚必须比上线快 |

## 十二、速查表

### 12.1 核心概念速查

```text
SLI   可测量的可靠性指标 (好事件/总事件)
SLO   内部可靠性目标 (SLI 要达到的值)
SLA   对外合同承诺 (比 SLO 宽松, 违约赔偿)
错误预算 = 1 - SLO (可用于冒险/变更的额度)
Burn Rate 预算燃烧速度 (1=正常, >14.4=立即 page)
Toil  手工重复可自动化的运维劳动 (上限 50%)
四大黄金信号: 延迟 / 流量 / 错误 / 饱和度
RED: Rate / Errors / Duration (服务视角)
USE: Utilization / Saturation / Errors (资源视角)
无责复盘: 找系统性原因, 不追责个人
三板斧: 熔断 / 限流 / 降级
缓解优先: 先止血(回滚/切流), 根因事后查
```

### 12.2 SLO 落地检查单

```text
□ 已识别 3~5 个核心用户旅程
□ 每个旅程有反映用户体验的 SLI (不是只看 CPU)
□ 延迟用分位数 (P95/P99), 成功失败分开统计
□ 先采 2~4 周真实数据, 再定 SLO (不拍脑袋)
□ SLO 用滚动 28/30 天窗口 (不用自然月)
□ SLA 比 SLO 宽松, 有缓冲
□ 有实时 SLO 看板和错误预算燃尽图
□ 定义了预算耗尽策略 (冻结发布) 且团队认可会执行
□ 配了多窗口多燃尽率告警
□ SLO 每季度回顾调整
```

### 12.3 事故响应检查单

```text
发现时:
□ 有人立即认领并判断级别
□ 指定 IC (指挥), 操作者和指挥者分离
□ 建立时间线记录 (谁/几点/做了什么)
处置中:
□ 缓解优先: 先回滚/切流/降级止血
□ 5~15 分钟无进展果断升级
□ 固定节奏对内对外同步
□ 冻结其他非必要变更
恢复后:
□ 确认 SLO 回升、用户真正恢复
□ 48 小时内开无责复盘
□ 行动项有负责人/期限, 跟踪到关闭
□ 行动项改系统, 不是"下次注意"
```

### 12.4 告警设计检查单

```text
□ page 告警都是"用户受影响"的症状, 且可操作
□ 内部组件异常只建工单, 不 page
□ 基于 SLO 燃尽率而非零散阈值
□ 双窗口确认, 防抖动误报
□ 告警分 P1~P4, 响应预期明确
□ 长期无人处理的告警已被删除或降级
□ 告警里附带排障链接/仪表盘/Runbook
```

### 12.5 容量规划速查

```text
□ 有单实例安全容量基准 (压到"快违反 SLO", 不是压到崩)
□ 有业务增长和大促峰值预测
□ 实例数 = 峰值需求 / 单容量 × 余量(1.2~1.4) + N+1/N+2 冗余
□ HPA 用 SLO 相关指标, minReplicas 兜底
□ 大促预扩容, 不赌自动伸缩
□ 容量到顶有熔断/限流/降级兜底
□ 有状态层(DB)的容量天花板单独评估
□ 定期浸泡测试发现内存/连接泄漏
```

### 12.6 可用性等级速记

```text
99%    每月可停 7h12m
99.5%  每月可停 3h36m
99.9%  每月可停 43m12s   ← 常见目标
99.99% 每月可停 4m19s
99.999%每月可停 26s      ← 成本指数级上升
多一个九 ≈ 成本翻数倍, 按业务需要选, 不要盲目追求。
```
