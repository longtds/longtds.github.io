# FinOps 云成本优化实战（自建 IDC + 公有云 + 混合云）

> 云花的钱越来越多，但钱花在哪了、花的值不值、怎么省——大部分团队答不上来。FinOps 不是"云财务"三个字，是一套把技术、财务、业务拉到同一张桌子上的方法论。本文从自建 IDC 折旧核算、公有云 RI/Spot/预留、混合云成本决策、到组织协同、工具链和 KPI，一站讲清怎么把云成本管起来。

---

## 一、FinOps 是什么？为什么需要

### 1.1 从 CAPEX 到 OPEX

```text
传统 IDC 模式:
  买服务器 = 资本支出 (CAPEX)
  一次花几百万, 分 3-5 年折旧
  好处: 量大摊薄, 越用越便宜
  坏处: 不灵活, 买多了浪费, 买少了不够

公有云模式:
  用多少付多少 = 运营支出 (OPEX)
  按需付费, 弹性伸缩
  好处: 灵活, 不用提前规划
  坏处: 一不小心账单爆炸, 月底才知道花了多少

混合云模式:
  一部分自建 + 一部分公有云
  稳态业务放自建 (便宜), 峰谷业务放公有云 (弹性)
  挑战: 两边成本口径不一样, 算不清楚
```

### 1.2 FinOps 的定义

```text
FinOps = Financial Operations (云财务运营)
  也叫 Cloud Financial Management / Cloud Cost Management

核心思想:
  把云成本的决策权下放到业务团队
  让每个团队对自己的云花费负责
  技术 + 财务 + 业务 三方协同, 在速度/成本/质量之间找平衡

三个关键词:
  Inform (可见): 钱花在哪了, 谁花的, 花的值不值
  Optimize (优化): 哪里可以省, 怎么省, 省了多少
  Operate (运营): 持续治理, 成本意识融入日常
```

### 1.3 FinOps 成熟度模型

| 阶段 | 特征 | 典型表现 |
|:---|:---|:---|
| **第 1 阶段: Crawl (爬行)** | 只有财务看账单，技术团队不管成本 | 月底财务报个数，大家说"知道了" |
| **第 2 阶段: Walk (行走)** | 有成本可视化，团队有分摊，开始做优化 | 有成本看板，季度做优化项目 |
| **第 3 阶段: Run (奔跑)** | 成本融入日常决策，团队有预算和问责 | CI/CD 里有成本检查，预估成本自动算 |

### 1.4 组织架构

```text
FinOps 不是一个人的事，需要三个角色协同：

  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
  │  技术/工程    │    │  财务/采购    │    │  业务/产品    │
  │  懂技术实现    │    │  懂预算核算    │    │  懂业务价值    │
  └──────┬──────┘    └──────┬──────┘    └──────┬──────┘
         │                  │                  │
         └────────┬─────────┘                  │
                  ▼                            │
          ┌───────────────┐                    │
          │ FinOps 团队    │ ◄──────────────────┘
          │ (中台/枢纽)    │
          └───────────────┘

FinOps 团队职责:
  - 建成本看板, 做数据可视化
  - 制定标签规范和分摊规则
  - 推动优化项目, 跟踪节省金额
  - 预算管理和预测
  - 和云厂商谈折扣/合同
```

## 二、自建 IDC 成本核算

### 2.1 自建成本构成

```text
自建 IDC 的 TCO (Total Cost of Ownership, 总拥有成本):

  ┌─────────────────────────────────────────────┐
  │                TCO 构成                      │
  ├─────────────────────────────────────────────┤
  │  基础设施成本 (一次性 + 持续)                 │
  │  ├─ 机房建设 / 机柜租金                       │
  │  ├─ 电力 (市电 + UPS + 发电机)                │
  │  ├─ 制冷 (空调)                              │
  │  └─ 网络 (带宽 + 设备)                        │
  ├─────────────────────────────────────────────┤
  │  硬件成本 (CAPEX, 需折旧)                    │
  │  ├─ 服务器 (计算节点)                         │
  │  ├─ 存储 (磁盘阵列 / 分布式存储)              │
  │  ├─ 网络设备 (交换机 / 路由器 / 防火墙)       │
  │  └─ 其他 (负载均衡 / 安全设备)                │
  ├─────────────────────────────────────────────┤
  │  软件成本                                    │
  │  ├─ 操作系统许可                              │
  │  ├─ 商业软件 / 数据库许可                     │
  │  └─ 运维管理平台                              │
  ├─────────────────────────────────────────────┤
  │  人力成本 (OPEX)                             │
  │  └─ 运维 / 网络 / 系统 / DBA 团队             │
  └─────────────────────────────────────────────┘
```

### 2.2 折旧计算

硬件是一次性购买但要用 3-5 年，所以要算**折旧**，把成本平摊到每个月。

```text
直线折旧法 (最常用):

  月折旧额 = (硬件采购成本 - 残值) / (使用年限 × 12)

  例:
    一台服务器 5 万, 用 5 年, 残值 5%
    月折旧 = (50000 - 2500) / 60 = 792 元/月
```

**常见折旧年限参考**：

| 设备类型 | 推荐折旧年限 | 残值率 |
|:---|:---|:---|
| 服务器 | 3-5 年 | 3-5% |
| 存储设备 | 5 年 | 3-5% |
| 网络设备 | 5-7 年 | 3% |
| 机房基础设施 | 10-15 年 | 5% |

> **注意**：财务上的折旧年限和技术上的使用年限可能不一样。财务可能按 5 年折，但技术上服务器跑 7 年也能用——多出来的 2 年就是"纯赚"。

### 2.3 单机位 / 单 CPU / 单 GB 成本

有了总成本，要换算成**单位成本**，才能和公有云比价。

```text
计算思路:
  总成本 = 硬件折旧 + 机房租金 + 电力 + 网络 + 软件 + 人力

  单机柜月成本 = 总成本 / 机柜数 / 12
  单服务器月成本 = 总成本 / 服务器数 / 12
  单 vCPU 月成本 = 单服务器月成本 / (CPU 核数 × 超线程系数 × 利用率)
  单 GB 内存月成本 = 单服务器月成本 / 内存容量
  单 TB 存储月成本 = 存储总折旧 / 总容量 / 12
```

**一个具体例子（2026 年价格估算）**：

```text
2 路 64 核 (128 vCPU) / 512GB 内存 / 2×960G SSD 服务器:
  采购价: 约 8 万元
  5 年折旧 (5% 残值): 80000 × 0.95 / 60 ≈ 1267 元/月

加上机房电力/带宽/人力分摊 (约等于硬件成本的 50%-100%):
  全成本 ≈ 1267 × 1.5 = 1900 元/月 (保守估计)

换算:
  单 vCPU 月成本 ≈ 1900 / 128 ≈ 15 元
  单 GB 内存月成本 ≈ 1900 / 512 ≈ 3.7 元

对比公有云按需 (8 核 16G 为例):
  公有云按需 ≈ 800-1500 元/月
  按同样规格: 自建全成本 ≈ 8×15 + 16×3.7 ≈ 180 元/月
  → 自建成本是公有云按需的 1/4 ~ 1/8
  → 但公有云预留实例 / 包年包月折扣后差距缩小到 1/2 ~ 1/4
```

### 2.4 自建 vs 公有云决策

| 对比维度 | 自建 IDC | 公有云 |
|:---|:---|:---|
| 单位成本 (稳态) | 低（1/4 ~ 1/2 公有云） | 高 |
| 弹性 | 差（采购周期几周到几个月） | 好（分钟级） |
| 前置投入 | 高（一次性几百万） | 低（零首付） |
| 运维复杂度 | 高（机房/网络/硬件全管） | 低（IaaS 厂商管） |
| 计费模式 | CAPEX 折旧 | OPEX 按量 |
| 适用场景 | 稳态业务、长期运行 | 波峰波谷、快速迭代、新业务 |
| 数据安全 | 完全可控 | 合规要看具体场景 |
| 地理覆盖 | 有限（几个机房） | 全球几十个区域 |

**决策公式**：

```text
业务负载稳定率 > 70% + 预计运行 > 3 年 → 自建更划算
业务负载波动大 + 峰值持续时间短 → 公有云更划算

混合云平衡点:
  稳态基础负载放自建 (保底)
  峰值/弹性/新业务放公有云 (按需)
  自建利用率维持在 60-70% (留余量给故障和增长)
```

## 三、公有云成本分析方法

### 3.1 账单的构成

```text
公有云账单的主要项:

  计算 (Compute):
    ECS/EC2 实例、裸金属、弹性伸缩
    → 通常占 50-70%, 成本大头

  存储 (Storage):
    云盘、对象存储、文件存储、归档存储
    → 通常占 15-25%

  网络 (Networking):
    带宽、流量费、CDN、负载均衡、NAT 网关
    → 通常占 5-15%
    ※ 出方向流量费容易被忽视

  数据库 & 中间件 (PaaS):
    RDS、Redis、Kafka、Elasticsearch
    → 占比逐渐升高 (PaaS 化趋势)

  其他:
    安全产品、CDN、日志服务、监控
```

### 3.2 成本标签体系（最重要的一步）

```text
没有标签的成本 = 一笔糊涂账
不知道谁花的 → 不知道找谁优化 → 优化不了

标签设计原则:
  ✅ 标签是强制的 (创建资源必须打, 不打不让建)
  ✅ 标签有规范 (命名统一, 值可选枚举)
  ✅ 标签有审批 (新增标签要走流程)
  ❌ 标签是可选的
  ❌ 标签命名随意 (有的叫 team, 有的叫 Team, 有的叫 团队)
  ❌ 标签值乱写 (同个团队 5 种写法)
```

**推荐标签体系**：

| 标签 Key | 说明 | 示例值 | 必填 |
|:---|:---|:---|:---|
| `team` | 归属团队 | `order-team` / `payment-team` | ✅ |
| `project` | 项目/产品 | `mall` / `data-platform` | ✅ |
| `env` | 环境 | `prod` / `staging` / `test` / `dev` | ✅ |
| `service` | 服务名 | `order-service` | ⭕ |
| `owner` | 负责人邮箱 | `zhangsan@example.com` | ⭕ |
| `cost-center` | 成本中心 | `cc-10023` | 财务需要 |
| `bu` | 业务单元 | `e-commerce` / `enterprise` | ⭕ |

**落地手段**：

```text
1. 标签策略 (Tag Policy): 云厂商原生功能, 不符合标签规则不让创建资源
2. IaC 强制: Terraform / 云模板里 tag 是必填字段
3. 标签检查流水线: CI/CD 里检查 Terraform 有没有按规范打标签
4. 定时巡检: 每天扫一遍没打标签的资源, 自动通知负责人
5. 无标签资源 = 共享成本池: 真找不到归属的, 按比例分摊
```

### 3.3 成本分摊 (Showback / Chargeback)

```text
Showback: 把成本展示给团队看 (不真扣钱)
  → 让团队知道自己花了多少, 引起重视

Chargeback: 真正从团队预算里扣 (内部结算)
  → 直接挂钩预算, 驱动力最强
  → 但需要财务制度配合, 实施难度大

阶段建议:
  先做 Showback (可视化 + 排名)
  → 大家有了成本意识
  → 再上 Chargeback (内部计费)
```

**分摊规则**：

| 资源类型 | 分摊方式 |
|:---|:---|
| 有明确标签的计算/存储 | 直接归到对应团队 |
| 共享资源 (数据库/中间件) | 按使用量 / 连接数 / 容量 分摊 |
| 平台资源 (K8s 集群) | 按 namespace 配额 / 实际使用 CPU & 内存 分摊 |
| 网络出口流量 | 按各服务流量比例分摊 |
| 公共服务 (监控/日志/安全) | 按人头均摊 / 按资源量比例分 |
| 无归属资源 | 成立"无主成本池"，限期认领，过期按比例分 |

### 3.4 成本分析的维度

拿到账单数据后，要从多个维度切片分析：

```text
成本分析维度:

  时间维度:
    ├─ 月环比 (这个月 vs 上个月)
    ├─ 年同比 (这个月 vs 去年同月)
    └─ 日粒度 (看周末/工作日差异, 找优化空间)

  组织维度:
    ├─ 按 BU / 部门
    ├─ 按团队
    └─ 按项目

  技术维度:
    ├─ 按服务 (ECS / RDS / OSS / CDN)
    ├─ 按实例规格 (大规格占比多少)
    ├─ 按地域 (哪个区域花得多)
    └─ 按付费方式 (按需/包年包月/预留)

  利用率维度:
    ├─ CPU 利用率分布 (多少实例 CPU < 10%)
    ├─ 内存利用率分布
    └─ 存储使用率 (多少磁盘用了不到 20%)
```

## 四、公有云优化实战

### 4.1 计算优化（最大头）

#### 4.1.1 选择合适的付费方式

| 付费方式 | 折扣 | 适用场景 | 灵活度 |
|:---|:---|:---|:---|
| 按需 (On-Demand) | 原价 | 短期 / 测试 / 不确定负载 | 最高 |
| 包年包月 / 预留实例 (RI) | 30-60% off | 稳定运行的长期服务 | 低 |
| Savings Plans | 30-60% off | 承诺一定使用量，更灵活 | 中 |
| 竞价 / Spot 实例 | 60-90% off | 无状态、可中断、批处理任务 | 最低（随时可能被回收） |

**RI 覆盖率目标**：

```text
RI 覆盖率 = 有预留的实例 / 总运行实例

  刚开始做: 目标 40-50%
  做了一年: 目标 70-80%
  极致优化: 目标 85%+

注意: 不是覆盖率越高越好。
  100% 覆盖 = 全买了预留 = 没有弹性
  预留 80% + 按需 20% 是比较健康的比例
```

#### 4.1.2 实例规格优化（Right Sizing）

```text
问题: 很多实例规格买大了, 实际用不到

  一个 16 核 32G 的实例, CPU 平均 5%, 内存用了 4G
  → 降到 4 核 8G, 成本直接砍 3/4

优化步骤:
  1. 看过去 7-14 天的 CPU / 内存 / 磁盘 IO 使用率
  2. 取 P95 峰值, 留 30-50% 余量
  3. 找到最接近的实例规格
  4. 先降一个级别观察, 没问题再继续降

利用率参考表:
  CPU 平均 < 10%      → 至少降 2 个规格
  CPU 平均 10-30%     → 降 1 个规格
  CPU 平均 30-60%     → 合适
  CPU 平均 > 80%      → 考虑升级 (或者横向扩容)
```

#### 4.1.3 Spot / 竞价实例

```text
Spot 实例 = 闲置的计算资源, 低价卖, 但随时可能被回收

适用:
  ✅ 无状态服务 (Web / API, 多副本部署)
  ✅ 批处理 / CI/CD 构建 / 大数据计算
  ✅ 测试环境 / 开发环境
  ✅ 弹性伸缩组里的扩容节点

不适用:
  ❌ 数据库 / 有状态服务
  ❌ 不能中断的任务
  ❌ 单实例服务 (挂了就不可用)

最佳实践:
  1. 多实例类型 + 多可用区 (分散被回收的风险)
  2. 优雅关闭: 收到回收通知 (提前 2 分钟) 时, 主动下线
  3. 混合使用: 一部分按需 (保底) + 一部分 Spot (省钱)
```

#### 4.1.4 自动扩缩容 (HPA / ASG)

```text
不用的资源就是最大的浪费。

  上班时间 10 个实例, 下班了还 10 个?
  半夜流量只有 10%, 用 2 个就够了 → 省 80%

实现:
  K8s: HPA (Horizontal Pod Autoscaler) + Cluster Autoscaler
  云厂商: ASG (Auto Scaling Group) / ESS

  指标: CPU / 内存 / 自定义指标 (QPS / 队列长度)
  最小副本数: 业务最低需要多少
  最大副本数: 峰值需要多少
  冷却时间: 避免频繁扩缩

成本节省比例:
  有明显峰谷的业务: 30-60%
  24 小时平稳的: 10-20% (还是有优化空间)
```

### 4.2 存储优化

#### 4.2.1 存储类型选型

| 存储类型 | 价格 (相对) | 适用场景 |
|:---|:---|:---|
| 本地盘 / 高性能云盘 | 最贵 (10×) | 数据库、低延迟要求高的 |
| 通用 SSD / 高效云盘 | 高 (3×) | 虚拟机系统盘、普通业务 |
| 大容量 HDD / 冷存储 | 中 (1×) | 日志、备份、归档前 |
| 对象存储标准 | 中低 | 图片、视频、静态文件 |
| 对象存储低频 | 低 (1/3) | 访问频率低的文件 |
| 对象存储归档 / 冷归档 | 极低 (1/10 ~ 1/30) | 长期备份、合规归档 |

#### 4.2.2 生命周期管理

```text
对象存储的生命周期策略 (Lifecycle Policy):
  创建后 30 天内 → 标准存储 (经常访问)
  30 天后     → 低频存储 (访问少了)
  90 天后     → 归档存储 (几乎不访问)
  3 年后      → 删除 (不需要了)

  成本: 标准(100%) → 低频(30%) → 归档(5%) → 删除(0)

适用场景:
  - 日志 (ELK / S3 日志)
  - 备份数据
  - 用户上传的图片/视频
  - 合规归档数据
```

#### 4.2.3 常见浪费

| 浪费场景 | 优化手段 | 节省幅度 |
|:---|:---|:---|
| 云盘用了 10% 不到 | 缩容 + 检查是什么占了空间 | 50-80% |
| 已经删除的实例云盘没删 | 定期扫描孤立资源并清理 | - |
| 对象存储旧版本/未完成上传 | 生命周期 + 过期清理 | - |
| 快照太多太旧 | 快照保留策略 (只留最近 N 个) | - |
| 日志存了就不删 | 日志分级 + 热温冷分层 | 50-90% |

### 4.3 网络优化

#### 4.3.1 流量费优化

```text
网络流量费容易被忽视, 但可能是个大数字:

  出方向流量 (互联网 → 公网): 最贵
  跨地域流量 (region 间): 中
  同地域内 (同 VPC): 免费
  入方向流量: 免费

优化手段:
  1. CDN 缓存静态资源 (图片/JS/CSS/视频)
     → 减少源站出口流量
  2. 同地域内调用走内网 (不要走公网)
  3. 跨地域数据传输用专线 (比互联网流量便宜)
  4. 数据压缩 (gzip / br)
  5. 图片/视频压缩 + 合适的格式 (WebP / AVIF)
  6. 大文件用对象存储 + CDN, 不用经过服务器
```

#### 4.3.2 NAT 网关费用

```text
NAT 网关 = 私有网络访问公网的出口
  费用: 实例费 + 流量费
  坑: 很多小流量场景, 实例费比流量费还贵

优化:
  1. 能用公网 IP 的就不用 NAT (适合少量实例)
  2. 批量服务走 NAT, 零散的用 EIP
  3. 不需要出公网的服务, 直接不给公网访问权限
```

### 4.4 数据库优化

| 优化项 | 方法 | 节省 |
|:---|:---|:---|
| 规格降配 | 看 CPU/连接数使用率，合理降配 | 20-50% |
| 读写分离 | 读多写少，加只读节点代替升主库规格 | 按需 |
| 非核心数据搬出去 | 日志/历史数据迁到对象存储/ES | 30-70% |
| 包年包月 | 稳定运行的库买预留 | 30-50% |
| 自建 vs 托管 | 自己部署在 ECS 上 vs 用 RDS | 省 30-60% 但运维成本高 |
| 冷数据归档 | 历史数据定期归档到对象存储 | - |

### 4.5 优化效果预估表

| 优化项 | 典型节省比例 | 实施难度 | 见效速度 |
|:---|:---|:---|:---|
| 清理未使用资源 | 5-20% | ★ | 立刻 |
| 标签体系 + 成本可视化 | （基础工作） | ★★ | 1-2 月见效 |
| 包年包月/RI 购买 | 20-40% | ★ | 立刻 |
| 实例规格降配 | 15-30% | ★★ | 1 周 |
| Spot / 竞价实例 | 40-80% | ★★★ | 1 周 |
| 自动扩缩容 | 10-50% | ★★★ | 2 周 |
| 存储分层 + 生命周期 | 30-70%（存储部分） | ★★ | 立即可配置 |
| 微优化（网络/快照/日志） | 5-15% | ★ | 立刻 |
| 架构优化（缓存/异步等） | 20-60% | ★★★★★ | 长期 |

> **低悬果实优先**：先做难度小、见效快的。清理僵尸资源 + 买 RI + 降配，这三件事做完，通常就能省 30-50%。

## 五、K8s 集群成本优化

### 5.1 K8s 资源分配与实际使用的差距

```text
K8s 里最常见的浪费:
  资源请求 (Requests) 远大于实际使用

  Pod 申请: 4 核 CPU + 8G 内存
  实际使用: 0.5 核 + 2G 内存
  → 浪费: 87.5% 的 CPU, 75% 的内存

  集群有 100 个节点, 一半是浪费 → 50 个节点白买了
```

**为什么会这样？**

| 原因 | 说明 |
|:---|:---|
| 开发者往大了填 | 怕不够用，往多了填保险 |
| 没有资源规范 | 不知道该填多少，拍脑袋 |
| 没有检查机制 | Request 设多少就是多少，没人 review |
| 环境多 | 测试/开发环境的 request 也是按生产填 |

### 5.2 Vertical Pod Autoscaler (VPA)

VPA 自动分析 Pod 的 CPU/内存使用率，推荐合理的 requests：

```text
VPA 工作原理:
  1. 收集历史资源使用数据
  2. 分析 P95 / P99 峰值
  3. 推荐合适的 CPU / memory requests

模式:
  - Off: 只推荐不调整 (推荐模式, 最安全)
  - Initial: 只在 Pod 创建时设置一次
  - Recreate: 需要改就重启 Pod
  - Auto: 自动调整 (生产慎用)

建议: 先用 Recommendation 模式看推荐值
      → 人工 review 后再调整
      → 确认没问题了再考虑自动模式
```

### 5.3 Cluster Autoscaler + 节点伸缩

```text
Cluster Autoscaler (CA):
  Pod 调度不进去 → 自动加节点
  节点利用率低 + Pod 能调度走 → 自动缩节点

配合 HPA:
  HPA 扩 Pod → Pod 调度不了 → CA 扩节点
  HPA 缩 Pod → 节点空出来 → CA 缩节点
```

### 5.4 命名空间级配额和成本归属

```text
K8s 成本怎么分摊到团队?

方案: 按 Namespace 分 (每个团队一个 namespace)

  每个 namespace 设置 ResourceQuota:
    - limits.cpu / limits.memory
    - requests.cpu / requests.memory
    - 存储 / PVC 数量

  成本分摊:
    按 namespace 的实际 CPU / 内存使用量比例分摊
    或者按 request 比例分摊 (更简单, 但可能有浪费)

工具:
  - Kubecost / OpenCost (开源 K8s 成本分析)
  - 云厂商容器服务自带的成本分析
```

### 5.5 其他 K8s 优化

| 优化项 | 方法 |
|:---|:---|
| **非生产环境缩容** | 测试/开发环境下班了/周末自动缩到 0 |
| **DaemonSet 控制** | 每个节点都跑的 DaemonSet 资源加起来可能很多 |
| **Garbage Collection** | 已完成的 Job/未使用的镜像/旧的 ReplicaSet 定期清理 |
| **超卖** | Limits > Requests，提高资源利用率（有风险，需要监控） |
| **节点池分层** | 不同类型节点池 (通用/计算型/内存型)，Pod 按需调度 |
| **Spot 节点池** | 弹性节点用 Spot，省 50-80% |

## 六、混合云成本管理

### 6.1 混合云的成本挑战

```text
自建 + 公有云 = 两边成本口径不一样, 很难比较

  自建: 折旧 + 电费 + 机房 + 人力 → 按年/按月
  公有云: 按需 / 预留 / 竞价 → 按小时甚至按秒

问题:
  1. 自建成本怎么和公有云比? (口径不同)
  2. 什么业务放哪边? (怎么决策)
  3. 跨云数据传输费? (数据在两边流动有成本)
  4. 人员成本怎么分? (同一拨运维管两边)
```

### 6.2 统一成本口径

要比较就要先**统一单位**。

```text
统一成本单位: 元 / vCPU / 月, 元 / GB 内存 / 月, 元 / TB / 月

  自建侧:
    把所有成本 (折旧 + 电力 + 机房 + 网络 + 人力) 平摊到:
      - 每 vCPU 每月成本
      - 每 GB 内存每月成本
      - 每 TB 存储每月成本
      - 每 Mbps 带宽每月成本

  公有云侧:
    同样换算成这些单位
    (按预留实例价格算, 不要按按需价格比, 不公平)

  比较:
    自建单 vCPU 月成本 vs 公有云预留 vCPU 月成本
    → 知道自建的成本优势有多大
    → 决策什么负载放哪边
```

### 6.3 工作负载分配决策

```text
什么放自建? 什么放公有云?

  ┌─────────────────────────────────────────────────┐
  │                  自建 IDC                        │
  │  ✅ 稳态核心业务 (稳定运行, 负载波动小)            │
  │  ✅ 数据库 / 中间件 (有状态, IO 密集)              │
  │  ✅ 高安全 / 合规要求的业务                        │
  │  ✅ 大数据 / 训练任务 (数据量大, 流量费贵)          │
  │  ✅ 长期运行, 确定性高的服务                       │
  └─────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────┐
  │                  公有云                          │
  │  ✅ 新业务 / 试点项目 (不知道需要多少资源)         │
  │  ✅ 峰值流量 / 大促弹性 (一年就那么几天)           │
  │  ✅ CI/CD / 构建 / 批处理 (用完就删)              │
  │  ✅ 测试 / 开发 / 演示环境 (不用就停)              │
  │  ✅ 全球化业务 (需要多地域部署)                    │
  │  ✅ 灾备 (平时不用, 故障时拉起)                    │
  └─────────────────────────────────────────────────┘

  灰色地带: 负载 70% 时间稳定, 30% 波动
    → 基础负载放自建 (保底)
    → 弹性部分放公有云 (云上云下联动弹性)
```

### 6.4 混合云成本优化的核心：利用率

```text
自建 IDC 的成本优化核心 = 提高资源利用率

  利用率 30% → 50%:
    相当于同样的硬件, 多承载了 67% 的业务
    或者说单位业务成本下降了 40%

怎么提高利用率:
  1. 资源整合: 把小负载合并, 减少碎片
  2. 虚拟化/容器化: 提高单台机器的业务密度
  3. 超卖: 在安全范围内适度超卖
  4. 弹性调度: 业务忙时从云上借资源, 不忙时还回去
  5. 资源回收: 定期清理不用的虚拟机/容器

利用率目标:
  测试环境: 可以高一些 (60-70%)
  生产环境: 40-60% (留余量给故障/峰值)
  整体均值: 50% 左右是比较健康的水平
  (再高就接近饱和了, 风险大)
```

### 7.2 自建轻量成本看板

小团队/创业公司不用一上来就买商业工具，用云厂商的 API + 简单的脚本就能做基础版。

```python
# 简化版: 拉账单数据 + 标签聚合
import boto3  # 阿里云/腾讯云同理, 用各自 SDK

def get_monthly_cost_by_tag(tag_key='team'):
    """按月 + 标签维度拉成本数据"""
    client = boto3.client('ce', region_name='us-east-1')

    response = client.get_cost_and_usage(
        TimePeriod={
            'Start': '2024-08-01',
            'End': '2024-09-01'
        },
        Granularity='MONTHLY',
        Metrics=['UnblendedCost'],
        GroupBy=[
            {'Type': 'TAG', 'Key': tag_key},
            {'Type': 'DIMENSION', 'Key': 'SERVICE'},
        ]
    )
    return response

# 结果存到数据库 / 输出到 Grafana
# 每天跑一次, 做趋势图
```

## 八、运营与治理

### 8.1 FinOps 循环

```text
FinOps 不是做一次就完了, 是个持续循环:

  ┌── 信息 (Inform) ──┐
  │  看见成本         │
  │  标签 / 分摊      │
  │  报表 / 看板      │
  └────────┬──────────┘
           │
           ▼
  ┌── 优化 (Optimize) ─┐
  │  识别优化点        │
  │  实施优化项目      │
  │  衡量节省金额      │
  └────────┬──────────┘
           │
           ▼
  ┌── 运营 (Operate) ──┐
  │  预算管理          │
  │  成本问责          │
  │  流程嵌入          │
  └────────┬──────────┘
           │
           └── 回到 Inform, 继续循环
```

### 8.2 预算管理

```text
预算怎么定?

  方法 1: 历史基线 + 增长预期
    上月花了 100 万, 这个月预计增长 10% → 预算 110 万
    → 简单直接, 适合初期

  方法 2: 零基预算
    每个季度从零开始, 每个服务 justify 自己的花费
    → 更精准, 但工作量大

  方法 3: 单位成本法
    按业务量算: 每个订单成本 X 元, 预计 N 个订单 → 总预算
    → 最合理, 但需要有数据支撑

预算告警线:
  60%: 提醒 (注意进度)
  80%: 黄色预警 (需要关注)
  90%: 红色预警 (可能超预算, 准备优化)
  100%: 冻结 (停止新资源创建, 需要审批)
```

### 8.3 把成本意识融入日常

| 环节 | 成本动作 |
|:---|:---|
| **设计阶段** | 架构评审时考虑成本，预估月花费 |
| **代码提交** | IaC 变更检查资源规格是否合理 |
| **CI/CD 流水线** | 部署前显示预估月成本 |
| **资源创建** | 强制打标签，不打不让创建 |
| **日常巡检** | 每周低利用率/闲置资源自动通知 |
| **周会 / 月会** | 成本数据同步，异常讨论 |
| **季度复盘** | 成本 KPI 回顾，下季度优化计划 |

### 8.4 组织驱动

```text
怎么让团队有动力做成本优化?

  1. 可视化 + 排名
     各团队花费排名公开展示
     (荣誉感/好胜心是最便宜的驱动力)

  2. 预算挂钩
     每个团队有自己的云预算
     超了要走审批
     (预算约束最直接)

  3. 节省激励
     团队优化省下的钱, 一部分可以留作团队预算
     (省钱有好处, 才有动力)

  4. 工程文化
     成本意识 = 工程师素养的一部分
     面试 / 晋升 / 绩效里体现
     (从价值观层面认可)

  5. 工具支撑
     不用大家自己算, 工具直接告诉你哪里可以省
     一键优化 (或给优化建议)
     (降低优化的门槛)
```

## 九、常见误区与反模式

| # | 反模式 | 为什么错 | 正确做法 |
|:---|:---|:---|:---|
| 1 | 只看总账单，不分摊 | 不知道谁花的，找不到责任人 | 标签 + 分摊到团队 |

| 8 | 不做架构级优化 | 小打小闹省 10%，架构改动能省 50%+ | 定期审视架构合理性 |
| 9 | 追求 100% 利用率 | 饱和了故障风险大，扩容来不及 | 生产 50-70%，留余量 |
| 10 | 全迁公有云最便宜 | 稳态业务自建比公有云便宜多 | 混合云，按业务特点分配 |

## 十、关键指标 (KPI)

### 10.1 效率指标

| 指标 | 公式 | 目标参考 |
|:---|:---|:---|
| 单位计算成本 | 总计算成本 / vCPU 总数 | 持续降低 |
| 存储利用率 | 已用存储 / 总存储 | 60-80% |
| CPU 平均利用率 | 集群 CPU 平均使用率 | 40-60% (生产) |
| 内存平均利用率 | 集群内存平均使用率 | 50-70% |
| RI / 预留覆盖率 | 预留实例数 / 运行实例数 | 70-85% |
| Spot 使用率 | Spot 实例占比 | 越高越好（前提是业务适合） |
| 僵尸资源比例 | 未使用资源 / 总资源 | < 5% |

### 10.2 业务指标

| 指标 | 公式 | 说明 |
|:---|:---|:---|
| 云成本同比/环比 | 本月 vs 上月 / 去年同月 | 看趋势 |
| 单位业务成本 | 总成本 / 业务量 (订单/用户/流量) | 最重要的效率指标 |
| 预算达成率 | 实际花费 / 预算 | 目标 90-100% |
| 优化节省金额 | 优化项目累计节省 | 跟踪优化效果 |
| 无归属成本占比 | 没打标签 / 找不到归属的成本 / 总成本 | < 5% |
| 每工程师成本 | 总成本 / 工程师人数 | 看人均云资源使用 |

### 10.3 成熟度评估表

| 维度 | 初级 (Crawl) | 中级 (Walk) | 高级 (Run) |
|:---|:---|:---|:---|
| 成本可见性 | 财务月底给总数 | 实时看板 + 团队维度 | 全链路成本，精确到服务 |
| 标签体系 | 没有 / 随便打 | 核心标签强制 + 80% 覆盖 | 100% 覆盖 + 自动治理 |
| 优化机制 | 偶尔手动做 | 季度优化项目 + 责任人 | 自动化优化 + 持续改进 |
| 预算管理 | 没有 / 拍脑袋 | 团队预算 + 告警 | 精细化预算 + 自动控制 |
| 团队意识 | 不关心成本 | 知道自己花多少 | 成本意识融入日常决策 |
| 工具 | 云厂商自带 | 自建看板 + 利用率分析 | 商业 FinOps 平台 |
| 节省比例 | 0-10% | 10-30% | 30%+ |

## 十一、速查表

### 11.1 省钱 Checklist

```text
每月过一遍这个清单:

  计算:
    □ 未使用/停止的实例删掉了吗?
    □ 低利用率实例降配了吗?
    □ RI / 包年包月覆盖率够吗?
    □ 可以用 Spot 的用了吗?
    □ 自动扩缩容开了吗?
    □ 非生产环境下班/周末关了吗?

  存储:
    □ 孤立的云盘 (没挂实例的) 删了吗?
    □ 旧快照清理了吗?
    □ 对象存储生命周期策略配了吗?
    □ 低频/归档存储用了吗?
    □ 存储类型选对了吗 (SSD vs HDD)?

  网络:
    □ 出口流量优化了吗 (CDN/压缩)?
    □ 没用的 EIP / NAT 网关清了吗?
    □ 跨地域流量有没有不必要的?

  数据库 & PaaS:
    □ 数据库规格合理吗 (降配空间)?
    □ 只读节点用起来了吗 (不要硬升主库)?
    □ 不用的 PaaS 实例删了吗?

  K8s:
    □ Pod requests 设置合理吗 (看 VPA 推荐)?
    □ Cluster Autoscaler 工作正常吗?
    □ 测试环境下班缩容了吗?
    □ 低利用率的节点能合并吗?
```
