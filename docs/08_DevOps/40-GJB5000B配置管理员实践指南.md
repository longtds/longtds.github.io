# GJB5000B 配置管理员实践指南与最佳实践

> GJB5000B（GJB 5000B-2021《军用软件研制能力成熟度模型》）评价中，配置管理（CM，Configuration Management）是最容易被查出问题、也是证据链要求最完整的实践域之一。本文从配置管理员（CMO）的真实岗位职责出发，讲清三库、三基线、CCB、变更控制、状态纪实、配置审核、发布交付全流程，并给出可直接套用的模板、检查单和评价证据清单。
>
> 说明：GJB5000B 标准条文以正式发布文本为准，本文面向落地实施，具体实践项编号和裁剪要求请对照本单位体系文件和最新版标准。

---

## 一、GJB5000B 与配置管理的定位

### 1.1 GJB5000B 是什么

```text
GJB5000B = 国家军用标准《军用软件研制能力成熟度模型》(2021 版)
  替代 GJB5000A-2008
  用于评价承制单位的军用软件研制能力

成熟度等级 (5 级):

  5 级  卓越级    持续优化, 用数据驱动改进
  4 级  量化级    过程量化管理, 统计技术控制
  3 级  全面级    组织级标准过程, 全项目一致执行
  2 级  规范级    项目级过程已建立, 能按规矩做事
  1 级  初始级    靠人, 结果不可预测

结构变化:
  5000A: 过程域 (PA), 分通用目标/特定目标
  5000B: 实践域 (Practice Domain), 22 个,
         分为管理类 / 实施类 / 支持类 / 组织改进类四类,
         用"实践"和"工作产品"组织要求
```

**配置管理（CM）在模型中的位置**：

| 项 | 说明 |
|:---|:---|
| 所属类别 | 实施类实践域 |
| 适用等级 | **2 级（规范级）起就是必做项**，没有 CM 过不了 2 级 |
| 核心思想 | 在整个软件生命周期中，建立并维护工作产品的完整性 |
| 和谁配合 | 项目管理（PM）、质量保证（QA）、产品研制（PDM）、同行验证（PR）、供方协议管理（SAM） |

> 一句话理解：CM 管的是"**什么时间、什么东西、由谁、改成了什么样**"这四件事的完整证据链。

### 1.2 CM 的四大经典活动

无论标准版本怎么变，配置管理的内核始终是这四件事（+ 发布交付）：

```text
┌─────────────────────────────────────────────────────────┐
│                    配置管理五大活动                        │
├──────────────┬──────────────────────────────────────────┤
│ 1. 配置标识   │ 识别配置项、命名编号、确定基线              │
│ 2. 配置控制   │ 变更申请 → 评审 → 审批 → 实施 → 验证闭环    │
│ 3. 配置状态纪实│ 记录"谁在什么时候改了什么", 定期出报告      │
│ 4. 配置审核   │ 功能配置审核 FCA + 物理配置审核 PCA         │
│ 5. 发布与交付 │ 受控发布、介质交付、现场版本一致性           │
└──────────────┴──────────────────────────────────────────┘

记忆口诀: 标识 → 控制 → 纪实 → 审核 → 交付
```

### 1.3 配置管理员（CMO）在项目中的位置

```text
                 ┌──────────────────────┐
                 │  CCB 配置控制委员会     │
                 │  (主任设计师/PM/用户代表)│
                 └──────────┬───────────┘
                            │ 审批重大变更/基线
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
┌───────────────┐   ┌───────────────┐   ┌───────────────┐
│ 项目经理 PM    │   │ 配置管理员 CMO │   │ 质量保证 QA    │
│ 计划/进度/资源 │◄─►│ 库/基线/变更/   │◄─►│ 过程符合性审计 │
│               │   │ 状态纪实/审核  │   │ (独立于项目)   │
└───────────────┘   └───────┬───────┘   └───────────────┘
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
        ┌──────────┐  ┌──────────┐  ┌──────────┐
        │ 开发人员  │  │ 测试人员  │  │ 文档人员  │
        │ 检出/检入 │  │ 基线出库  │  │ 文档受控  │
        └──────────┘  └──────────┘  └──────────┘
```

**关键原则：CMO 和 QA 必须分离**。配置管理员是"建规矩并执行"的人，QA 是"检查你有没有按规矩做"的人，不能自己管自己。涉密项目里还要和"三员"体系（系统管理员、安全保密管理员、安全审计员）做好职责切分。

## 二、配置管理员的岗位职责

### 2.1 职责清单

| # | 职责 | 具体工作 | 主要产出 |
|:---|:---|:---|:---|
| 1 | 编制配置管理计划 | 项目初期明确配置项、库结构、权限、基线计划、审核安排 | 《配置管理计划》 |
| 2 | 配置标识 | 识别配置项、登记台账、执行命名编号规范 | 《配置项清单》《配置项登记表》 |
| 3 | 配置库管理 | 建库、权限分配、备份恢复、库维护 | 三库 + 权限矩阵 + 备份记录 |
| 4 | 版本管理 | 分支/标签管理、版本号规则执行 | 版本树、发布标签 |
| 5 | 基线管理 | 基线建立、发布、变更控制 | 基线发布通知、基线清单 |
| 6 | 变更控制 | 受理变更申请、组织 CCB 评审、跟踪闭环 | 变更申请单/问题报告、变更台账 |
| 7 | 配置状态纪实 | 收集变更/基线/库状态数据，定期出报告 | 《配置状态报告》（月/里程碑） |
| 8 | 配置审核 | 组织/配合 FCA、PCA，跟踪问题闭环 | 《配置审核报告》、不符合项 |
| 9 | 发布交付 | 受控发布、产品库入库、交付介质制作 | 发布记录、交付清单、回执 |
| 10 | 培训与支持 | 培训项目组成员使用配置库和流程 | 培训记录 |

### 2.2 配置管理员不该干什么（边界）

```text
CMO 做的是"管理"和"流程", 不是:
  ❌ 替开发人员写代码 / 决定技术方案
  ❌ 替 CCB 拍板批变更 (CMO 是秘书和执行, 不是决策者)
  ❌ 兼任 QA 审计自己的工作 (职责不相容)
  ❌ 一个人同时持有库的全部超级权限 (最小权限 + 三权分立)
  ❌ 后补记录、代签、把"实际怎么干"改成"应该怎么干"
     (评价时这是真实性问题, 比不规范严重得多)
```

### 2.3 能力要求

| 能力 | 说明 |
|:---|:---|
| 标准理解 | 熟悉 GJB5000B CM 实践域要求，了解 GJB 438C（软件文档）、GJB 5235 等配套标准 |
| 工具能力 | SVN/Git、缺陷/变更管理工具、文档管理系统，涉密环境下的国产工具 |
| 流程能力 | 会写计划、报告、会议纪要，能组织 CCB 评审 |
| 细致严谨 | 台账、编号、版本一致性是基本功，差一个字母都是问题 |
| 沟通推动 | CMO 没有行政权力，要靠流程和数据推动开发人员配合 |

## 三、核心概念：配置项、三库、三基线

### 3.1 配置项（CI）

**配置项**：纳入配置管理的工作产品，代码、文档、数据、环境都算。

**哪些东西必须识别为配置项？**

| 类别 | 典型配置项 |
|:---|:---|
| 需求类 | 软件研制任务书、需求规格说明（SRS）、接口需求规格说明 |
| 设计类 | 软件设计说明（SDD）、数据库设计说明、接口设计说明 |
| 代码类 | 源代码、第三方库/组件清单、构建脚本 |
| 测试类 | 测试计划、测试说明、测试用例、测试记录、测试报告 |
| 用户类 | 用户手册、操作手册、安装说明 |
| 管理类 | 项目计划、配置管理计划、质量保证计划、评审记录 |
| 产品类 | 可执行程序、固件、配置数据、标定参数、License |
| 环境类 | 编译环境版本、工具链版本、操作系统基线（复现构建必需） |

**识别时机**：越早越好。项目策划阶段先出初版清单，随阶段迭代补充。经验法则——**凡是影响"能不能复现这个产品"的东西，都要进配置管理**。

### 3.2 三库架构

军工软件配置管理的经典制度是**三库分离**：

```text
┌─────────────────────────────────────────────────────────────┐
│                       产品库 (静态库)                         │
│  内容: 通过评审/审核、正式批准发布的产品版本                    │
│  管者: 组织级配置管理部门 (不是项目自己管)                      │
│  特点: 只进经过发布流程的成品, 变更最严格, 交付从这里出          │
└──────────────────────────▲──────────────────────────────────┘
                           │ 发布/入库审批 (FCA/PCA 通过后)
┌──────────────────────────┴──────────────────────────────────┐
│                       受控库 (主库)                           │
│  内容: 通过评审的阶段产品、基线 (需求/设计/测试/代码基线)       │
│  管者: 项目配置管理员 CMO                                     │
│  特点: 检入需评审, 修改走变更流程, 全程可追溯                   │
└──────────────────────────▲──────────────────────────────────┘
                           │ 评审通过后检入 (基线化)
┌──────────────────────────┴──────────────────────────────────┐
│                       开发库 (动态库)                         │
│  内容: 开发人员正在工作的代码、草稿文档                         │
│  管者: 开发人员自己                                            │
│  特点: 自由出入, 不对外, 工作产品成熟评审后才进受控库           │
└─────────────────────────────────────────────────────────────┘

数据流向: 开发库 ──评审──► 受控库 ──发布审批──► 产品库
           ◄──变更出库──        ◄──出库发放────
```

| 库 | 别称 | 存放内容 | 读写权限 | 变更方式 |
|:---|:---|:---|:---|:---|
| 开发库 | 动态库、程序员库 | 在制品、草稿 | 开发人员自由读写 | 不需要流程 |
| 受控库 | 主库 | 阶段基线、评审通过的文档/代码 | CMO 控制写入，开发只读/受控检出 | 变更申请 + 审批 |
| 产品库 | 静态库、软件库 | 正式发布版本、交付介质 | 组织级专人管理 | 严格审批 + 重新发布 |

> **落地要点**：小项目三库可以是同一工具内的三个逻辑区域，但**权限和流程必须分开**；涉密/重点项目要求物理或逻辑隔离。最常见的扣分点是"三库名义上有，实际开发直接改受控库"。

### 3.3 三种基线

**基线（Baseline）**：经过正式评审和认可、作为后续工作起点、只能通过变更流程修改的一组配置项。

```text
三种基线 (随研制阶段递进):

  ① 功能基线 (Functional Baseline)
     时点: 系统需求/软件任务书评审通过
     内容: 软件研制任务书、系统规格说明类文档
     含义: "要做什么"被正式确认

  ② 分配基线 (Allocated Baseline)
     时点: 软件需求规格说明 SRS 评审通过
     内容: SRS、接口需求说明
     含义: 每个配置项"分到什么需求"被确认

  ③ 产品基线 (Product Baseline)
     时点: 系统测试完成, FCA/PCA 通过后
     内容: 正式源代码版本、可执行产品、设计文档最终版、
           用户文档、测试报告
     含义: "实际做成了什么"被冻结, 交付以此为准
```

**基线的三个法律级特性**：

1. **必须经过评审批准**才能建立——没有评审记录的"基线"不是基线
2. 基线一旦建立，**只能走变更流程修改**——不能直接覆盖
3. 基线必须**可追溯、可复现**——任何时候能从基线重新构建出当时的产品

### 3.4 基线与三库、阶段的对应关系

```text
阶段:       立项/论证      需求分析       设计/实现/测试         交付/定型
            │             │              │                    │
开发库:     任务书草稿 ──► SRS草稿 ──► 设计/代码/用例 ──► 问题修复
                              │              │
受控库:        功能基线 ─────► 分配基线 ─────► 代码基线/测试基线
            (任务书批准)     (SRS批准)       (各阶段评审)
                                                │
产品库:                                         └──► 产品基线 ──► 交付
                                                   (FCA/PCA后发布)
```

## 四、配置管理计划

### 4.1 什么时候写、谁批准

- **时机**：项目策划阶段，与项目计划同步编制，一般在第一次基线建立前完成审批
- **编制**：CMO 编写，项目经理审核，必要时报上级配置管理部门/顾客批准
- **更新**：项目发生重大变化（范围、组织、工具、里程碑调整）时修订，修订本身要留版本记录

### 4.2 《配置管理计划》推荐目录

```text
1. 引言
   1.1 目的和范围
   1.2 术语定义
   1.3 参考文件 (GJB5000B、组织级配置管理过程、项目合同)
2. 项目概述
   2.1 软件概况 (名称、规模、密级、研制周期)
   2.2 项目组织与职责 (CMO、CCB 成员及职责)
3. 配置管理组织
   3.1 组织机构与 CCB 组成
   3.2 配置管理员及备份人员
4. 配置标识
   4.1 配置项识别准则与配置项清单 (附)
   4.2 命名与编号规则
   4.3 版本号规则
5. 配置库管理
   5.1 三库的物理/逻辑结构
   5.2 工具及环境
   5.3 权限分配矩阵 (附)
   5.4 备份与恢复策略
6. 基线计划
   6.1 基线种类、建立时点、审批权限 (基线计划与里程碑对应表)
7. 变更控制
   7.1 变更分类 (重大/一般)
   7.2 变更流程与 CCB 议事规则
   7.3 问题报告与变更申请单格式
8. 配置状态纪实
   8.1 记录内容、报告频次、分发范围
9. 配置审核
   9.1 FCA/PCA 计划、审核组组成、检查单
10. 发布与交付
   10.1 发布流程、交付介质、验收方式
11. 工具、环境与基础设施
12. 配置管理里程碑与进度 (与项目 WBS 对应)
13. 风险与应对 (如: 涉密介质损坏、人员变动交接)
附录: 配置项清单 / 权限矩阵 / 表单模板清单
```

### 4.3 计划里最容易漏的点

| 漏项 | 后果 |
|:---|:---|
| 没写备份恢复策略和恢复演练 | 库真坏了无法恢复，评价时直接是严重不符合 |
| 权限矩阵只写角色不写具体人 | 人员变动后权限失控 |
| 基线计划与项目里程碑对不上 | 基线建立时点说不清楚 |
| 没规定第三方组件怎么管 | 交付物缺第三方软件清单，安全性审查过不了 |
| 没写外包/供方交付件如何入库 | 供方交付件游离在库外，追溯链断裂 |

## 五、配置标识与命名规范

### 5.1 配置项编号规则（示例）

```text
推荐结构: 项目代号-类型码-序号-版本号

  示例: XM03-SRS-001 V1.2
        │     │   │    │
        │     │   │    └─ 版本号
        │     │   └────── 流水号 (001 起)
        │     └────────── 文档/配置项类型码
        └──────────────── 项目代号

常用类型码 (按本单位体系调整):
  RQ   任务书/需求类
  SRS  软件需求规格说明
  SDD  软件设计说明
  IDD  接口设计说明
  SRC  源代码
  TPL  测试计划
  TPR  测试报告
  UM   用户手册
  CMP  配置管理计划
  EXE  可执行程序
  3RD  第三方组件清单
```

### 5.2 版本号规则（示例）

```text
文档版本: V主版本.次版本
  V0.x    草稿/在制品 (开发库)
  V1.0    首次评审通过, 进入受控库
  V1.1    一般变更后小版本递增
  V2.0    重大变更/基线升级, 主版本递增

代码/产品版本: V主版本.次版本.修订号 (构建号)
  V2.1.3 (Build 20260825.01)
  └─ 主版本: 不兼容的大版本
     └─ 次版本: 兼容性的功能增加
        └─ 修订号: 缺陷修复
           └─ 构建号: 每次自动构建, 保证二进制可追溯

规则要求:
  1. 版本号在全项目唯一、单调递增
  2. 文档版本和其描述的代码版本要有追踪关系
  3. 发布标签 (Tag) 必须和版本号严格一致
  4. 禁止出现 "最终版"、"最终版2"、"真的最终版" 这类命名
```

### 5.3 配置项登记表（台账模板）

| CI 编号 | 名称 | 类型 | 责任人 | 所在库 | 当前版本 | 所属基线 | 入库日期 | 存放位置/路径 | 备注 |
|:---|:---|:---|:---|:---|:---|:---|:---|:---|:---|
| XM03-SRS-001 | 软件需求规格说明 | 文档 | 张工 | 受控库 | V1.2 | 分配基线 | 2026-03-10 | /受控库/需求/ | - |
| XM03-SRC-001 | 飞控软件源码 | 代码 | 李工 | 受控库 | V2.1.0 | 产品基线 | 2026-07-20 | svn://.../tags/V2.1.0 | 含构建脚本 |
| XM03-3RD-001 | 第三方组件清单 | 记录 | 王工 | 受控库 | V1.0 | 产品基线 | 2026-07-20 | /受控库/发布/ | 5 个组件 |

**台账铁律**：
- 一物一码，入库即登记
- 责任人到人，不能只写"开发组"
- 位置写具体路径/标签，不能写"在库里"
- 台账本身也是受控文档，变更留痕

## 六、配置库建设与权限管理

### 6.1 工具选型

| 工具 | 适用 | 涉密环境注意 |
|:---|:---|:---|
| SVN + TortoiseSVN | 文档+代码混合、权限目录级控制、上手简单，军工项目存量最大 | 内网部署，版本服务器加固 |
| Git（GitLab 内网版/国产化替代） | 代码为主、分支模型复杂的团队 | 必须内网部署，禁止公网 SaaS；注意代码防拷贝导出 |
| ClearCase 等传统工具 | 历史项目维护 | 老项目延续使用 |
| 文档/PDM 系统 | 受控文档的流程化管理 | 选有涉密资质的国产产品 |
| 变更/问题工具 | JIRA 内网版或国产替代（如自研变更系统） | 同样内网化 |

> 现实建议：文档用受控文档系统/SVN 管理，代码用 SVN 或内网 Git；**工具不重要，"流程在工具里固化、操作有日志"才重要**。

### 6.2 权限矩阵（示例）

| 角色 | 开发库 | 受控库 | 产品库 |
|:---|:---|:---|:---|
| 开发人员 | 读写自己模块 | 检出读；检入需 CMO 执行/审批后 | 只读已发布版本 |
| 测试人员 | - | 只读基线 | 只读 |
| CMO | 读 | 建目录、标签、基线；按审批检入 | 无直接写权限（走发布审批） |
| 项目经理 | 读 | 读 | 读 |
| QA | 读（审计需要） | 读 + 审计日志查看 | 读 |
| 产品库管理员 | - | - | 写入（凭发布审批单） |
| CCB 主任委员 | - | - | 发布审批 |

**权限管理三条红线**：
1. **最小权限**：默认无权限，按角色申请授予
2. **职责分离**：开发不能有受控库的直接写权限；CMO 不能有产品库直接写权限
3. **权限定期复核**：人员调离/项目结束当日回收权限，每季度复核一次并留记录

### 6.3 备份与恢复

```text
备份策略 (写进配置管理计划):

  备份内容: 三库全量数据 + 权限配置 + 操作日志
  备份方式: 全量 (周) + 增量 (日)
  备份介质: 双份异地存放 (涉密介质按密级管理, 专柜保管)
  保留周期: 至少覆盖产品全生命周期 + 合同约定的售后年限

最关键的一步: 恢复演练!
  □ 每半年至少做一次恢复演练 (不是只备份不验证)
  □ 演练记录: 演练时间、操作人、恢复出的数据量、校验结果
  □ 评价必查项: 只有备份记录没有恢复演练记录 = 不符合
```

## 七、基线管理流程

### 7.1 建立基线的标准流程

```text
① 配置项成熟
   开发库工作产品完成自测/自审
        │
        ▼
② 提交入库申请
   开发人员填写《配置项检入申请》, 附工作产品
        │
        ▼
③ 评审 (技术评审 + 同行验证)
   按 GJB5000B 同行验证要求组织评审, 形成评审记录/问题清单
        │
        ▼
④ 问题闭环
   评审意见全部关闭 (修改 → 确认 → 签字)
        │
        ▼
⑤ CMO 检入受控库
   按命名编号规则登记, 打标签, 更新配置项台账
        │
        ▼
⑥ 建立基线
   CCB/授权人审批《基线建立申请》
   冻结该组配置项版本, 形成基线清单
        │
        ▼
⑦ 发布基线通知
   CMO 向项目组发布《基线发布通知》
   (内容: 基线名称、包含 CI 及版本、标签、生效日期)
        │
        ▼
⑧ 配置状态纪实更新
```

### 7.3 基线管理常见问题

| 问题 | 风险 | 正确做法 |
|:---|:---|:---|
| 代码打了标签但文档没同步 | 交付版本文档与代码不一致 | 基线是"一组"配置项，文档代码同时冻结 |
| Tag 被移动/覆盖 | 基线不可复现 | 标签创建后锁定，只允许新标签 |
| 基线建立了但没人通知 | 开发还在旧版本上改 | 基线发布通知必须分发并签收 |
| 紧急修改绕过流程直接改 | 追溯链断裂 | 紧急也要补单（先口头批、24h 内补流程） |

## 八、变更控制（核心中的核心）

### 8.1 变更分类

| 类别 | 定义 | 审批权限 | 典型例子 |
|:---|:---|:---|:---|
| 重大变更（I 类） | 涉及已基线化的需求、接口、架构，影响功能/性能/进度/经费 | CCB 集体评审，必要时报顾客/上级 | 需求增减、接口协议变更、核心算法替换 |
| 一般变更（II 类） | 不影响基线外部约定的局部修改 | 授权分级审批（PM/主任设计师） | 局部缺陷修复、文档错别字以外的小完善 |
| 紧急变更 | 试验/交付现场必须立即处理 | 先授权后补单，限期补办 | 靶场试验阻断性问题 |

### 8.2 标准变更流程

```text
  ┌──────────┐
  │ 变更提出  │  填写《变更申请单》(或问题报告)
  │ 任何人    │  写清: 变更内容、原因、影响分析
  └────┬─────┘
       ▼
  ┌──────────┐
  │ 受理与分类│  CMO 登记台账, 编号, 判定 I/II 类
  └────┬─────┘
       ▼
  ┌──────────┐
  │ 影响分析  │  责任人评估: 影响哪些配置项/文档/测试/
  │          │  进度/成本/风险 (影响分析是必填, 不能空)
  └────┬─────┘
       ▼
  ┌──────────┐
  │ 评审审批  │  I 类 → CCB 评审表决
  │          │  II 类 → 分级审批人
  └────┬─────┘
       │ 不批准 → 关闭申请, 记录原因
       ▼ 批准
  ┌──────────┘
  │ 变更实施  │  从受控库检出 → 修改 → 必要的回归测试
  └────┬─────┘
       ▼
  ┌──────────┐
  │ 验证确认  │  同行验证/测试确认变更正确, 无副作用
  └────┬─────┘
       ▼
  ┌──────────┐
  │ 检入入库  │  CMO 凭审批单+验证记录检入, 版本升级
  └────┬─────┘
       ▼
  ┌──────────┐
  │ 基线更新  │  涉及基线的, 更新基线并重新发布通知
  └────┬─────┘
       ▼
  ┌──────────┐
  │ 闭环归档  │  申请单、评审记录、验证记录全部归档
  └──────────┘
```

### 8.3 CCB 怎么运作

**CCB（Configuration Control Board，配置控制委员会）**：

| 要素 | 做法 |
|:---|:---|
| 组成 | 主任（通常主任设计师/技术负责人）、PM、CMO（秘书）、QA、各专业组长，必要时请顾客代表、可靠性/安全性人员列席 |
| 职责 | 审批 I 类变更、审批基线建立与发布、裁决变更争议 |
| 议事规则 | 例会（如每月/里程碑）+ 紧急会；**会议要有纪要、决议要有签字** |
| 决策原则 | 技术可行、影响受控、风险可接受；重大意见分歧上报 |
| 留痕 | 会议通知、签到、材料、纪要、表决意见全部进受控记录 |

### 8.4 变更申请单模板

```text
─────────────────────────────────────────────
            配置项变更申请单
编号: CR-2026-017
─────────────────────────────────────────────
项目: XXXX 飞控软件          提出日期: 2026-08-21
提出人: 李某                 联系: xxx

变更类型: □ 重大(I类)  ☑ 一般(II类)  □ 紧急
紧急程度: □ 高  ☑ 中  □ 低

1. 变更配置项:
   XM03-SRS-001 软件需求规格说明 V1.2 (分配基线)
   关联: XM03-SDD-001 设计说明、相关测试用例

2. 变更内容:
   新增 BIT 自检项 3 条 (具体描述...)

3. 变更原因:
   联试中发现 xxx 故障无法地面检测, 顾客联络单 LR-2026-009 要求

4. 影响分析:
   □ 影响需求: 是 (SRS 3.2.5 节)
   □ 影响设计: 是 (SDD 4.3 节)
   □ 影响代码: 是 (bit_check 模块, 约 200 行)
   □ 影响测试: 是 (新增 3 个用例, 回归范围...)
   □ 影响进度: 预计 5 人日, 不影响里程碑
   □ 影响经费: 无
   □ 影响安全性/可靠性: 已会签安全性人员, 无新增风险
   □ 影响其他配置项/分系统: 无

5. 审批意见:
   组长意见: ____________ 签字/日期
   CCB 决议: ☑ 同意  □ 不同意  □ 修改后再审
   主任委员签字: ________ 日期: ______

6. 实施与验证:
   实施人: ___ 完成日期: ___ 新版本: V1.3
   验证方式: ☑ 评审  ☑ 回归测试  验证记录编号: TR-2026-022
```

> **评价时的关注点**：变更单不是"签字表"，**影响分析、验证记录、版本变化三者必须能对上**。最典型的不符合是：单子写了改需求，但代码版本没变、测试没回归——闭环造假。

## 九、配置状态纪实（CSA）

**配置状态纪实（Configuration Status Accounting）**：记录和报告配置项、基线、变更的状态，回答"现在库里到底是什么状况"。

### 9.1 要记录什么

```text
状态纪实的三类数据:

  1. 标识状态
     - 有哪些配置项、编号、版本、责任人、位置
  2. 变更状态
     - 多少变更申请: 提出/审批中/实施中/已闭环/被拒绝

  3. 基线状态

```

## 十、配置审核

### 10.1 两类配置审核

| 审核 | 全称 | 回答的问题 | 典型时机 |
|:---|:---|:---|:---|
| **FCA** | 功能配置审核（Functional Configuration Audit） | 产品的**功能**是否满足需求规格？测试是否证明了这一点？ | 产品基线建立前、定型前 |
| **PCA** | 物理配置审核（Physical Configuration Audit） | 交付的**物理产品**和文档是不是与基线完全一致？能不能照此复现生产？ | FCA 通过后、交付/定型前 |

```text
FCA 关注: 一致性 (需求 ↔ 实现 ↔ 测试)
  - 每条需求是否都有设计对应、测试覆盖? (需求追踪矩阵)
  - 测试是否全部通过? 遗留问题是否经过批准/有让步接收?
  - 变更是否全部闭环?

PCA 关注: 一致性 (文档 ↔ 产品 ↔ 介质)
  - 交付介质里的程序是不是受控库里的那个版本?
  - 源文件、构建脚本、编译环境能否重新构建出同一二进制?
  - 版本标识、文档清单、标签、注释是否与实物一致?
  - 现场安装版本和产品库版本是否一致?
```

### 10.2 FCA 检查单（示例）

```text
□ 需求规格说明已基线化且为最新版本
□ 需求追踪矩阵完整: 需求 → 设计 → 代码 → 测试用例 双向可追踪
□ 所有需求均有测试用例覆盖, 覆盖分析经过评审
□ 测试用例全部执行, 通过率/遗留缺陷清单与实际相符
□ 遗留缺陷均有问题报告, 分级准确, 处理意见经过审批
□ 所有变更申请已闭环, 无"先改后批"未补单情况
□ 接口测试、强度/边界等专项测试结论齐备
□ 第三方组件清单与实际使用一致, 安全审查通过
```

### 10.3 PCA 检查单（示例）

```text
□ 交付介质 (光盘/U盘/固件) 与产品基线清单逐项核对一致
□ 介质内程序版本号/构建号与标签 Release_Vx.y 一致
□ 从受控库源码重新构建, 与交付二进制比对一致 (或差异有说明)
□ 用户手册、操作手册版本与交付软件版本匹配
□ 文档清单、产品清单、装箱单实物一致
□ 软件版本标识 (启动画面/关于页/版本命令) 与基线一致
□ 安装包、配置数据、标定参数均为受控版本
□ 产品库入库手续齐全, 发放记录与现场版本可对应
□ 涉密标识、密级标注、介质编号符合保密要求
```

### 10.4 审核流程

```text
① 计划: 写进配置管理计划, 明确时间、审核组 (QA + 独立技术专家, CMO 配合)
② 准备: CMO 提供配置项清单、基线、变更台账、追踪矩阵
③ 实施: 按检查单逐项核对 + 实物抽查 + 必要的重新构建
④ 报告: 出《配置审核报告》, 列不符合项
⑤ 闭环: 不符合项开问题报告, 责任人整改, CMO/QA 验证关闭
⑥ 结论: 全部关闭后给出"建议建立产品基线/同意交付"结论
```

> **抽查技巧**：审核时评价员最爱做的事——随便点一个基线版本，让你现场从库里重新构建并和交付件比对；再点一个变更单，让你翻出影响分析和测试记录。这套链路平时跑得通，审核就不怕。

## 十一、发布与交付管理

```text
受控发布流程:

  发布申请 → 发布评审 (含 FCA/PCA 结论) → CCB/顾客代表批准
     → 从受控库冻结版本 → 产品库入库 → 制作交付介质
     → 清点封袋/封箱 → 交接签字 → 现场安装确认 → 归档

关键记录:
  □ 《软件发布申请/审批单》
  □ 《产品入库单》
  □ 《交付清单/装箱单》(逐项: 名称、编号、版本、数量、密级)
  □ 介质交接回执 (谁收的、什么时候、版本是多少)
  □ 现场安装/版本确认记录
```

**交付后变更（售后阶段）**：现场发现的问题同样要走"问题报告 → 变更 → 新版本发布"的完整链路，不能直接在现场改程序。现场版本必须能在产品库和发放记录中找到对应记录——这是交付后评价/审计的高频抽查点。

## 十二、涉密环境的特殊要求

军工项目大多涉密，配置管理还要叠加保密要求：

| 要求 | 落地做法 |
|:---|:---|
| 物理隔离 | 配置库部署在涉密内网，与互联网物理断开；严禁代码上传公网 Git/SaaS |
| 三员分立 | 系统管理员、安全保密管理员、安全审计员分设，CMO 不兼任超级管理员 |
| 介质管理 | 光盘/U盘编号登记、密级标识、专柜存放、带出审批、闭环归还 |
| 操作审计 | 库的检出/检入/权限变更日志保留，安全审计员定期审计 |
| 最小知悉 | 按项目、按模块授权，跨项目看不到库 |
| 人员离场 | 调离当日冻结账号、回收介质、交接台账签字 |
| 打印拷贝 | 受控文档打印受控、带水印/编号，电子拷贝审批留痕 |
| 密码与国产化 | 按项目要求使用国产密码、国产操作系统/数据库/中间件适配版本入库管理 |

## 十三、GJB5000B 评价准备：证据链怎么组织

### 13.1 评价方式认知

评价员通过三种客观证据判断实践是否落地：

```text
客观证据 = 访谈 (问人) + 文档 (查记录) + 演示 (看系统)

  访谈: 问开发人员"你改代码走什么流程?" —— 答不上来 = 实践没落地
  文档: 查计划、台账、变更单、评审记录、报告 —— 对不上 = 不符合
  演示: 现场看库、现场构建、现场走一张单 —— 演不出来 = 直接暴露

三者必须互相印证, 不能只有文档。
```

### 13.2 CM 证据清单（按实践组织）

| 实践主题 | 应准备的证据 |
|:---|:---|
| 配置管理策划 | 配置管理计划（有审批、有修订记录）、与项目计划的关联 |
| 配置标识 | 配置项清单/台账、命名编号规范、配置项与阶段对应关系 |
| 配置库 | 三库结构（现场可看）、权限矩阵及审批记录、备份与恢复演练记录 |
| 基线建立 | 基线申请/审批、评审记录、基线清单、发布通知及签收 |
| 变更控制 | 变更单全套（申请→影响分析→CCB 纪要→实施→验证→闭环）、变更台账 |
| 问题报告 | 问题报告单及与变更单的关联、遗留问题批准记录 |
| 状态纪实 | 历月配置状态报告、报告分发记录 |
| 配置审核 | FCA/PCA 计划、检查单、审核报告、不符合项闭环记录 |
| 发布交付 | 发布审批、入库单、交付清单、回执、现场版本确认 |
| 人员能力 | CMO 任命/授权记录、培训记录 |

### 13.3 证据组织方法（PIID 思路）

```text
PIID (过程实施指示数据) 式整理:

  对每条实践建立一行记录:
    实践要求 | 制度依据 | 直接证据(记录编号) | 间接证据 | 存放位置 | 备注

  要求:
  1. 每条实践至少有一条可出示的、本项目真实发生的证据
  2. 证据之间编号互链 (变更单 ↔ 评审纪要 ↔ 测试记录 ↔ 版本标签)
  3. 证据分散在工具里的, 提供索引清单, 保证评价时 5 分钟内调得出
  4. 全项目周期持续积累, 严禁评价前集中伪造/补签
```

### 13.4 高频不符合项（提前自查）

| # | 高频问题 | 自查方法 |
|:---|:---|:---|
| 1 | 配置项识别不全（环境、第三方组件、标定数据漏管） | 拿"能否完整复现构建"倒查 |
| 2 | 三库只有制度没有实际隔离 | 现场用普通开发账号尝试写受控库 |
| 3 | 有备份无恢复演练 | 查演练记录，要求现场演一次 |
| 4 | 变更单影响分析一句话、无验证记录 | 抽查 10 张单逐张核对 |
| 5 | 先变更后补单、日期逻辑矛盾 | 比对变更单日期与库提交时间 |
| 6 | 需求追踪矩阵断链 | 随机选 3 条需求双向追踪 |
| 7 | 基线无评审记录或发布后无人知晓 | 查评审材料和通知签收 |
| 8 | 交付介质版本与产品库不一致 | 抽查介质现场比对 |
| 9 | 权限矩阵与实际授权不符 | 导出库权限清单与矩阵比对 |
| 10 | 人员调离后账号未回收 | 查账号清单与在职名单 |
| 11 | 开发人员不知道配置管理流程 | 随机访谈 2-3 名开发 |
| 12 | 文档版本与代码版本不匹配 | 抽查手册中版本号与实际程序 |

## 十四、最佳实践与经验

### 14.1 让流程跑得动的 7 个做法

```text
1. 流程内嵌工具
   检入按钮旁边就是变更单号必填项 —— 不靠人自觉, 靠工具强制

2. 台账自动化
   SVN/Git 日志自动汇总变更; 标签与变更单关联;
   状态报告 80% 数据自动生成, CMO 只做分析判断

3. 规则一页纸
   命名/版本/权限做成一页纸速查卡贴在组里, 培训半小时讲完

4. 变更不过夜受理
   CMO 每天固定处理入库/变更申请, 不卡开发脖子
   (流程被骂"碍事"通常是因为响应慢, 不是因为严格)

5. 里程碑前强制审核
   每个基线建立前做一次迷你审核, 问题早暴露,
   不要全堆到 FCA/PCA

6. 紧急通道但不例外
   现场紧急变更: 授权人口头批准 → 实施 → 24 小时内补单
   通道存在, 但记录一个都不能少

7. CMO 早介入
   项目策划第一天就进组, 别等代码快写完了才来建库
```

### 14.2 CMO 的数据看板（建议每月维护）

| 指标 | 含义 | 健康参考 |
|:---|:---|:---|
| 变更闭环率 | 已闭环变更 / 总变更 | ≥ 95% |
| 变更平均闭环周期 | 从提出到闭环天数 | 按项目设阈值，持续观察趋势 |
| 先改后批率 | 无单提交次数 / 总提交次数 | 0 |
| 基线一致性问题数 | 审核发现的版本不一致项 | 趋零 |
| 备份成功率 / 恢复演练频次 | - | 100% / ≥ 半年 1 次 |
| 权限复核完成率 | - | 季度 100% |
| 需求追踪覆盖率 | 有测试覆盖的需求 / 总需求 | 100%（按合同要求） |

### 14.3 和其他实践域的接口

| 接口 | 配合点 |
|:---|:---|
| 项目管理 PM | CM 计划纳入项目计划；变更影响进度/成本时同步 PM |
| 质量保证 QA | QA 独立审计 CM 执行；CM 审核发现的问题进 QA 不符合项台账 |
| 产品研制 PDM | 研制各阶段工作产品的入库、评审、基线时点 |
| 同行验证 PR | 评审是入库/基线化的前置条件，评审问题与变更单关联 |
| 供方协议管理 SAM | 供方交付件按合同要求入库、验收、纳入基线 |
| 知识管理/资产 | 可复用组件从受控库沉淀到组织资产库 |

### 14.4 常见认知误区

| 误区 | 正解 |
|:---|:---|
| "配置管理就是管代码" | 文档、数据、环境、介质、第三方组件全是配置项 |
| "CMO 就是库管员" | CMO 管的是完整性、可追溯性和变更秩序，是技术管理岗 |
| "评价前补一补记录就行" | 补的记录经不住日期、日志、访谈三方印证，真实性问题最致命 |
| "小项目可以不搞这么复杂" | 可以裁剪，但裁剪要写进计划并经过批准，不能直接不做 |
| "基线影响效率" | 基线保护的是并行工作和可复现性，没基线返工成本高得多 |
| "变更单是走形式" | 影响分析和验证是变更单的灵魂，缺了它变更控制等于零 |

### 16.1 概念速查

| 概念 | 一句话 |

| CSA | 配置状态纪实，定期报告库与变更的状态 |
| FCA | 功能配置审核：功能是否符合需求、测试是否证明 |
| PCA | 物理配置审核：实物与基线文档是否一致、可否复现 |
| RTM | 需求追踪矩阵：需求↔设计↔代码↔测试双向追踪 |
